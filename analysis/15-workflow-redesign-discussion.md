## 一、现状基线（讨论起点）

三层流程（light/heavy/huge）、三道门、四份产物文档（design.md / spec.md / plan.md / map.md）。

重流程五段：

1. 阶段 1 访谈（grilling）→ design.md + spec.md 骨架 → 门 1
2. 阶段 2 机械分解（补用例详版 + 切任务）→ 门 2
3. 阶段 3 开发（TDD → verification → code-review → commit → 记账 → 上下文预算）
4. 门 3 最终确认
5. 回退协议

已确认的一个事实：`spec.md` 在阶段 1 就产出（骨架版），阶段 2 补成用例详版，同一文件经历两次批准、两种形态。

## 二、诊断：三个结构性问题

### 2.1 门 1 的判据作用在手段而非目的

现状红线是「design.md 开放问题应为空」。它约束的是**访谈是否完整**（手段），而不是**开工风险是否可控**（目的）。具体三处缺陷：

- **二元门槛**：开放问题只有「空 / 非空」两态，等于用颠覆型问题的标准去管装饰型问题。
- **把完整性当作可解除性**：含糊的真实风险取决于**未定项的爆炸半径**，不取决于未定项的数量。现在的红线对「十个已定但彼此矛盾的决策」完全失明。
- **逼出过重兜底件**：清不空就只能先建地图，于是多一份 map.md、多四个术语（destination / fog / ticket / frontier）、多一个命令，且地图走完还要「翻译」回 design.md，信息在这一步必然损耗。

### 2.2 巨流程的判据难以自我判断

「一次访谈装不下」「存在说不 sharp 的区域」这两条要求用户在开工前判断访谈规模——而这恰恰要先试访谈才知道。地图真正独占的价值只有两条：AFK 调研可并行派发、中断恢复的记账单位更细。为一个判不准的判据、两条独占价值，付整套文档体系的代价。

### 2.3 四份文档用了四种划分轴

| 文件 | 划分轴 |
|---|---|
| design.md | 文档性质（决策快照 vs 实现契约） |
| spec.md | 技术层（数据结构 + 接口） |
| plan.md | 时间（任务 + 进度） |
| map.md | 成熟度（探路 vs 落定） |

四种轴混用导致三个真实病症：

- **同一事实活在两处**：模块鸟瞰在 design、接口清单在 spec，靠检查项「图与鸟瞰一致」修补设计缺陷。
- **边界不可判**：「数据结构定义放 design 还是 spec」无机械判据，争议只能靠回退协议裁决。
- **形态漂移**：spec.md 骨架 → 详版的两次批准。

## 三、议题 1：门 1 准入改为三条可判定条件

把判据从「开放问题是否为空」换成「剩余未定项的爆炸半径是否已被围起来」。

### 3.1 三条件

1. **方向唯一**（不可协商）：方案概述里只有一个活方案，被否方案各一行「名称 + 放弃原因」。
2. **骨架确定**：数据结构、模块边界、接口面清单已定（后经议题 2 修订为「接口草案不存在结构性矛盾」，见 4.4）。
3. **未定项已圈定**（替代「开放问题为空」）：未定项表四列——未定项 / 爆炸半径 / 若不解决的后果 / 处置。

### 3.2 准入规则

- 爆炸半径为**整个特性 / 数据结构 / 跨模块**的，一律阻塞，必须门 1 前解决。
- 爆炸半径圈在单模块或单函数内、且 spec/contract 中标为**暂定契约（provisional）**的，允许带入门 1：用例表留空并标注，对应任务排到最后、依赖标记为「需解决 X 后才能开始」。
- 带入门 1 的暂定契约在**门 3 时必须为零**——这是防滥用的闸门：有明确关闭时限的豁免才叫圈定，没有时限的豁免就是拖延。

### 3.3 连带改动

- design-template：开放问题节改为未定项表（四列），节名从「开放问题」改为「未定项」——语义从「缺德」变为「有账」。
- spec/contract：新增 provisional 标记。
- dev/SKILL 门 1 三条准入 + 门 3 零 provisional 硬约束。
- 判巨判据收窄为单条：**方向无法收敛**（不是「工作量大」，而是「要做什么本身还悬着」）。地图从「巨型需求的必经之路」降级为「发散期的可选收敛工具」。

### 3.4 已否决的替代方案

- **门 1 只批第一个 tracer-bullet 切片，后续切片就地访谈、design 改 append-only**：否。架构级决策天然需要全局视野，第一个切片假设的数据结构会被后续切片推翻，而那时已有代码——把风险从「前期访谈过长」换成「后期返工」，方向反了。
- **保留二元门槛、只把 map.md 合并进 design.md**：否。只解决文档数量，没解决判据的层次错误；且 design.md 同时有「活的探路态」与「冻结快照」两副面孔，会削弱它作为门 1 冻结物的可信度。

## 四、议题 2：阶段 1 拆成 1a / 1b，伪代码降为访谈素材

### 4.1 出发点

现状阶段 1 把两类信息源的答案塞进同一轮提问：

| 问题类型 | 典型问题 | 答案从哪来 |
|---|---|---|
| 需求类 | 搜索要不要支持同义词？搜不到时用户看到什么？ | 只有用户能答 |
| 实现类 | 函数叫 findPosts 还是 searchPosts？放哪个模块？ | 读代码库能推出 |

grilling 现有铁律「事实是你的活，决策是用户的活」没有区分**需求决策**与**实现决策**，所以实现类问题被当决策交付给用户。需补第三条：实现决策是 AI 的活。

### 4.2 1a：只定需求（HITL）

产出 brief 的：背景与问题、目标与非目标、方案（一句话级）、权衡、未定项表。

结束条件：非工程师也能独立读完并说「这就是我要的」。
明确不做：数据结构、接口签名、模块划分、命名。

### 4.3 1b：接口设计（AFK + 一次可行性审）

输入：1a 的 brief + 现有代码库。
动作：读代码找可复用结构 → 出数据结构定义（真实语法）+ 关键调用的伪代码（调用形状与数据流，不写函数体）→ 列「实现决定清单」→ 切交付批次。

产出：brief 的「可行性核查」节。

### 4.4 伪代码的三条边界

| 边界 | 规定 |
|---|---|
| 精度上限 | 只写调用形状与数据流，不写函数体逻辑 |
| 精度下限 | 签名、数据结构、返回类型必须是真实语法，不是散文 |
| 身份 | 伪代码是**访谈素材，不是契约**——契约必须可判定（签名 + 后置条件 + 用例） |

推论：伪代码是保真度工具，不是契约工具；它留在 brief 作为「当时为什么方案可行」的证据，不升级、不搬运进 contract。

### 4.5 1b 的防线：「实现决定清单」

1b 是 AFK 阶段，最容易的问题是 AI 推出一套与用户心智不符的接口还当成事实。草案必须单列一节：

```markdown
## 实现决定（1b 自定，请扫一眼有无异议）
- 复用既有 Paginated<T> 而不新建分页类型 -- 理由：项目已有 3 处使用
- 索引放内存不做持久化 -- 理由：未定项 2 未定，先按最小可行
- 接口放 src/search/ 新模块 -- 理由：模块鸟瞰要求搜索独立成层
```

没有这节，1b 就是在偷决策。

### 4.6 门 1 批什么

条件 1（方向唯一）与条件 3（未定项圈定）不变；条件 2 从「已经设计好」改为「**接口草案不存在结构性矛盾**」——门 1 此刻本就没有足够信息把接口设计到位，强行要求「已设计好」只会让 1b 变成「为了让门通过而填满的表」。

用户在门 1 只做两个判断：

1. 「这需求是我要的吗？」（读 brief）
2. 「这骨架撑得住吗？」（读可行性核查节 + 实现决定清单）

「四件套是否齐全」不是门 1 的事，是门 2 的事。

### 4.7 切片：两次收敛

现状切片只在阶段 2 做，但切片依据在阶段 1 就产生，晚一步会出问题——等到用例详版写完才切，接口可能已被设计成「必须一次性全部实现」的形状（如所有接口共享一个尚未定义的全局状态），想切也切不动。

- **第一次收敛（1b）**：顺手切「交付批次」，宏观。它同时反向验证条件 2——某数据结构若必须整体建好才能用（无法只建一半），它就是一个骨架阻塞项，必须门 1 前定死。
- **第二次收敛（阶段 2）**：用例详版写完后按「一组 seam 条目从红到绿」精确切任务。

一句话：1b 切出**交付顺序**，阶段 2 切出**可执行单元**；后者不能违反前者（若不违反不了，说明 1b 的接口设计有结构问题，回退到 1b，不硬在阶段 2 重切）。

### 4.8 边界规则

**接口设计只能澄清需求，不能产生需求。** 若 1b 发现草案暴露了 1a 未覆盖的需求矛盾（如「排序需要 relevance 概念，但需求里没提」），回 1a 补访谈，不就地拍板。

## 五、议题 3：文档体系按批准层级重划（brief / contract / plan）

> **2026-11-01 后续修订**：本节的三文件是讨论中间态。最终落地为**四层**：`brief.md` / `plan.md` / `spec.md` / `tasks/T<n>.md`，已落进 `devflow/skills/dev/references/`。以技能文档为准。

### 5.1 新划分轴

一条轴贯穿全部：**谁批准 + 批准后谁能改**。

| 层级 | 批准者 | 批准后修改权限 | 变更代价 |
|---|---|---|---|
| 需求层 | 门 1 | 冻结，只能走回退 | 最高 |
| 契约层 | 门 2 | 可改，每次改必须登记 | 中 |
| 执行层 | 无需批准 | AI 自治维护 | 零 |

好处是**机械可判**：「这条内容属于哪份文件」的答案是「它被门 1 批过了吗」——不需要理解语义，只需查历史。

### 5.2 三个文件

```
docs/plans/<YYYY-MM-DD>-<slug>/
├── brief.md      需求与方案       门 1 批准 → 冻结
├── contract.md   数据与接口契约    门 2 批准 → 演进须登记
└── plan.md       任务与执行状态    无需批准 → AI 自治
```

**brief.md**（取代 design.md）：背景与问题 / 目标与非目标 / 方案 / 约束 / 权衡 / 未定项 / 可行性核查（接口草图 + 实现决定 + 交付批次）。

关键决定：**模块鸟瞰不进 brief**。它本质是「有哪些接口面」，唯一价值是与接口清单一致，必须与清单同文件。brief 只留一段文字级模块列表（模块名 + 一行职责），够用户判断方案对不对。

**contract.md**（取代 spec.md）：模块结构（鸟瞰 + mermaid 图）/ 数据结构 / 接口规格（四件套 + 用例 + 覆盖声明）/ 接口面清单 / 非 seam 模块与视觉验收 / 变更记录。

关键决定：contract 从诞生就是契约形态，**不再有「骨架 → 详版」的漂移**。1b 的伪代码草案留在 brief，不升级、不搬运。

**plan.md**：保持，但变纯——删掉「编码方向」（那是设计内容，移到 contract），只装全局约束 / 任务清单 / 任务详情（端到端行为、涉及、接口组引用、验收标准、依赖）/ 开发记录。

### 5.3 map.md 被消解

| map 概念 | 新位置 |
|---|---|
| destination | brief 的「目标与非目标」 |
| 已定决策 | brief 的「方案」与「权衡」 |
| fog | brief 未定项表中标注「还说不精确」的行 |
| ticket | 未定项表中「已能说精确」的行 |
| out of scope | brief 的「非目标」 |

探路不再是独立流程，而是「写 brief 草稿的过程」。纪律保留、载体更换：「每会话最多解一张 ticket」→「每次会话最多落定一条未定项」；「地图不改代码」→「brief 未过门 1 不碰代码」；「ticket 解完回填 commit」→ 未定项表加一列「落定于」。

代价：brief 在探路期会很长。但这是**一份会收窄的文件**，而 map.md 是**一份写完还要翻译成 design 的文件**——前者收敛，后者翻译必然损耗。

### 8.1 superpowers：brainstorming 重建，与本次讨论高度同构

v7.0.0 把 brainstorming 从零重写，v7.0.1 再调。五个机制与本次讨论直接对应：

**① Look Before You Ask**：在已有项目或用户给了上下文（spec、plan、文件）时，先读再开口，「Never ask what the project or their context already answers」。对应本次讨论中「实现类问题该 AI 自己查代码」。

**② 实现选择的所有权分离**：brainstorming 明确询问「哪些 how-it-gets-made 选择（平台、语言、库）你要自己定，哪些交给我」，并规定——

> Any choice you make goes in the design as your call, never as something they agreed to.

这与议题 2 的「实现决定清单」是同构解法，且措辞更锋利：**AI 自定的决定必须显式标为「我的判断」，不得伪装成「用户同意过」**。

**③ Lay out the approaches**：在写文档之前，单独一条消息摆出 2-3 个真实备选（砍掉弱者与违背目标者），推荐一个并说明理由，由用户选。对应议题 1 的「方向唯一」条件。

**④ Size the Work**：按规模自适应文档——小改动写短文档（就是聊过的内容写下来），项目写完整文档；中途变大要停下来说、升级一档。**这与议题 1 的分档主张方向一致，但解法不同：它把分档收在同一技能内自适应，而不是拆成三条流程。**

**⑤ Builder check**：派一个新 subagent，以「将要构建它的人」身份读 design，只报告「还得问的问题」，并三分堆——

- 已回答过 → 直接写进文档
- 次要 → 自己定，在文档里标注为「我的判断」
- 只有用户能答且会改变构建内容 → 一轮内一次性带回

**这是议题 2 中 1b「可行性核查」的成熟形态**，且多两条纪律：只产出一轮问题、无 subagent 时自己扮演 builder 读一遍。

**⑥ HARD-GATE**：design doc 批准前不写任何产品代码（含脚手架、装依赖、建项目）。同时允许「spike」（一次性原型，明说丢弃）跳过整套流程。

### 8.2 superpowers：compaction 生存与「Rulings, not stalls」

**① SKILL.md 的 20,000 字符墙**：Claude Code 在 compaction 后只重新挂载每个技能的前 20,000 字符，超出即永久丢失。v7.0.1 因此把 subagent-driven-development / writing-skills / executing-plans 的大段内容移入 `references/`、按需从磁盘读取，并加测试 `tests/skill-size/test-skill-size.sh` 断言任何 SKILL.md 不得超过 20,000 字节。

给出的真实事故：某次 compaction 后 subagent-driven-development 丢失了「五轮修复上限」，于是一个任务跑了 18 轮修复。

> 对本项目的直接含义：`devflow/skills/dev/SKILL.md` 当前 15,762 字节，是全部技能中最大者，距墙 27%。本次重设计如果把 1a/1b、三条件、回退协议都塞进该文件，很可能撞墙——**文档重划应当同步把 dev/SKILL.md 拆入 references/**。

**② Rulings, not stalls**：跑的 plan 不等人。冲突、歧义、计划缺陷、上限超限，一律自己裁决，并在 ledger 记一行 `Ruling: <决定> — <理由> — <错了的代价>`。只有四件事停：不可逆或破坏性操作、安全敏感动作、worktree 外的副作用（merge / push / publish）、计划崩到每一步都是猜。

> 与 devflow 的冲突：devflow 阶段 3 规定「Critical 或方案性偏离计划 → 暂停询问用户」。superpowers 认为这是把判断成本转移给了人，且停一天什么也买不到；它选择「错了让人看得见、能撤销」。

**③ ledger 落盘**：每个 plan 独占 `.superpowers/sdd/` 下 workspace，进度写 `progress.md`。理由是观察到的最贵失败——**compaction 后 controller 重新派发了整段已完成任务**。devflow 用 plan.md 承担同一职责，机制等价。

### 8.3 skills：流程被拆成可组合的小技能，且默认并行

**① 管线拆解**：`to-spec`（把当前对话合成为 spec，**不访谈**，只综合已知）→ `to-tickets`（切 tracer-bullet tickets + blocking edges，发布到 issue tracker）→ `implement`（单 ticket）/ `implement-spec`（整个 spec）。

> 对应议题 2：`to-spec` 明确「Do NOT interview the user; just synthesize what you already know」——**需求访谈与契约合成分离**，与 1a/1b 拆分同向。

**② implement-spec 是并行派发**：tickets 是 task graph，永远存在一个 ready frontier；每个 ticket 一个 fresh implementer subagent、各自 worktree、各自 branch，完成后由 **merger subagent** 合入 integration branch，全部完成后再整体 code-review。通信原则是「sparse + context pointers」（指向 spec/ticket/研究笔记/前次 commit，不复制内容）。

> **直接推翻 devflow 的 ADR-0002（串行任务派发）**。ADR-0002 的三条理由之一是「devflow 明确舍弃了 worktree 隔离，没有隔离就没有并行的安全前提」。上游的答案是把隔离补回来：worktree 隔离 + merger subagent + integration branch。这不能靠论证否掉，需要实证。

**③ wide refactor 的例外**：`to-tickets` 承认某些改动（重命名一列、改一个共享符号的类型）无法切出能独立变绿的垂直切片，给出 **expand–contract** 序列：先并存新形态 → 按爆炸半径分批迁移（每批一 ticket）→ 最后删除旧形态。这是 devflow 的 tracer-bullet 规则缺的一块。

**④ wayfinder 迁到 issue tracker**：地图与 tickets 不再是 markdown 文件，而是 `wayfinder:map` label 的 issue + child issues；blocking 用 tracker 原生依赖关系（为的是在 UI 里**可视化** frontier）；认领用 **assignee**（替代 devflow 的「每会话一 ticket + git 提交」fallback）；结论写成 resolution comment。

> 对应议题 3：devflow 正打算把 map 消解进 brief，上游反而把 map 从文件搬到了 tracker——**双方都认为 map 不该是 markdown 文件，但替代方向相反**（消解 vs 上移）。这一条会影响 5.3。

**⑤ tdd 的 seam 前置确认**：写任何测试前，先写下待测 seam 清单并与用户确认；每个 seam 附一行「catch 什么 / miss 什么」；尽量用最高处的 seam，理想数目是一次改动一个 seam。

> devflow 目前把 seam 设计放在 spec 骨架里由门 1 批准，隐含了这件事；上游把它显式化为「测试前确认」的动作。

**⑥ code-review 双轴并行**：Standards 轴与 Spec 轴各派一个平行 subagent，报告分开呈现、**禁止合并重排**（理由：一个轴能掩盖另一个轴）；Standards 轴内置 12 条 Fowler smell 基线，repo 自己的标准可覆盖基线。

> devflow 的 code-review 是单轴合并裁决（规格符合 + 代码质量同一份报告）。上游的双轴分离值得吸收。

**⑦ 术语迁移**：`CONTEXT.md` / `CONTEXT-MAP.md` 已并入 `GLOSSARY.md`（含 `git mv` 迁移指引）；domain-modeling 技能统一维护 GLOSSARY + ADR + triage labels；新增 `GLOSSARY.md` 里的 _Flagged ambiguities_ 一节记录「曾经混用过什么、怎么裁决的」。

**⑧ grilling 措辞修正**：每个问题措辞成「yes = 接受推荐答案」，避免「同意」意味着答 no。

### 8.4 对本次讨论的三类结论

| 本次讨论的主张 | 上游核对的结论 |
|---|---|
| 1a/1b 拆分（需求 vs 接口） | **被验证**：superpowers 用「实现选择所有权 + builder check」实现同一目标；skills 用 to-spec/implement 分离实现同一目标。上游都没用「两阶段访谈」的说法，而是「同一技能内自适应 + 一次 builder check」 |
| 门 1 判据从「问题清空」改为「爆炸半径圈定」 | **未直接对应**：superpowers 用 HARD-GATE + builder check 的三分堆来保证「不留隐性假设」，没有引入暂定契约与爆炸半径的概念。我们的方案在这一点上是独有设计，需自行验证 |
| 三文件（brief/contract/plan）按批准层级划分 | **部分被反驳**：superpowers 只有 design doc + plan 两份（契约并入 design 的「实现决策」节）；skills 是 spec（issue）+ tickets。两者都不设独立契约层。**「契约必须独立成文件」这个论断在我们的讨论里没有被充分论证** |
| map 消解进 brief | **方向相反**：上游把 map 迁到 issue tracker 并保留为独立产物。若本项目没有 tracker，消解进 brief 仍成立；若有，则应重新考虑 |
| 串行派发（ADR-0002） | **被推翻，待实证**：上游用 worktree + merger subagent + integration branch 做并行，且已发布 |
| 「Critical → 暂停问用户」 | **受到挑战**：上游主张「rulings, not stalls」，只有四类动作才停 |
| 伪代码作为访谈素材 | **无直接对应**：superpowers 用「spike（可丢弃原型）」承担提高保真度的职责，而不是伪代码。我们的伪代码方案更轻，但缺少 spike 那种「能跑」的说服力 |

## 九、落地与实证（2026-11-01 补记）

讨论落成技能文档后，做了两次端到端真实运行（空项目、空仓库、Node 24）。结论按发生顺序：

### 9.1 门 2 被砍掉是错的

第三轮讨论里判断「计划阶段只是机械分解，不值得单独设门」，落地时据此废掉了门 2（只保留一句「给用户一份清单，这不是门，是通知」）。

第一次实跑：agent 在门 1 之后一口气跑完切片、规格、契约、3 个任务、整特性终审，直接停在门 3。**整个会话 assistant 只发了 3 条文本**，中间一百多条全是工具调用。用户的原话是「第二步没有让我审阅」。

根因不是执行不力，是设计漏洞：**一个不停顿的通知，在流式输出里等于不存在**。「不是门」这个定位，实际上让它不必停下来。

修法：恢复门 2，呈报形态定为「任务清单 + 每个任务的接缝与用例条数 + 覆盖标准档位 + 九条自查结果（逐条）+ 三个问题」，文件在呈报时已写好，用户直接打开看。原 design/spec 两文件方案的门 2 是「批计划」，现在的门 2 是「批切片与契约」，职责变了。

第二次实跑验证通过：门 2 正确停下，呈报完全符合模板。

### 9.2 干跑暴露的三个模板缺口

没派 agent，自己拿假想需求填了一遍四份模板，发现：

1. **依赖要看用例能不能跑**。T3 的用例含中文场景，但中文分词在 T5——代码能编译，用例跑不绿。切片规则补了一条。
2. **接缝数量对不上**。`brief` 7.2 写两个接缝，写 `spec` 时发现需要三个。九条自查里原本没有一条能抓这个，补了第 7 条。
3. **测试规格缺编号列**。`spec` 的覆盖标准要写「落在哪：T3 #1」，但契约的用例表没有 `#` 列。模板补上，并规定改编号要同步改 spec。

### 9.3 第二次实跑的耗时分布

66 分钟总量：门 0→门 1 占 20m47s（写 brief 与等审阅），门 2 只占 2m59s（切片 + spec + 两份契约 + 九条自查）。

**时间花在需求上，后面就快。** 这是继续投入 brief 质量的依据，也是「先看再判」这个入口设计的正面证据。

同一次运行还验证了 intake 的一条规则确实有用：它指出 `git shortlog -sn` 已能满足需求，阻止了一个无意义任务；并发现 `AGENTS.md` 写死项目定位，塞第二个工具等于改范围——摆出来让用户裁决，没有自己选边。
