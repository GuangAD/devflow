# devflow 流程全解——从任务描述到门 3

> 依据 v3.0.0 + 2026-09-17「阶段 3 子代理纪律硬化」后的 skills 原文整理,供阅读理解;规范契约以各 SKILL.md 与 references 为准,本文与其冲突时以前者为准。

## 1. 资源地图

**命令(5)**:/dev(主入口,classifier)/ dev-map(巨流程决策地图)/ dev-resume(断点续做)/ dev-doc(知识沉淀)/ dev-review(代码库巡检)

**纪律技能(6)**:grilling(访谈)/ domain-docs(词汇表+ADR)/ tdd(红绿循环+mutation check)/ debugging(根因先行)/ verification(证据先于声称)/ code-review(独立评审+分级处置)

**references**:implementer-prompt / reviewer-prompt / re-review-prompt(三个派发模板)、design / spec / plan 三个产物模板、design-checklist(十条自查)、map-template(地图模板)

## 2. 全景

```
用户任务描述
     │
  /dev ── classifier ──┬─ 轻 → 轻流程(零门,直接干)
     │                 ├─ 重 → 重流程(三道门)──────────────┐
     │                 └─ 巨 → /dev-map 决策地图 ──fog 散尽──┘
     │                                              │
     │   阶段1 访谈(grilling+domain-docs)→ design.md+spec 骨架
     │   门1 【人】批设计 → 阶段2 计划(机械分解)→ 用例详版+plan.md
     │   门2 【人】批计划 → 阶段3 开发(自治循环)→ 整特性终审
     │   门3 【人】验收 → 收尾
     │
横切:/dev-resume(恢复)/ /dev-doc(沉淀)/ /dev-review(巡检)
```

设计哲学一句话:**人只守三道门(方向、路径、结果),agent 在门间自治;一切状态落盘于文档与 git,信任靠独立证据而非自述。**

## 3. 入口:classifier 三分与升级棘轮

| 判定 | 信号 | 去向 |
|---|---|---|
| 巨(优先判) | 一次访谈装不下;存在「连问题都说不 sharp」的区域;列不出完整 design tree | /dev-map |
| 重 | 新功能/新模块/新项目;改动数据结构;新建文件多;「做个/加个/实现一个」;无设计文档覆盖 | 重流程 |
| 轻 | 修 bug、调文案、改配置、重构既有函数、已有计划中的任务 | 轻流程 |

拿不准 → 问一句并附推荐。**升级棘轮**:只可轻→重→巨单向升(修 bug 发现根因在数据结构→转重;访谈装不下→转巨),不可反向降——误判代价不对称:重判轻在方向未定时开工,返工按 design tree 规模放大;轻判重只多花一轮访谈。

## 4. 轻流程(零门)

1. 有歧义且不问就会错 → 单句澄清;否则按最合理理解干,汇报假设;
2. 修 bug → **debugging**:无根因不修——先建「一条命令跑一次能变红」的复现信号,再定位根因、假设一次一变量、回归测试写在修复前;三次修复失败 = 架构问题,停下谈设计;
3. 行为改动 → **tdd**:红绿循环,waiver 留痕;
4. 宣称完成前 → **verification**:本回合跑过验证并读全输出;
5. 提交,汇报:做了什么、验证证据、waiver 及理由、所做假设。

## 5. 重流程(三道门)

### 5.1 阶段 1:访谈(grilling + domain-docs)

- **design tree**:讨论建模为决策树,根是「要做什么」,每个决策分支下挂子决策;
- **round + frontier**:每轮把「前置已落定、现在就能问」的问题一次性抛出,每题编号附推荐答案(用户可一个词接受);回答解锁下游 → 重算 frontier;
- **分工铁律**:事实 agent 自己查(可派 subagent),绝不反问用户「查一下就知道」的;决策必须交用户拍板,禁止自问自答;
- **已有地图时**:map.md 的「已定决策」直接作为访谈既有共识,只补空白;
- **domain-docs 全程并行**:设计前读 CONTEXT.md 与相关 ADR,不重新争论已有决策;术语当场入词汇表;满足三条件(难逆转+缺上下文会困惑+真实权衡)的决策当场提议 ADR;ADR 不可修改只可被取代;
- **结束条件**:frontier 为空 → 总结共识,等用户确认;中途变卦 → 重算受影响分支并重新交付确认。

**产物两份**(写前过 design-checklist 十条自查,任一不过 = 开放问题非空,不得呈报):

- `design.md`(**决策快照**,门 1 后冻结):背景/目标与非目标/方案概述+模块划分鸟瞰(附可选 mermaid 架构图:图承载依赖方向与数据流向,文字保留职责边界,互补不重复;属冻结范围,修订走回退协议)/技术栈约束/权衡(链 ADR)/开放问题(必须为空);
- `spec.md` **骨架**(**实现契约**,随开发演进):数据结构说明(代码块类型定义)/ seam 接口规格(按模块分节,每条目四件套:签名/后置条件/副作用与可重入性/错误行为,每条 ≥1 条 pinned case 带事实源)/ 接口面穷举清单(全部公共导出一行一个,标 seam/非 seam)/ 非 seam 与视觉验收(数值预算必附机检方案)/ 编码方向 / 空「变更记录」节。

### 5.2 门 1:设计确认【人】

呈现两份文档路径+各节摘要,**停等明确批准**,修订循环至批。此门前一行代码不写。**批准后立即提交**(此后停止可经 /dev-resume 从阶段 2 接续)。

### 5.3 阶段 2:计划(机械分解,不跑访谈)

1. spec 骨架补成**用例详版**:每 seam 条目 3-8 条用例(典型+边界+反例,期望值附事实源);
2. 按 plan-template 写 `plan.md`:任务 = 一组 seam 条目**从红到绿**(tracer-bullet vertical slice:纵向贯穿、可独立验收、单会话可容纳);详情含端到端行为/涉及/编码方向/接口组/数据结构落地/验收标准(机检注明命令与判定;门 2 预判本机不可达项)/依赖(硬依赖定派发顺序;纯顺序偏好给推荐排序);全局约束从 design.md 逐字继承;可预判的 TDD waiver 在此预登记;
3. 边界规则:暴露设计级空白 → 回退协议,禁止在 plan.md 夹带设计决策;纯执行细节 agent 自定。

### 5.4 门 2:计划确认【人】

呈现用例详版+任务清单,批计划即批拆分与详版。**批准后立即提交 spec 与 plan。**

### 5.5 阶段 3:开发(自治,任务间不停顿)

#### 单任务八步循环

| 步 | 做什么 | 技能/模板 | 执行者 |
|---|---|---|---|
| 1 | 记 `BASE=$(git rev-parse HEAD)` | — | controller |
| 2 | 实现(双形态) | implementer-prompt / tdd | implementer 或 controller |
| 3 | 亲验 + git status 核对 | verification | controller |
| 4 | 独立评审 | code-review + reviewer-prompt | reviewer |
| 5 | 处置发现 | code-review 分级 + re-review-prompt | controller |
| 6 | 提交 | — | controller |
| 7 | 落盘 | plan-template | controller |
| 8 | ready set + 预算 | context_usage | controller |

**步 1 · 记基线**:HEAD 即本任务 diff 边界——评审取 `git diff BASE..HEAD`、回退协议的线性历史都以此为准;BASE 短哈希随第 7 步落盘。

**步 2 · 实现(双形态)**:
- **优先派 implementer**(自包含简报五节:任务要求/接口规格与用例/全局约束逐字/上游已完成(接口签名+「结论」)/工作区状态)。执行纪律:TDD vertical slice 逐用例红→绿;期望值来自独立事实源,禁止放宽断言换绿;不超出接口组;不改三份文档;不提交;**不派发任何 subagent**(能力声明);完成后**写入自证**(git status 实况粘贴进「工作区改动」节)。发现设计空白 → 停手报告;
- **fallback 会话内实现**:读 tdd,逐条用例红(预期原因)→ 最小实现 → 绿;waiver 留痕或对照预登记。

**步 3 · 验证**:铁律「implementer 回报不算数,必须自己重跑」。verification 五道门:识别证明命令 → 新鲜完整跑 → 读全输出+退出码 → 核对支持声称 → 才开口。**改动清单与 git status 实况逐项核对,不符即整体降信**(防沙箱假写入)。本机不可达的验收项显式标注「未验证」留遗留,禁止等价替代关闭。

**步 4 · 评审**(生产发现):diff 写入 `.review/<任务号>.patch`(项目内相对路径,不灌上下文)派发;reviewer 只读取证(read/grep/find/ls),命令类核查写成请求交 controller 代跑,带 shell 也不得用;先读差异(BLOCKED 不算失败),不信任 implementer 报告;每条发现带 文件:行号 + 理由(controller 视为 patch 内坐标,裁决前回源码核对)。**双裁决**:规格符合(缺失/夹带/误解)+ 代码质量(真实行为测试、错误处理、命名、边界、过度构建)。无 subagent → 冷却 self-review 并标注「非独立」。可异步,但处置前不得提交下一任务。

**步 5 · 处置**(消费发现):Critical(错误行为/破坏数据/安全/测试伪造)→ **暂停问用户**;Important → 修复+重跑覆盖测试+复审(re-review 收窄范围:只答「是否解决、有无引入新问题」,reduced reasoning tier);Minor → 记录,门 3 汇总;⚠️ → controller 亲核归类。升级线:implementer 停手(设计空白)或同一发现两轮不过 → 升级用户决策。「评审声称 vs 源码实况」分歧 → 静态路径证明 + 复审复核,controller 不代做变异(变异归 implementer 红绿循环)。

**步 6 · 提交**:controller 统一提交,message 引用任务号与要点;每任务一 commit 的线性历史是回退协议前提。

**步 7 · 落盘**:勾选+回填 commit 哈希;开发记录追加一行(`任务 N | BASE xxx | 完成 | 评审:… | waiver | 结论:… | commit xxx`;动过 spec 注明「变更记录已登记」;补 pinned case 注明 mutation check 结果;**写入「下一步用得上的结论」**——跨任务、跨会话唯一软依赖通道);删除 `.review/` diff。

**步 8 · ready set + 预算**:重算 ready set(硬依赖全完成且自身未完成),从其中取下一任务;调 `context_usage` 读占比——**≥45% → 任务边界提示开新会话**(先写结论再停,提示 /dev-resume);工具不可用退回三条可数信号(同一节文档第三次重读/最近两任务都需回翻接口/记不清早前决定);底线:4 个任务后必查一次。

#### 依赖与派发

依赖字段构成 DAG,每次重算 ready set;**串行**执行(vertical slice 天然撞文件、无 worktree 隔离、线性历史是回退前提);串行的红利:上游提交后代码真实存在,下游读代码即得接口,隐性依赖不必穷举;派发时把上游签名与「结论」贴进简报。

#### 上下文被压缩后

先重读 design.md、spec.md(含变更记录)、plan.md 再继续;信文档与 git,不信记忆。主动切换与被动中断同走 /dev-resume 一条协议。

### 5.6 整特性终审 + 门 3【人】

终审:全部任务完成后对 `git diff <特性起点>..HEAD` 整体评审——任务衔接、跨任务一致性(命名/接口对齐)、挂起 Minor 是否需处理;每个修复必有一次复审。

门 3:呈现验收清单逐项结果、各任务评审记录、waiver 清单、完整提交列表、遗留 Minor;确认后清理 `.review/` 等,写收尾总结(含沉淀的 CONTEXT.md/ADR 清单)。

### 5.7 回退协议

- 计划期发现设计错误 → 回访谈,只重开受影响分支;design/spec 重过门 1;plan 重过门 2(此时代码不存在,零成本);
- spec 与 design 冲突以 design 为准;spec 修订登记「变更记录」;触及 design 决策必须走回退,禁止就地改;
- 任何阶段发现设计缺陷:停下报告(缺陷是什么/影响哪些任务/修订方向),不将错就错、不偷偷绕过。

## 6. 巨流程:/dev-map(决策地图)

前提:**地图产决策,不产代码**。不该用:design tree 一轮能收(那是「重」);广度扫描没扫出 fog(停下问用户)。

- **地图**:`docs/maps/<日期>-<slug>/map.md` 单文件,五节:destination(先定,定死范围)/备注/已定决策/fog/out of scope;索引不是仓库——每条决策只活在自己的 ticket 里;
- **ticket 四类**:调研(AFK,派 subagent)/原型(HITL,粗糙具体物提高讨论保真)/访谈(HITL 默认,调 grilling+domain-docs)/任务(解锁某个决策才有位置);
- **fog vs ticket 判据**:能不能把问题**说精确**(不是能不能回答)。能 → 开 ticket(哪怕被阻塞);不能 → 留 fog,别预先切小块;
- **建图(一会话)**:定 destination → 广度扫 frontier → 建图 → 开能说精确的 ticket 并接依赖 → 放调研 subagent → 停;
- **走图(每会话一 ticket)**:读图 → 认领(frontier 第一张或点名)→ 解 → 勾选+gist 进「已定决策」+提交回填 → 补 ticket/清 fog/关出界 ticket;
- **出口**:fog 散尽、frontier 空 → 已定决策汇总进 /dev,design.md 直接生成,访谈只补空白;地图留档不删;
- **纪律**:已定决策只可被取代不可就地改;全程 domain-docs 并行;想动手的冲动 = 该交接给 /dev 的信号。

## 7. design.md 与 spec.md:分工、seam 与缺口处理

**分工**:design.md 是决策快照(门 1 冻结,回答「为什么这样」);spec.md 是实现契约(随开发演进,回答「接口长什么样、怎么算对」),任何修订登记「变更记录」;冲突以 design 为准。

**seam 的确定**:先穷举、后标注——「接口面穷举清单」列全部公共导出一行一个,逐个问「是否承载需要被测试钉住的行为」:是 → seam(四件套 + pinned case);否 → 非 seam(有状态附重用语义)。判据可操作化:能用四件套描述且能构造 pinned case(后置条件可断言、错误行为可触发、期望有独立事实源)。类型定义、barrel、常量天然非 seam。模块名三处对齐:design 鸟瞰(A)、spec 模块节(B)、plan 接口组(C)。

**开发期 seam 没覆盖全**(判据:是否触及 design 决策):
- **小缺口** → spec 变更记录登记 + 回填穷举清单(防线:reviewer 对照计划外导出的变更记录,「没要求却做了」按夹带抓);
- **设计空白** → implementer 停手 → controller 回退协议(重过门 1、门 2),禁止就地绕过;
- **验证期发现无测试入口** → 「无正确 seam」本身是架构发现:补 pinned case 走 mutation check,提给 /dev-review 作深化候选。

漏登的兜底:穷举清单的完备性检查在整特性终审硬执行(pi-w 实证曾拦下漏登的 19 个类型导出)——机制的价值不在「保证不漏」,在「漏了必有门能抓住」。

## 8. 支撑命令

| 命令 | 工作 |
|---|---|
| /dev-resume | 定位计划 → 重建上下文(plan 的「结论」通道 + design + spec 含变更记录 + git log 核对勾选,不一致以 git 为准)→ 查残局(丢弃需用户确认)→ 续做(阶段 3 循环;只有 design+spec 时从阶段 2 继续)。恢复后先重算 ready set;已批计划不重过门 2;新需求是变更不是恢复(小变更走轻流程,设计级走回退) |
| /dev-doc | domain-docs 的独立入口:定对象(术语/ADR/会话提取)→ 核门槛(查重;ADR 三条件,不满足要说明为什么不写)→ 按格式写入 → 回报。ADR 只在用户认可决策后写;术语须与代码现实交叉验证 |
| /dev-review | 巡检:git log 找热点 → subagent 按摩擦信号扫描(无局部性/浅模块+删除测试/测试抽取的纯函数/紧耦合泄漏/seam 缺失)→ 报告写 docs/reviews/(每候选一张卡+首推)→ 不擅自开工,选中后提示走 /dev |

## 9. 阶段 3 的信任链(为什么这样设计)

八步循环构造并检验一条信任链:步 2 产出主张(implementer 报告)→ 步 3 亲跑证据否决二手主张(且 git status 核对封死「沙箱写入假成功」)→ 步 4 独立 reviewer 双裁决(诊断者与处置者分离:reviewer 只有只读取证权,发现原样到达 controller,处置可审计)→ 步 5 分级处置、只有 Critical 级穿透自治层到达用户 → 步 6-8 把终态固化到 git 与 plan.md。

每个技能都不是装饰:tdd 保证每条行为有测试钉住,verification 保证声称有新鲜证据,code-review 保证规格与质量有独立裁决,plan-template 保证状态可无损恢复,context_usage 保证自治不透支上下文——**任何时刻进程被杀,步 7 的落盘记录都够下一个会话从步 8 无损接续**。
