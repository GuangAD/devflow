# mattpocock/skills 项目分析

## 一、这个项目是什么

这是 TypeScript 圈知名教育者 Matt Pocock 开源的 AI 编码技能集合,叫 "Skills For Real Engineers"。它不是软件,而是二十多个 Markdown 文件,每个文件教 AI 编码代理(agent)一门具体的工作方法。

作者的出发点是:AI 编码的失败,大多不是模型不够聪明,而是使用流程缺了环节。他把最常见的四种失败各对应一种 remedy:

1. **你说的和 agent 理解的不是一回事。** 你说"加个邀请功能",agent 按自己的理解写了一堆代码,做完才发现方向错了。解法是开工前先让 agent 把你"拷问"清楚。
2. **agent 说话做事啰嗦、用词混乱。** 项目里的概念没有统一叫法,agent 每次都要重新猜。解法是维护一份项目词汇表,让人和 agent 说同一种语言。
3. **agent 写的代码跑不起来。** 没有快速反馈,agent 就是蒙着眼写代码。解法是测试驱动开发和一套严格的调试流程。
4. **代码库越写越乱。** agent 写码速度太快,腐化速度也快。解法是把"每天投资设计"变成可执行的动作。

整套技能刻意做得很小、很散,不搞大一统框架。作者明确说:BMAD、Spec-Kit 那类工具"接管了你的流程",出了问题你没法修;他的技能你随时可以改,人始终握着方向盘。

## 二、跟着一个例子走一遍完整流程

假设你维护一个 SaaS 项目,想加"团队邀请"功能。下面是使用这套技能的完整过程。

### 第 0 步:一次性配置(setup)

新仓库第一次使用前,你运行 `/setup-matt-pocock-skills`。agent 会自己查看仓库:git remote 指向哪里(判断用 GitHub 还是 GitLab)、有没有现成的配置文件、是不是 monorepo。然后问你几个问题,每个都带推荐答案,你回"好"就能通过:issue 记在哪里?分诊标签用默认的吗?文档放哪?问完后它写三个配置文件到 `docs/agents/` 目录,并往 `CLAUDE.md` 追加一段说明。

以后所有技能需要"发工单"、"贴标签"时,都是**运行时读这些配置文件**,而不是写死某个平台。所以换 tracker 只需要改文件。

### 第 1 步:把想法拷问清楚(grill-with-docs)

你对 agent 说:"我想加团队邀请功能。" 放着不管的话,agent 会按脑补的理解直接开写——这正是失败模式一号。所以第一步是 `/grill-with-docs`。

这个技能内部运行一个叫 `grilling` 的访谈方法,核心机制叫"design tree 加 round":

- agent 把你还没定的决策整理成一棵树。每一轮,它把**所有前置条件已经确定、现在就能问**的问题一次性列出来,每题附上自己的推荐答案。比如第一轮可能是:邀请有数量上限吗(推荐:按套餐区分)?用邀请链接还是邮件(推荐:链接)?受邀者没有账号怎么办(推荐:注册后自动加入)?
- 你回答之后,有些答案会解锁新的问题(你选了链接邀请,它才能问"链接有效期多久"),于是它重新计算一遍,抛出第二轮。
- 访谈里有个分工原则:**查资料是 agent 的活,做决策是你的活。** 问题需要了解代码现状时,它自己派 subagent 去读,不反过来问你。
- 访谈过程中,`domain-modeling` 纪律同时在跑。你随口说"过期后邀请就失效了",它会立刻停下追问:"失效是指链接点不开,还是接受过邀请的人被移出团队?这是两件事。" 你们敲定的每个术语,当场写进项目根目录的 `CONTEXT.md` 词汇表;每个难回头的大决定(比如"邀请令牌存 Redis 不进主库"),当场写成一份 ADR(架构决策记录)。

**结束条件很严格**:那棵决策树必须每条分支都走到,没有任何问题是被含糊带过的。然后 agent 总结一遍共识,你确认后,访谈才算完。这之前一行代码都不会写。

**为什么词汇表这么重要**:有了 `CONTEXT.md`,你以后只需说"物化级联出问题了",agent 就秒懂——不用每次解释二十个字。省 token 是小事,命名一致、跨会话理解不衰减才是大事。

顺便一提:如果你不在代码仓库里(比如只是在琢磨一个点子),用 `/grill-me`,同一个访谈方法但不写任何文件。

### 第 2 步(岔路):有问题是"跑起来才知道"的(prototype)

**这一步解决什么问题。** 访谈中有些设计问题在纸面上争不出结果。比如聊到邀请链接的状态时:链接过期了点开会看到什么?团队满员时呢?已经是成员的人又点了一次呢?这类"状态之间跳转顺不顺、界面直不直观"的问题属于手感问题,必须真正点一点、看一眼才有答案——靠嘴争论半小时也说服不了谁。而 agent 的默认工作方式是纯文字推理,这类问题放任不管,它就会猜一个写进正式代码,上线后才发现手感不对。原型这一步就是把"猜"提前变成"试"。

**完整的一次岔路有四个动作。**

动作一,从主会话交接出去:运行 `/handoff`,agent 把当前对话压缩成交接文档存到系统临时目录——访谈进行到哪、已定了什么、待解决的那个具体问题是什么。不在当前会话里直接做原型,是因为主会话装着整个 design tree,是后面写规格的地方;原型要写代码、跑调试,这些琐碎细节灌进来会把主会话撑大冲淡。交接等于把"问题"从主线程摘出来,支线干完只把"答案"带回来。

动作二,开一个新会话做原型(这就是 `/prototype` 技能)。新会话的 agent 先判断问题属于哪一类,因为两类问题做出的东西完全不同:问"这个逻辑或状态模型对不对",它做一个双击就能在浏览器打开的单 HTML 文件——一排按钮加状态展示,你点"点击邀请链接",它显示状态机走到了哪一步、页面该显示什么文案;把参数改成"已过期"再点,看跳转对不对;还内置几个导览标签页,自动带你走"满员加已是成员加链接仍有效"这种最难想清的组合场景。关键是每次点击后把完整状态摊出来——你不是在用一个页面,是在审问一个状态机,不懂开发的同事也能上手。问"这个界面长什么样",它在同一路由上做几个风格截然不同的版本(不是同风格微调,是彻底不同的布局),底部悬浮切换栏一点就换。两类共用几条硬规矩:不许打磨(不写测试、不处理异常、不做抽象,能跑就行);不需要持久化(数据放内存);必须一键能跑(双击或一条命令)。

动作三,把答案交接回去:再跑一次 `/handoff`,这次写的是结论——"过期与满员同时发生时应先提示满员;重复点击应静默跳转"。你把文档带回原来的访谈会话,设计继续。

动作四,结论的去向(最容易被误解的地方)。访谈结束写规格时,原型定稿的状态机以一小段代码的形式内联进规格——这种东西几十行代码比一千字散文精确。原型代码本身不删:提交到一个 `prototype/invite-flow` 之类的独立分支永久留档,规格和工单里放指向它的链接。这就是原技能那句话的含义:"一次性是对写代码方式的要求,不是销毁代码的承诺"——写的时候不按生产标准写,所以永远不进主干;留着是因为它是"当时为什么这么设计"的第一手证据,三个月后有人问起,点开分支就能重现整个推理。

**为什么它是岔路。** 主流程是"想清楚了再动手";原型岔路承认有些事不动手就想不清楚。访谈的结束条件是 design tree 没有任何含糊分支,而原型正是消灭某类含糊分支的工具——问题在原型里被回答了,那个分支才算真正关闭,访谈才能诚实地结束。这个技能单独也能用:任何时候有个设计问题说不清,都可以直接做个原型;它出现在主流程第 2 步,只是它最常见的位置。

### 第 3 步:共识变成规格(to-spec)

访谈的结论只存在于对话里,而对话会被压缩、会丢失。所以多会话的工程需要把它落成一份规格,运行 `/to-spec`。

这个技能**不再问你任何问题**——刚才已经问够了,现在纯综合。它做三件事:

1. 把共识按模板写成规格:问题陈述、方案、一份**穷举式的用户故事清单**(不是三五个,是二十条以上,逼着把边界情况在纸面上想全)、实现决策、测试决策、明确不做什么。
2. 规格里有一条特别的规矩:**不许写具体文件路径和代码片段**,因为它们几周就过期了。规格记录的是决策,不是施工图。唯一的例外是原型验证出的状态机、数据结构片段——那种东西代码比文字精确,可以内联。
3. 写完发布到 GitHub Issues(或你配置的 tracker),打上"ready-for-agent"标签,表示 agent 可以直接领。

写规格之前它还会跟你确认一件事:**测试在哪几个"seam"上做**。seam(seam)是这套技能的关键概念,指模块的公共边界——测试只从公共接口观察行为,不伸进内部实现。它倾向复用现有 seam、尽量少新增,并要你点头认可。这个约定后面会被 TDD 环节严格执行。

### 第 4 步:规格切成工单(to-tickets)

这个功能一个会话做不完,需要拆分。`/to-tickets` 把规格切成若干"工单",切片方式叫"tracer-bullet(曳光弹)":

- 每片**纵向贯穿所有层**(数据库、接口、界面、测试),而不是"先做完所有后端再做前端"的水平切法。
- 每片完成时**可以独立演示**,能真刀真枪跑给你看。
- 每片的大小**恰好一个全新会话能装下**。

工单之间声明依赖("02 号被 01 号阻塞"),形成一个有向无环图,凡是阻塞都已解除的工单随时可以开工。切完它会列出来问你:粒度合适吗?依赖关系对吗?要不要合并或再拆?

连特殊情况都有协议:如果中途需要一次"全局改列名"式的重构,这种改动没法垂直落地(一动就牵动全库),那就走"扩张-收缩"序列——先让新旧两种写法并存,然后一批一批迁移调用点(每批一张工单,期间测试始终是绿的),最后一张工单删掉旧写法。

### 第 5 步:逐个工单实现(implement + tdd + code-review)

从这里开始,**每个工单开一个全新的会话**——因为访谈、规格、切分 ticket 积累的上下文对这个工单没有用处,清空反而干净。新会话里你运行 `/implement`,它按顺序做四件事:

1. 在第 3 步约定好的 seam 上,运行 `/tdd`:写一个失败测试,亲眼看它失败;写**刚好让测试通过**的最少代码;再看它变绿;进入下一个切片。tdd 技能里写死了三种反模式让人防:测试 mock 了内部细节(重构就挂但行为没变)、断言用代码同样的算法算出期望值(同义反复,永远不会失败)、一口气写完所有测试再写实现(验证的全是想象中的行为)。
2. **节奏控制**:类型检查和单个测试文件频繁跑,完整测试套件只在最后跑一次——每次改动都跑全量太慢。
3. 收尾时运行 `/code-review`。它从 `main` 到当前提交做一次 diff,然后**同时派两个互不知情的 subagent**:一个对照仓库的编码规范加一份固定的"Fowler 十二坏味"清单查代码质量;另一个对照原始规格查"要求做的有没有做、没要求的有没有夹带、做了的是不是做错了"。两份报告并列呈现,刻意不合并、不排优先级——因为"代码很漂亮但做错了事"和"功能做对了但破坏项目惯例"是两种独立的失败,合在一起汇报时一方总会掩盖另一方。
4. 提交。

### 支线:线上出了个查不出的 bug(diagnosing-bugs)

以上是功能开发主线。另一类工作是救火,比如"支付回调一天丢一两次,查了两天没头绪"。这种就该用 `/diagnosing-bugs`,它的六阶段里藏着整套技能最狠的一条规矩:

**第一阶段是"建反馈回路",在做出来之前,禁止产生任何假设。** 所谓反馈回路,就是"一条命令,跑一次,能对这个具体的 bug 显示红"。技能里列了十种手段:写失败测试、curl 脚本、重放抓包、headless 浏览器、模糊测试、二分排查……哪条路能通走哪条。本例中,agent 可能把生产抓的回调日志重放进本地消费者,发现复现率只有百分之一点五,然后加并发、压缩时间窗,把复现率拉到百分之四十——**偶发 bug 的目标不是完美复现,是可调试的复现率**。

有了红绿信号,后面才允许:复现并最小化(逐个删变量,直到剩下的每个因素都缺一不可);一次性提出三到五个可证伪的假设并排序给你过目(你的领域知识常能瞬间重排);一次一个变量地插桩验证(调试日志统一带特殊前缀,清理时一次搜索全灭);在正确的 seam 上先写失败测试再修复;最后清理现场,把确认的根因**写进 commit message**,给下一个排查的人留线索。

如果最后发现 bug 没法在任何合适的 seam 上锁死——这本身就是重要发现:说明代码库的结构防不住这类问题,该记录下来,交给 `/improve-codebase-architecture` 去找重构机会。

### 支线:工单堆成了山(triage)

第三类场景是维护:GitHub 上积了二十个 issue,有 bug 报告、功能请求、外部 PR。`/triage` 把它们推过一个小的状态机:待分诊 → 缺信息(等报告者补充)→ 可交给 agent / 需要人做 / 不做。

对每个 issue,agent 会先查代码库确认这个功能是不是**已经实现了**(按领域概念搜,不是按字面措辞搜),再看它是不是以前被拒绝过(拒绝记录存在 `.out-of-scope/` 知识库里,防止同样的请求三个月后又被提一遍)。bug 要真的复现过才能标"可交给 agent";PR 要真的 checkout 跑过测试。分诊完的 issue 附上一份结构化的"agent 任务简报",之后 `/implement` 就能直接领。

### 支线:工程大到看不清路(wayfinder)

最后一类场景最特殊:"我想把整个单租户系统改造成多租户。"这个想法大到——你连要经过哪些决策都说不清。这不是执行问题,是**迷路问题**,`/wayfinder` 专治它。

它把"想清楚"本身变成一张挂在 issue tracker 上的**地图**:一个标着 destination(什么叫做完)的 issue,下面挂着一堆"决策工单"。每张工单是一个待解决的问题,分四种类型:查资料型(agent 后台自己干)、做原型型、谈话决策型、前置手工活型。想不清的问题不硬切,先放进地图的"fog of war"区;每解开一张工单,fog 就散一片,露出新的、现在能说清楚的工单。多个会话可以并行认领不同的工单。

等 fog 散尽尽、路看清了,wayfinder **移交而不建造**:把所有决策汇总进 `/to-spec`,回到第二节的主流程。它的产出是决策,不是代码。

### 日常:代码库保健(improve-codebase-architecture)

功能之外,作者建议每隔几天跑一次 `/improve-codebase-architecture`。它先翻提交历史找**热点**(最近反复改动的文件才值得投资,三年没动的角落不值得),然后派 subagent 在代码库里"散步",找那些"接口十二个方法、实现三十行"的浅模块、"理解一个概念要在八个文件间横跳"的碎片化区域。发现的问题汇总成一份可视化的 HTML 报告(存系统临时目录,不进仓库),每个候选项附改动前后的示意图和推荐强度。你挑中一个,它再启动一轮 grilling 跟你把方案谈细,谈出来的结论就是一个新"想法",自然汇入主流程。

## 三、全部技能清单与作用

编排层(你敲命令触发,决定流程怎么走):

| 技能 | 一句话说明 |
|---|---|
| `setup-matt-pocock-skills` | 每仓库跑一次的配置:issue 在哪、标签叫什么、文档放哪 |
| `ask-matt` | 活地图:不知道该用哪个技能时问它,它知道全部流程关系 |
| `grill-with-docs` | 拷问式访谈,同时维护词汇表和决策记录;主流程入口 |
| `to-spec` | 把访谈共识综合成规格并发布到 issue tracker |
| `to-tickets` | 把规格切成纵向的、可独立交付的工单,声明依赖关系 |
| `implement` | 按工单实现:驱动 TDD,收尾跑双轴评审,最后提交 |
| `triage` | 把积压的 issue 和外部 PR 分诊成 agent 能直接领的任务 |
| `wayfinder` | 超大工程用:在 tracker 上建"决策地图",逐 ticket 解题直到看清路 |
| `improve-codebase-architecture` | 定期巡检代码库,找出值得"由浅加深"的重构候选 |
| `handoff` | 把当前对话压缩成交接文档,用于换工具、换目录、交同事 |
| `grill-me` | 不在代码仓库里时的访谈版,不落任何文件 |
| `to-questionnaire` | 答案在别人脑子里时,帮你写一份问卷发给那个人 |
| `wait-what` | agent 说的你没听懂时,让它用大白话和项目词汇重新讲一遍 |
| `teach` | 跨会话教学:当前目录变成学习工作区,有课程、笔记、进度 |

纪律层(agent 可自动调用,负责把一件事做好):

| 技能 | 一句话说明 |
|---|---|
| `grilling` | 访谈方法本身:design tree、round、frontier 问题、附推荐答案;五个技能共用 |
| `domain-modeling` | 维护 CONTEXT.md 词汇表和 ADR;遇模糊术语当场逼你定义 |
| `codebase-design` | "深模块"设计词汇:接口、深度、seam、杠杆;设计时统一语言 |
| `tdd` | 红绿循环纪律:预约定 seam、三种反模式、重构不属于循环 |
| `code-review` | 双轴评审:代码规范轴和规格符合轴,并行 subagent,分开汇报 |
| `diagnosing-bugs` | 六阶段调试:先建"能变红的一条命令",再谈假设 |
| `prototype` | 一次性原型回答设计问题;结论进主干,原型留档分支 |
| `research` | 后台 subagent 查官方文档等一手资料,产出带引用的笔记 |
| `resolving-merge-conflicts` | 逐块解决合并冲突:追溯两边意图,尽量都保留,绝不中止 |
| `wizard` | 生成 bash 向导脚本,带人逐步完成只有人能做的操作(开页面、填密钥) |
| `writing-for-agents` | 写 agent 消费的文档(技能、AGENTS.md)的规范 |

## 四、技术实现细节

**形态与分发。** 每个技能就是一个文件夹,里面一个 `SKILL.md`(带 YAML 元信息:名字、描述、是否允许模型自动触发)加若干参考文件(比如 tdd 附带测试写法详解)。整包以 Claude Code 官方插件分发,也可以用 `npx skills add` 把文件拷进自己的仓库随意修改。

**调用方式的分轴。** 每个技能要么是"用户触发"(元信息里声明禁止模型自动调用,只能人敲命令),要么是"模型触发"(人和 agent 都能用)。铁律是:编排层可以调用纪律层,编排层之间不互相调用——防止流程套流程变成迷宫。

**组合机制。** 技能之间靠 agent 的"调用另一个技能"动作组合。典型的组合如 `grill-with-docs`,它的正文其实只有一句话:"依次调用 grilling 和 domain-modeling"。共享的原语(grilling、词汇纪律)被五个以上的技能复用,这是它能保持每个文件很小的原因。

**状态放在文件里。** 这套体系没有数据库、没有后台服务,所有状态都是文件:领域语言在 `CONTEXT.md`,架构决策在 `docs/adr/`,平台配置在 `docs/agents/`,工单在 tracker 或 `.scratch/` 目录。任何工具都能读,人也能直接改。

**上下文管理是一门显式学问。** 项目专门写了一篇"阶段边界"指南:一个会话里的每段工作(访谈、实现、验收)结束时,有五个选项——继续、清空、交接文档、派 subagent、压缩——并给出严格的判断顺序:下一阶段需要本阶段的原始推理就继续;本阶段的东西对后面没用就清空;要换工具/换目录/给同事才写交接;能独立跑的活派 subagent;都不成立才压缩。核心洞察是:**压缩和交接都会把一手信息变成有损的二手摘要**,所以能用更便宜的手段就别压缩。

**所有交互都降门槛。** 访谈每题带推荐答案(你回一个"好"就能推进);切分 ticket 后盘问你确认(防粒度拍脑袋);破坏性操作先确认。人的参与被设计成"低成本高频次",而不是"一次性大决策"。

## 五、这套体系的强项与代价

强项:每个技能小而独立,可以只取两三个用;领域词汇表和决策记录是真正的长期资产,越用越值钱;wayfinder 和 triage 覆盖了"超大工程"和"日常维护"两个多数工具不管的场景;人不被框架绑架。

代价:几乎所有流程都要人敲命令驱动,agent 不会自己"想起来"该访谈了;技能之间靠约定组合,没有强制力,agent 偷懒跳步时没有机制拦截;上下文管理(何时清空、何时压缩)依赖使用者的判断。这些代价,正好是第二个项目 superpowers 要解决的。
