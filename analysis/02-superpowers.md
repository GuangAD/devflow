# obra/superpowers 项目分析

## 一、这个项目是什么

Superpowers 是 Jesse Vincent(开源社区老将,RT 工单系统作者)团队做的一套完整的 AI 编码方法论。它和 mattpocock/skills 想解决的问题相同——让 agent 按工程纪律干活——但路线完全相反:skills 项目把技能做小、让人敲命令来掌舵;superpowers 把整套流程做成**自动运转的机器**,agent 一开工就自动进入纪律,人只在关键节点做批准。

它由两部分组成:十几个技能文件(方法剧本),加上一层"强制装置"(安装时往 agent 会话里注入启动指令的钩子脚本)。支持 Claude Code、Codex、Cursor、Gemini CLI 等十几个主流编码工具。

团队的四条信条贯穿所有技能:永远测试先行;用系统化流程代替临场猜测;把简单作为首要目标;先拿证据再下结论。

## 二、强制装置:技能为什么会"自动触发"

这是 superpowers 最核心的工程发明,值得先讲清楚。

每个技能文件本身只是被动的说明书——agent 不去读,它就等于不存在。skills 项目的解法是人来敲命令;superpowers 的解法是**安装时挂一个钩子**:每次会话开始,一段叫 `using-superpowers` 的"宪法"被自动注入到 agent 的上下文里。宪法的内容大意是:

> 只要一个技能有哪怕百分之一的可能适用于当前任务,你就必须先调用它——在任何回应之前,包括在你提出澄清问题之前,包括在你查看文件之前。"我先看看代码再说"是借口,技能教的正是怎么查看。

为了防止 agent 用各种理由绕开,宪法里直接预写了十二种它预计会出现的借口,逐条驳回:"这只是个简单问题"——问题也是任务,先查技能;"我记得这个技能的内容"——技能会更新,读当前版本;"这个任务用不上正式流程"——简单的事会变复杂,用它。

更细的保险在长会话里:上下文压缩之后,注入逻辑会**再次**把宪法塞回去(通过 Pi 这类工具的扩展接口实现,检测到压缩事件就重新标记)。否则长会话干到一半,纪律会随着被压缩的上下文一起消失。

作者甚至给"集成是否成功"定了验收标准:在新工具里装好后,发送一句"我们做个 react 待办清单",如果 brainstorming 技能**没有**在写任何代码之前自动触发,这个集成就是不合格的。

每个技能内部还配有一张"合理化对照表":预写 agent 执行到一半想放弃纪律时的内心戏,以及反驳。"太简单了不用测了"——简单代码也会坏,测试只要三十秒。"已经手工试过了,能跑"——手工测试没有记录、没法重放、高压下必漏。"这已是第三种改法了,再试一次"——三次失败说明是架构问题,不是运气问题。这些表格不是文学创作,是团队拿真实 agent 会话做对抗测试调出来的,贡献者想改一句话都必须附上前后对比的评测证据。

## 三、跟着一个例子走一遍完整流程

假设你对装了 superpowers 的 agent 说:"给我的博客加个评论功能。"以下是接下来自动发生的一切。

### 第 1 步:brainstorming 自动启动,先分类再设计

没有任何人调用技能,agent 自己就开始了 brainstorming。它做的第一件事是**给任务分类,并把分类大声说出来**:

- **Spike(探路)**:任务是"能不能做到"之类的问题,产出是一份结论,代码是次要的。流程最短:说两句方案、你点头、它去试、汇报结果。
- **Bounded(小改)**:改动的是仓库里**已经存在**的流程,比如给现有接口加个参数。注意判定标准是仓库现实,不是你的熟悉程度——"我懂这类应用"不算数,要改的代码必须已经在仓库里。这种走短流程:看现状、问几个关键问题、在聊天里给一段简短设计、等你批准、直接开工,不写正式文档。
- **Architectural(大动)**:新项目、新子系统、会改变组件关系的改动。评论功能对博客来说是全新子系统,落在这档,走完整流程。

分类规则里有一条"棘轮":干到一半发现复杂度超预期,只能**升档**,不许降档。而且每个任务独立分类——"探路的代码写得不错,留着用吧"不行,保留代码是一个新任务,要重新分类重新批准。

评论功能走大动流程。agent 先看项目现状(文件、文档、最近提交),然后**一次只问一个问题**:"评论要支持嵌套回复吗?"……"允许匿名吗?"……问清楚目的、约束、成功标准之后,它提出两到三个方案并附权衡,推荐项放最前面,同时毫不留情地砍掉没人要求的功能(信条:You Aren't Gonna Need It)。

然后它**分段呈现设计**:架构一段、组件一段、数据流一段、错误处理一段、测试策略一段,每段讲完都停下来问"到这里对吗?"。你全部点头后,设计写成文档存到 `docs/superpowers/specs/` 目录并提交 git。写完它还会**自查一遍**:有没有写着"待定"的地方?前后有没有矛盾?范围是不是大到一份实现计划装不下(装不下就先建议拆项目)?有没有能读出两种意思的表述?

最后它把文件交给你:"规格已写好并提交,请审阅,没问题我就开始写实现计划。"——**停在这里等你回复**。

这里就是整套体系的第一道铁闸:**硬性门禁。在人类批准之前,禁止写任何代码、禁止搭任何脚手架。** 官方表述是:仪式可以随任务变小——两句话的设计也算设计——但批准这道门永远不缩放。原因写得很直白:越是看起来简单的任务,越是未经验证的假设造成返工的重灾区。

### 第 2 步:writing-plans,写一份"施工图"

你批准规格后,agent 接着自动进入 writing-plans(大动路径的终点被锁死为这个技能,不许拐去别的)。计划的目标读者被设定为"一个热情但品味差、没有判断力、没有项目上下文、讨厌测试的初级工程师"——也就是说,计划必须详细到不需要任何临场判断。

计划长什么样?先画文件结构:哪些文件新建、哪些修改、各自负责什么——文件专注不是洁癖,agent 对"能一次装进脑子"的代码推理最可靠。然后把工作切成任务,每个任务再切成**两到五分钟一步**,关键在于:每一步连代码都写好。

```
任务 3:评论提交接口
文件:新建 src/routes/comments.ts;测试 tests/comments.test.ts
接口:使用任务 2 定义的 CommentStore.add();产出 POST /api/comments 返回 201

步骤 1:写出失败测试(测试代码原文贴出)
步骤 2:运行 npm test tests/comments.test.ts,预期失败,报"路由未定义"
步骤 3:写出最小实现(实现代码原文贴出)
步骤 4:运行测试,预期通过
步骤 5:git 提交
```

计划里有明文的**占位符禁令**:"待定"、"稍后实现"、"添加适当的错误处理"、"类似任务 2"(必须把代码重复写全,因为执行者可能乱序读任务)。计划头部还有一段从规格**逐字复制**的"全局约束"(版本下限、命名规则等),每个任务默认继承。写完计划,agent 自查三件事:规格的每条要求都能指到某个任务吗?有没有漏网的占位符?任务 3 定义的函数名到任务 7 还是同一个拼写吗?

最后它给你两个执行选项:subagent 驱动(推荐)或本会话顺序执行。

### 第 3 步:开工前的隔离(using-git-worktrees)

不管选哪种执行,动工前 agent 会先确认工作环境是隔离的。它先检测自己是不是已经在一个独立工作区里(比对 git 的两个内部目录路径是否一致,还有专门的检查防止把 git 子模块误判成工作区);如果不是,优先用当前工具自带的工作区功能,实在没有才手动 `git worktree add` 建一个到 `.worktrees/` 目录(建之前先确认这个目录被 git 忽略,否则会把整个工作区文件提交进仓库)。

然后自动安装依赖(按 package.json、Cargo.toml 等文件探测用哪个包管理器),再**跑一遍全量测试确认基线是绿的**。基线是红的就停下来问你——带着红色基线开工,之后每次测试失败都说不清是谁的锅。

### 第 4 步:subagent-driven-development,流水线开工

这是整个项目工程含量最高的部分。选了 subagent 驱动后,你的主 agent 变成一个**controller**,它给自己立了规矩:**自己一行业务代码都不写**。每个任务走这么一圈:

**派活。** controller 从计划文件里抽出当前任务的全文,存成一个"任务简报"文件,然后派一个**全新上下文**的 implementer subagent。给 subagent 的东西精确到五项:一句定位(这个任务在项目里的位置)、简报文件路径(并告诉它"需求以简报为准,精确数值都在里面")、前序任务定下的接口签名、controller 对计划里模糊之处的裁决、报告文件的路径。之所以抠到这个程度,是因为团队实测发现:把会话历史粘进派发词,曾搞出四万两千字符的提示,其中百分之九十九是无用信息。**精确值只出现在简报里,永远不让 subagent 去读整份计划。**

另外有个铁则:**implementer 和 reviewer 都不许再派自己的 subagent**。Worker 私自 spawn 一个评审员,等于同一个 diff 花两份评审钱,而且私设的评审不算数。

**干活与汇报。** implementer 照简报做测试驱动开发,写好代码,提交,自查一遍,把详细过程写进报告文件,然后只回四行话:状态(DONE 完成 / DONE_WITH_CONCERNS 完成但有疑虑 / BLOCKED 干不了 / NEEDS_CONTEXT 缺信息)、提交号列表、一行测试结果、疑虑。四种状态各有预案:有疑虑先看疑虑再送审;缺信息就补;干不了要诊断原因——缺上下文就补,需要更强推理就换个更强的模型重派,任务太大就拆小,如果是**计划本身错了**,controller 裁决修正、记档、再派。绝不允许"无视求救、原样重试"。

**评审。** implementer 报完成后,controller 把这段时间的完整差异(提交列表、变更统计、全部代码变化)打包成一个文件,派**评审 subagent**。reviewer 拿三样东西:任务简报、implementer 报告、差异文件,外加从规格逐字复制的全局约束。它的模板里写着几条很有意思的纪律:把 implementer 的报告当作未经核实的主张——报告里说"按 YAGNI 故意留白",这也是主张,是作者给自己打分;不重复跑 implementer 已经跑过的测试,报告就是测试证据;每条发现必须带文件和行号;实在无法从差异判断的,标出来交还 controller。最后它必须给出**两个独立裁决**:规格符合吗(缺了什么、多了什么、理解错了什么)?代码质量过关吗?两个都过才算过——implementer 的 self-review 不能替代这道评审。

**修复循环。** 发现严重问题就进循环:第一到第三轮,把发现原文发回**原 implementer**(它的上下文还在,最了解自己的代码);第四、五轮,换一个**全新 implementer 并升一级模型**——团队的经验是,三轮都修不好的任务,多半是 implementer 看不见自己的问题。每轮修复后必须做一次**范围收窄的复审**:只验证那几条发现是否解决、修复本身有没有引入新问题,不允许借机漫无边际地重审。五轮还修不完就"熔断":controller 逐条裁决——评审错了的,记录理由搁置;确实有问题但不影响后续的,记录后推迟;真要命的,裁一个最小修复方案记档带进下一个任务。**每条裁决都必须落到 ledger,静默丢弃被明文禁止。**

**ledger。** 每个计划有一个独立的临时工作区,里面一个进度文件,第一行是计划文件名(身份标识),每完成一个任务追加一行。为什么非要这个文件?团队记载的最贵事故:controller 的会话被压缩后,忘了哪些任务做过,把**整个已完成的任务序列重新派了一遍**。所以规矩是:压缩之后,信 ledger 和 git 历史,别信自己的记忆。

**模型分档。** 并不是每个 subagent 都用最强模型:计划里代码都写好的"转录型"任务用最便宜的;跨文件集成用中档;架构决策和最终全分支评审用最强的。还有一条反直觉的经验:最便宜的模型干多步任务经常要花两三倍的来回次数,总账反而更贵——所以中档才是多步任务的下限。派发时必须**显式写明模型**,因为不写就继承主会话的最强最贵模型,悄无声息地烧钱。

**controller 的行为纪律。** 两条最突出。其一,任务之间**不停下来请示**——不会冒出"要我继续吗"这种消息;它被要求自己裁决歧义和小缺陷然后继续走,理由是"错误的裁决顶多造成看得见、可撤销的返工,停在问题上白费人类一整天"。裁决要按固定格式记档:决定了什么、为什么、错了损失什么。只有四类事允许停下:不可逆或破坏性操作;安全敏感动作;工作区之外的副作用(合并、推送共享分支、发布);计划烂到每条路都是瞎猜。其二,controller**永远不亲手修代码**——既污染自己的上下文,又绕过了评审。

**收尾。** 所有任务完成后,做一次**全分支终审**(用最强模型,并把之前搁置的小问题一并交给它判断哪些必须修才能合并);有问题就派**一个**修复 subagent 带全部清单(不逐条派,团队实测逐条修复的总开销超过所有任务之和);然后 controller 把 ledger 里所有裁决汇总成一份"我替你做的决定"清单交给人类,每条附上"错了会损失什么"——这是它替你做主的部分唯一的暴露渠道。最后删掉临时工作区(git 历史就是档案),进入收尾技能。

(没有 subagent 工具的环境走备胎 `executing-plans`:读计划、先批判性挑毛病、严格照碎步执行。核心纪律就一条:阻塞、看不懂、验证反复失败——立即停下问人,不许猜。)

### 穿插全程的三个常驻纪律

**TDD(test-driven-development)。** 铁律只有一行:**没有先看到测试失败,就不许写生产代码。** 由此派生的细节都很硬:如果发现自己在测试之前已经写了代码——删掉,重来,不许"留着当参考"(留着就必然会照着抄,等于还是测试后写);写完测试必须**亲眼看它失败**,而且是"路由未定义"这种预期原因的失败,不是拼写错误的失败;测试一写完就通过,说明它在测已有行为,修测试。绿色之后允许重构,但重构不属于红绿循环——只做清理不加行为。它还给了张"卡住了怎么办"对照表:不会写测试,就先写你希望存在的那个函数调用;测试特别难写,说明设计有问题,听测试的话。

**systematic-debugging。** 任何 bug、测试失败、异常行为,先走四阶段:第一,根因调查——通读错误信息(答案常就在里面)、稳定复现、查最近改了什么、多层系统在每一层边界插桩取证再定位;第二,模式对比——找同库里能正常工作的相似代码,完整读完参考实现("略读等于埋雷"),列出所有差异;第三,单变量假设——"X 是根因,因为 Y"写下来,做最小改动验证,失败就换假设,不许往上叠补丁;第四,测试先行的单一修复——不许"顺手改进",不许捆绑重构。中间有条红色的线:**修三次还没好,就不再是运气问题——停下,和人类讨论是不是架构本身错了。**

**verification-before-completion。** 完成声称的门卫。规则:做出任何"完成了/修好了/通过了"的声明之前,必须在**这一条消息里**重新运行过验证命令、读过完整输出。禁用词:任何"应该可以了"、"大概没问题"。连"agent 报告说成功了"都不算数——要看 git 里的实际变化。回归测试还有附加要求:必须演示过红绿循环(通过之后,把修复撤掉,测试必须变红,再恢复修复,测试变绿),否则不知道它到底能不能抓住这个 bug。

### 第 5 步:收尾(finishing-a-development-branch)

所有任务完成、终审干净之后,agent 依次做:跑全量测试(红了就不往下走,"绿灯之后才谈集成");确认从哪个分支分出来的(不确定就问,合错基线很难撤);然后给你一个**精确的三选一菜单**——本地合并回主分支、推送并建 PR、分支先留着——菜单怎么定义的就怎么呈现,不许自由发挥。选了本地合并,合并完成后**还要在合并结果上再跑一遍测试**(分支上绿不代表合并后还绿);选了 PR,工作区保留着供你改评审意见。整个过程有一条底线:删除工作永远只在人类明确要求时发生,而且要求人类**逐字输入"discard"**这个词才算确认。

### 支线:并行排查(dispatching-parallel-agents)

修完一个大重构后六个测试文件挂了,而且根因互不相关——这种场景有专门技能。判定树先问"这些失败相关吗"(修一个能好三个的必须一起查),再问"能并行吗"(有共享状态的不行)。然后**在同一条消息里发出多个 subagent 派发**(同消息=并发),每个的指令四件套:范围聚焦(一个文件)、自带上下文(把报错和测试名贴上)、明确约束("不许改生产代码")、指定交付("返回根因和修复摘要")。收尾必须查冲突、跑全量套件、抽查——"agent 会犯系统性错误"。

## 四、全部技能清单与作用

| 技能 | 触发时机 | 一句话说明 |
|---|---|---|
| `using-superpowers` | 每次会话开始由钩子注入 | 宪法:有百分之一可能适用就必须调技能;预写十二种借口的反驳 |
| `brainstorming` | 检测到创造性工作,自动 | 三档分类,一次一问,方案对比,分段设计;硬性门禁:批准前不写码 |
| `using-git-worktrees` | 设计批准后,自动 | 确保隔离工作区,验证测试基线是绿的才开工 |
| `writing-plans` | 规格批准后,自动 | 碎步施工图:每步两到五分钟、代码写全、占位符即失败 |
| `subagent-driven-development` | 用户选了 subagent 驱动 | controller 派全新 implementer 干每个任务,双裁决评审,五轮修复上限,ledger 记进度 |
| `executing-plans` | 无 subagent 环境 | 本会话照计划逐字执行;阻塞即停下问人 |
| `test-driven-development` | 任何实现,自动 | 没看到测试失败不许写码;测试前写的码删掉重来 |
| `systematic-debugging` | 任何 bug,自动 | 四阶段根因调查;三次修复失败=架构问题,停下找人类 |
| `requesting-code-review` | 每任务后、合并前,强制 | 派独立评审 subagent,给精确上下文,不给会话历史 |
| `receiving-code-review` | 收到评审意见,自动 | 先验证再实现;禁止谄媚用语;评审有错就拿证据反驳 |
| `verification-before-completion` | 声称完成前,自动 | 本条消息里没跑过验证命令,就无权宣称通过 |
| `dispatching-parallel-agents` | 多个互不相关的故障 | 每个独立问题域派一个并行 subagent,收尾查冲突跑全量 |
| `finishing-a-development-branch` | 全部完成,自动 | 全量测试、三选一菜单、合并后复测、删工作需逐字确认 |
| `writing-skills` | 创建或修改技能 | 元技能:给"写技能"这件事本身套上 TDD——先看 agent 没技能时怎么失败 |

## 五、技术实现细节

**跨工具的钩子层。** 每个编码工具挂钩子的方式不同,superpowers 为此维护一层薄适配:Claude Code 用 SessionStart 钩子输出标准 JSON,Cursor 用另一套字段,Copilot CLI 又一种;Pi 这种支持扩展的工具则用 TypeScript 扩展监听"会话开始/压缩"事件注入。所有路径殊途同归:把宪法全文塞进上下文。零第三方依赖是硬性设计约束。

**技能的写法本身有规范。** 元信息里的 description 只写"什么时候用"(触发条件和症状),**绝不概括技能的流程**——否则模型读了描述就自以为掌握了,跳过正文。长参考资料拆独立文件,原则和短示例留在正文。这些规范连同上面说的合理化对照表,都写在 `writing-skills` 这个元技能里,它把"写技能"本身做成了 TDD:先跑一个没有该技能的 agent 看它怎么失败、把它当时的借口逐字记下来,再写技能堵住这些具体的借口,然后再测,直到堵干净。

**质量保障管线。** 技能不是散文,是被当作代码管理的:改技能必须走评测(官方的 drill 评测框架驱动真实终端会话,用另一个模型判卷技能是否被遵守),PR 必须披露"这是 agent 生成的还是人写的、用的什么模型和工具"。仓库维护者声明他们的 PR 拒收率是百分之九十四,拒收理由模板写着"这是由谎言组成的 slop"——这套凶悍的流程本身就是他们行为工程理念的自证。

## 六、这套体系的强项与代价

强项:真正的全自动——从"我想加个功能"到"PR 挂好"可以几小时不碰键盘;行为工程扎实,十二种借口式的漏洞是被真实对抗测试逐个堵上的;subagent 流水线的上下文工程(简报文件、报告文件、差异文件、ledger)是整套设计里最可复用的资产;跨工具一致,换编码工具不用换方法论。

代价:流程重,小改动也要过门禁,对于"顺手改一行"的场景显得笨重(它自己给了 bounded 档来缓解,但门禁本身不 waiver);人退出日常循环后,方向性错误要到设计批准点才被拦住,批准点之间的执行全靠评审网兜底;对工具能力有依赖(subagent、钩子),老工具上会退化;技能内容被刻意"锁死",想按自己习惯改流程的人会觉得束手束脚——这恰好是 skills 项目把"可魔改"作为第一原则的原因。

## 七、两个项目的对照结论

两者是同一枚硬币的两面。skills 项目回答"**纪律应该是什么**":拷问式对齐、领域词汇表、seam 上的测试、双轴评审、诊断回路、决策地图——它提供了高质量的"操作剧本",但靠人驱动。superpowers 回答"**怎么让 agent 真的执行纪律**":钩子注入、强制触发、硬性门禁、subagent 隔离、ledger 抗压缩、借口预堵——它提供了可靠的"执行引擎",但剧本相对单一,而且知识资产(词汇表、决策记录、长期工程)不如 skills 丰富。

蒸馏一个新工作流时,最自然的取法是:执行引擎取 superpowers(钩子、门禁、subagent 流水线、ledger、验证纪律),操作剧本与知识资产取 skills(frontier 访谈、CONTEXT.md、seam、双轴评审、诊断六阶段、wayfinder 式的长期工程),再按自己的使用场景决定自动化与人工介入的平衡点。
