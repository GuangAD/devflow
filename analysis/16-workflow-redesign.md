## 二、入口：从分类到判断

分类发生在理解之前等于猜。新入口先把能查的查完，再按顺序判断，判断的结果决定路径与 brief 档位：

1. **看清**：需求、涉及的代码、`CONTEXT.md`、`docs/adr/`、`docs/plans/` 历史；能自己查的事实查完
2. **定路径**：修 bug / 直接做 / 大需求探路 / 几件独立事拆开 / 进入 brief；判据依次是性质、信息完整度、能否向用户复述并获确认
3. **定档位**：进入 brief 后只有一页纸与完整两档；八节、三道门和开发纪律不随档位缩放
4. **整轮访谈**：一轮问完当前 frontier，回答后只回述新增或改变的决定，再重算；不设数量上限，用户可叫停，但结构级未知不能带过门 1
5. **方案对比**：理解要什么之后、写 brief 之前，单独一条消息让用户选定实现路线；只有一个合理方案时不硬凑备选

落点：`dev/references/intake.md` 只负责看清、入口与档位；`grilling/SKILL.md` 是访谈唯一真值；`domain-docs` 由 intake 显式触发，术语就地写，ADR 在门 1 呈报。

「直接做」是入口结果，不是文档档位。修 bug 走 `debugging`，不写需求文档。几件独立的事先拆包，再逐件重新判断，不混进同一份 brief。

## 三、五阶段与三道门

```
阶段 0 接到需求（intake）
阶段 1 写 brief.md            → 门 1
阶段 2 切片，写 plan.md
阶段 3 写 spec.md + tasks/，跑十条自查 → 门 2
阶段 4 逐任务开发（自治，任务间不停顿）
阶段 5 全量测试 + 整特性终审 + 最终报告 → 门 3
```

**门 2 是三道门里最容易被砍掉的一道，也是最不该砍的。** 它的存在理由：切片与契约是判断（切几件、接缝开在哪、用例够不够），不是机械分解；而只发通知不停顿，在流式输出里等于不存在——2026-11-01 实测，agent 在门 1 之后一口气跑到门 3，中间几十个工具调用，用户一次都没看到切片结果。

门 2 的呈报形态：任务清单 + 每个任务的接缝与用例条数 + 覆盖标准档位 + 十条自查结果（逐条，不许写「已检查」）+ 五个问题，其中切片 quiz 明确检查可演示粒度、硬依赖、合并/拆分。**文件在呈报时已写好，用户直接打开看。**

落点：`dev/SKILL.md` 各阶段；`dev/references/self-check.md`「门 1 呈报」「门 2 呈报」；ADR-0005。

## 四、四层文档

按**批准层级**划分，而不是按主题：

| 层 | 文件 | 批准者 | 读者 | 不写什么 |
|---|---|---|---|---|
| 需求 | `brief.md` | 门 1 | 用户 | 签名、路径、表结构 |
| 路径 | `plan.md` | 门 2 | 用户看进度 | 签名、路径、用例 |
| 整体 | `spec.md` | 门 2 | 评审、后来的人 | 任务级签名与文件落点（在契约里） |
| 局部 | `tasks/T<n>.md` | 门 2 | 只会看到这一份的实施者 | 别的任务的内容 |

**判据是机械的**：这条内容被门 1 批过了吗？

`spec.md` 不设篇幅上限，按内容职责控制：整体实现与按需流程图说明特性级数据流，数据结构与模块路径描述整体骨架，覆盖标准（分完整档 / 抽样档，每行要有「落在哪」）与接口面清单（接缝 / 非接缝，非接缝的有状态导出要写重用语义）供任务契约与评审引用。

落点：`dev/references/brief-template.md`、`slice.md`、`tech-spec-template.md`、`task-spec-template.md`；ADR-0005。

## 五、契约的精度

任务契约三节：接口（伪代码）/ 开发步骤 / 测试规格。

**伪代码只写调用形状，不写算法。** 看到 `sort` 可以，看到比较函数内部怎么算就过了——算法细节由测试逼出来，不由计划规定。

理由：写到算法层，契约就成了代码的另一种写法，而它自己会过时。上游 skills 的做法更极端（票里连接口都不写），代价是类型一致性要到实现时才暴露；本仓库选择中间位置：签名与调用形状写死，算法留空。

副作用与错误行为**只在有状态或会失败时写**，但硬规矩是：凡创建对象、持有缓冲、能累积的东西，一律必须写「副作用与重入」——判据不看感觉，看它是不是「新建了东西、或者能越攒越多」。教训：builder 复用未清空缓冲区，几何翻倍，复审才抓到。

## 六、十条自查

八条主检 + 两条排版。主检覆盖：要求有任务承接 / 接口名跨任务一致 / 接口都在清单里 / 覆盖标准每行落地 / 没有自证式期望值 / 比例合理 / **接缝数量与名称对得上 brief** / **每条未定项都有承接**。

最后一条是唯一能抓「需求阶段想漏了东西」的自查，其余六条都在已有内容内部查一致性。干跑时它抓到了实践中的真实漏项（brief 写两个接缝、spec 列了三个）。

落点：`dev/references/self-check.md`。

## 七、开发循环

沿用原有设计，只改规格来源：简报给 `tasks/T<n>.md` 全文 + `spec.md` 相关节，不再从 `spec.md` 摘接口组。

八步：记基线 → 派实现（优先 subagent）/ 会话内做 → 自己重跑验证 → 派评审 → 处置 → 提交 → 记账 → 判下一步。

三条不变：串行不并行、每任务一提交、状态一律落盘。处置不变：Critical 或方案性偏离 → 停；Important 修完继续；Minor 记录。

新增一条检查：`git status` 的改动文件数要对照契约里「涉及」的文件数，多出来就是越界。

落点：`dev/SKILL.md` 阶段 4；`implementer-prompt.md`；`reviewer-prompt.md`。

## 八、实证记录

两次端到端真实运行（空项目、Node 24）：

| 轮次 | 结果 |
|---|---|
| 第一次（门 2 缺失） | agent 在门 1 之后一口气跑完切片、规格、契约、3 个任务、整特性终审，直接到门 3。用户全程只看到两条文本。**门 2 由此恢复** |
| 第二次（门 2 恢复后） | 门 2 正确停下，呈报完整（清单 + 接缝与用例条数 + 覆盖标准档位 + 十条自查逐条 + 三个问题）。十条自查逐条执行。终审抓出真缺陷（`-n -1` 吐三行报错） |

第二次的耗时分布（66 分钟总量）：门 0→门 1 占 20m47s（写 brief 与等审阅），门 2 只占 2m59s（切片 + spec + 两份契约 + 十条自查）。**时间花在需求上，后面就快**——这是继续投入 brief 质量的依据。

同一次运行还验证了 intake 的一条规则有用：它指出 `git shortlog -sn` 已能满足需求，**阻止了一个无意义任务**；并发现 `AGENTS.md` 写死项目定位，塞第二个工具等于改范围——摆出来让用户裁决，没有自己选边。

## 九、静态检查

新增 `devflow/tests/skill-check.sh`，五项：SKILL.md 字节上限、引用的 references 是否存在、旧文件名残留、旧概念残留、frontmatter 完整。

它守的是上游实证过的一条硬约束：**compaction 后每个技能只重挂前 20,000 字符**，超出即永久丢失。某次真实事故里，一个技能丢了「五轮修复上限」，于是一个任务跑了 18 轮修复。

脚本本身也会漂移：门 2 恢复后，第 4 项「旧概念残留」把「门 2」当成废弃词误报了一次。改流程时要同步看脚本。

## 十二、2026-11-03 需求收集再定稿

这次只重划阶段 0 到门 1，门 1 后的流程不动。动因不是增加机制，而是修正 4.0.0 的三处失真：

- **两套访谈范式并置**：intake 同时抄了 skills 的整轮 frontier 与 superpowers 的对话机制，又加了上游明确拒绝的数量上限。现在选边为固定整轮，回述只写本轮变化，数量由依赖关系而不是计数器控制。
- **真值被副本架空**：intake 复制了 grilling 的三分类、提问限制与停止条件，导致 grilling 无人读取，副本已出现措辞漂移。现在 intake 只留指针，提问纪律回到 grilling。
- **知识沉淀静默回退**：3.x 阶段 1 有「访谈全程执行 domain-docs」的显式触发，4.0.0 重写时删掉，但 `analysis/04` 没有登记这项回退。现在恢复指针式触发，门 1 增加「本次沉淀」对账；不把 domain-docs 的纪律再抄进 intake。

入口最终是四种结果加一个前置拆包动作：直接做、一页纸 brief、完整 brief、大需求探路；修 bug 独立走 debugging，几件独立的事先拆开再逐件重判。**四种结果不是四种文档档位，文档只有一页纸与完整两档。**

新增方案对比的理由：brief 第 3 节原本只要求「被否方案各一行」，那是成品字段，不能保证用户真的选过。现在把选择动作放在写 brief 之前，单独一条消息呈报真实备选；没有真实备选时不制造仪式。

回述不设 200-300 字指标。逐轮全文复述会增加阅读负担，最终被用户跳过；只写新增或改变的决定，最后一轮才完整回述共识。

builder check 未纳入本次流程；ADR 七类自检清单仍留在 `17-pending-fixes.md` 待评估，不因本次重划顺带加入。

## 十三、2026-11-03 规格与任务契约扩充

本轮只扩充 `spec.md` 与 `tasks/T<n>.md` 的表达能力，不改变 plan.md 的职责与路径禁令：plan 只切任务、排序、标记出向依赖，不写文件路径。

- **`spec.md` 取消一页半上限**。整体规格需要能描述特性全貌，长度服从内容职责；任务级签名、逐步实现与用例仍归任务契约。
- **整体实现与流程图前置**：spec 先说明特性级数据流，再按需给模块间流程图，随后定义数据结构、模块路径与职责、选型、覆盖标准和接口面清单。流程图只在真实流程复杂时画。
- **任务契约增加实现方式**：每个任务先说明本模块的逻辑处理方式，再按需给流程图；之后列接口与具体文件落点、可选的任务局部数据结构、开发步骤和测试规格。模块级数据结构由 spec 定义，任务不得重定义其形状。
- **门 2 quiz 增加三项切分审查**：每项任务是否能演示、依赖边是否真是硬依赖、任务是否应合并或拆分；连同原覆盖充分性与接口边界问题，共五问。
- **plan 的「挡谁」明确为出向依赖**：列出本任务阻塞的下游任务；无下游依赖显式写「无」。它不表示本任务无前置；是否可立即开始由依赖图判定。


## 十四、2026-11-03 编码与测试执行补强

本轮在现有阶段 4 和覆盖标准中补入三项低重复的执行检查，不增加确认门：

- **T1 前接口预检**：按 Superpowers `subagent-driven-development` 的 preflight 思路，逐项比对任务生产方与消费方的接口名、签名、数据形状及 spec 定义，结果记入 plan 的开发记录。把发现前移到实现开始前，避免到下游任务才暴露契约不一致。
- **命令步骤写 Expected**：参考 Superpowers `writing-plans` / `executing-plans`，任务步骤中的每个运行命令都写预期结果；红测试写明预期失败原因，成功验证说明关键结果与退出状态。implementer 与 controller 都逐条对照实际输出。
- **隐含高风险输入落测试**：借鉴 `writing-plans` 的 Review Focus 检查，把由目标行为、状态变化、边界和失败形态推导出的危险输入映射进现有覆盖矩阵或抽样行，再指到具体任务用例；不另建一份可能漂移的风险清单。
