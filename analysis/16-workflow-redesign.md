## 二、入口：从分类到判断

分类发生在理解之前等于猜。新入口先把能查的查完，再做判断，判断的结果决定产出多长。三个阶段：

1. **先看**（不回复）：需求、涉及的代码、`CONTEXT.md`、`docs/adr/`、`docs/plans/` 历史；能自己查的事实查完
2. **两个判断**：要做事还是有东西坏了 / 我复述得出来吗
3. **分析**：现实允不允许、哪里和代码打架、还有哪几条路、用户可能没想到的一件事
4. **提问**：先过滤（用户的事 / 我的事 / 代码的事），一轮 3-6 个，每题附推荐答案
5. **定大小**：直接做 / 一页纸 / 完整设计 / 大需求

落点：`dev/references/intake.md`。判据与措辞在 `grilling/SKILL.md`。

「直接做」这一档替代了原来的轻流程：它不是入口的输入，而是判断的结果。修 bug 走 `debugging`，不写需求文档。

## 三、五阶段与三道门

```
阶段 0 接到需求（intake）
阶段 1 写 brief.md            → 门 1
阶段 2 切片，写 plan.md
阶段 3 写 spec.md + tasks/，跑十条自查 → 门 2
阶段 4 逐任务开发（自治，任务间不停顿）
阶段 5 全量测试 + 整特性终审 + 最终报告 → 门 3
```

**门 2 是三道门里最容易被砍掉的一道，也是最不该砍的。** 它的存在理由：切片与契约是判断（切几件、接缝开在哪、用例够不够），不是机械分解；而只发通知不停顿，在流式输出里等于不存在——2026-11-01 实测，agent 在门 1 之后一口气跑到门 3，中间几十个工具调用，用户一次都没看到切片结果。

门 2 的呈报形态：任务清单 + 每个任务的接缝与用例条数 + 覆盖标准档位 + 十条自查结果（逐条，不许写「已检查」）+ 三个问题。**文件在呈报时已写好，用户直接打开看。**

落点：`dev/SKILL.md` 各阶段；`dev/references/self-check.md`「门 1 呈报」「门 2 呈报」；ADR-0005。

## 四、四层文档

按**批准层级**划分，而不是按主题：

| 层 | 文件 | 批准者 | 读者 | 不写什么 |
|---|---|---|---|---|
| 需求 | `brief.md` | 门 1 | 用户 | 签名、路径、表结构 |
| 路径 | `plan.md` | 门 2 | 用户看进度 | 签名、路径、用例 |
| 整体 | `spec.md` | 门 2 | 评审、后来的人 | 签名（在契约里） |
| 局部 | `tasks/T<n>.md` | 门 2 | 只会看到这一份的实施者 | 别的任务的内容 |

**判据是机械的**：这条内容被门 1 批过了吗？

`spec.md` 上限一页半，只留两件别处没有的东西：**覆盖标准**（分完整档 / 抽样档，每行要有「落在哪」）与**接口面清单**（接缝 / 非接缝，非接缝的有状态导出要写重用语义）。

落点：`dev/references/brief-template.md`、`slice.md`、`tech-spec-template.md`、`task-spec-template.md`；ADR-0005。

## 五、契约的精度

任务契约三节：接口（伪代码）/ 开发步骤 / 测试规格。

**伪代码只写调用形状，不写算法。** 看到 `sort` 可以，看到比较函数内部怎么算就过了——算法细节由测试逼出来，不由计划规定。

理由：写到算法层，契约就成了代码的另一种写法，而它自己会过时。上游 skills 的做法更极端（票里连接口都不写），代价是类型一致性要到实现时才暴露；本仓库选择中间位置：签名与调用形状写死，算法留空。

副作用与错误行为**只在有状态或会失败时写**，但硬规矩是：凡创建对象、持有缓冲、能累积的东西，一律必须写「副作用与重入」——判据不看感觉，看它是不是「新建了东西、或者能越攒越多」。教训：builder 复用未清空缓冲区，几何翻倍，复审才抓到。

## 六、十条自查

八条主检 + 两条排版。主检覆盖：要求有任务承接 / 接口名跨任务一致 / 接口都在清单里 / 覆盖标准每行落地 / 没有自证式期望值 / 比例合理 / **接缝数量与名称对得上 brief** / **每条未定项都有承接**。

最后一条是唯一能抓「需求阶段想漏了东西」的自查，其余六条都在已有内容内部查一致性。干跑时它抓到了实践中的真实漏项（brief 写两个接缝、spec 列了三个）。

落点：`dev/references/self-check.md`。

## 七、开发循环

沿用原有设计，只改规格来源：简报给 `tasks/T<n>.md` 全文 + `spec.md` 相关节，不再从 `spec.md` 摘接口组。

八步：记基线 → 派实现（优先 subagent）/ 会话内做 → 自己重跑验证 → 派评审 → 处置 → 提交 → 记账 → 判下一步。

三条不变：串行不并行、每任务一提交、状态一律落盘。处置不变：Critical 或方案性偏离 → 停；Important 修完继续；Minor 记录。

新增一条检查：`git status` 的改动文件数要对照契约里「涉及」的文件数，多出来就是越界。

落点：`dev/SKILL.md` 阶段 4；`implementer-prompt.md`；`reviewer-prompt.md`。

## 八、实证记录

两次端到端真实运行（空项目、Node 24）：

| 轮次 | 结果 |
|---|---|
| 第一次（门 2 缺失） | agent 在门 1 之后一口气跑完切片、规格、契约、3 个任务、整特性终审，直接到门 3。用户全程只看到两条文本。**门 2 由此恢复** |
| 第二次（门 2 恢复后） | 门 2 正确停下，呈报完整（清单 + 接缝与用例条数 + 覆盖标准档位 + 十条自查逐条 + 三个问题）。十条自查逐条执行。终审抓出真缺陷（`-n -1` 吐三行报错） |

第二次的耗时分布（66 分钟总量）：门 0→门 1 占 20m47s（写 brief 与等审阅），门 2 只占 2m59s（切片 + spec + 两份契约 + 十条自查）。**时间花在需求上，后面就快**——这是继续投入 brief 质量的依据。

同一次运行还验证了 intake 的一条规则有用：它指出 `git shortlog -sn` 已能满足需求，**阻止了一个无意义任务**；并发现 `AGENTS.md` 写死项目定位，塞第二个工具等于改范围——摆出来让用户裁决，没有自己选边。

## 九、静态检查

新增 `devflow/tests/skill-check.sh`，五项：SKILL.md 字节上限、引用的 references 是否存在、旧文件名残留、旧概念残留、frontmatter 完整。

它守的是上游实证过的一条硬约束：**compaction 后每个技能只重挂前 20,000 字符**，超出即永久丢失。某次真实事故里，一个技能丢了「五轮修复上限」，于是一个任务跑了 18 轮修复。

脚本本身也会漂移：门 2 恢复后，第 4 项「旧概念残留」把「门 2」当成废弃词误报了一次。改流程时要同步看脚本。

## 十一、未验证与遗留

- **并行派发**仍不做（ADR-0002 有效）。上游 `implement-spec` 用 worktree + merger subagent 做了并行，本仓库没有 worktree 隔离，串行是形态决定。要改需先补隔离。
- ~~`dev-map` 文件未删~~ —— 已于 2026-11-01 删除（`skills/dev-map/` 与 `prompts/dev-map.md`）
- **`brief` 在探路期会很长**，未定项单开 `brief-items.md` 的例外通道没有实践过。
- **门 2 的呈报是否够用**只经过两次运行，样本小。
- 原 `SPEC` 的「四件套」被精简后，**副作用与错误行为只在有状态/会失败时写**这条判据依赖执行者的判断，尚未在真实项目上被检验。
