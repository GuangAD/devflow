# 0003 - 上下文读数以只读工具形态进入,不注入消息

日期:2026-09-16 | 状态:已采纳

## 背景

阶段 3 需要在 controller 会话里判断上下文是否已挤到该换会话。但模型无法感知自身的上下文占用——LLM 没有"还剩多少"的内省通道,任何"我感觉上下文有点长了"都是编出来的。pi 也不把用量放进模型可见的上下文:它只在 TUI footer 里给人类看。

devflow 原有的取舍是「命令启动、无自动注入」;`analysis/04` 第二节明确砍掉了 superpowers 的 session hook 家族(宪法注入、压缩重注入)。要为 agent 补上这个环境读数,就必须在那条取舍上开口子。

## 决策

`devflow/extensions/context-meter.ts` 注册一个只读工具 `context_usage`,读 pi 官方接口 `ctx.getContextUsage()`,返回上下文占比。扩展**不挂任何事件钩子、不注入任何消息**。

扩展**只报数,不含任何阈值判断**——占比是否超标、超标后怎么办写在 `dev/SKILL.md` 的「上下文预算」节(≥ 45% 在任务边界提示换会话)。调用时机也由契约规定:阶段 3 第 8 步的机械动作。

## 为什么不用「每步注入一行读数」

注入必须占用消息数组的末位,而 pi 把 prompt cache 的 message 级断点放在「最后一条 user/assistant/tool-result 文本内容」上(`docs/models.md` 的 `cacheControlFormat`)。常驻读数会持续夺走断点,使相邻两轮的共同前缀失配,进而**整段历史无法命中**——省下的那点上下文远抵不上这个损失。工具结果只在被调用时产生,而那些位置本来就会被新内容顶掉。

注:罪魁不是"删除旧读数",而是"占据末位"。删不删只在"注入是否被持久化"时才有区别。

## 为什么不用「越过阈值才注入」

仍然占用断点,只是频率降低;而且阈值逻辑一旦落进扩展,调线就得改代码、重装包。这与本仓库"策略写在契约里"的一贯做法相悖。

## 为什么不用「独立伴生包」

精度问题是同一个环境读数问题,分两个包安装会让"装了 devflow 却不知道有这个读数"成为常态。放进本包才能与契约同版本演进。

代价是 devflow 从「纯技能包」变为「技能 + 命令 + 扩展」——这是对上述取舍的**部分回收**,已在 `analysis/04` 第二节标注。

## 后果

好处:

- agent 拿到了与 TUI footer 同源的实测读数(末条 assistant 的真实 `usage` + 尾随消息估算,`contextWindow` 取当前模型实际窗口,故不写死窗口大小)
- **传感器与策略分离**,消掉了"阈值逻辑散在代码里"这个常见的漂移源;阈值改一行 Markdown 即可调,不必重装包
- 不注入意味着 `analysis/04` 那条「命令启动、无自动接管」的定位**仍然成立**——默认形态(只装 devflow 且不调用工具)零注入
- 派生出一条结构性纪律:扩展**不得挂事件钩子**

代价:

- 扩展是 devflow 第一个非 Markdown 产物,也是唯一不能靠人工核对的产物,必须配回归测试(`context-meter.test.mjs`,含「未注册任何事件钩子」的结构性断言,防止日后改回注入形态)
- 模型必须**主动调用**工具才拿得到读数,不会自动看见;因此调用被写成阶段 3 的一个机械步骤,而不是"想起来才做"
- 契约里多一条降级链:工具 → 三条可数信号 → 每 4 个任务至少检查一次的底线
- `package.json` 需补 `"type": "module"`,否则 Node 会因 `export default` 触发 ESM 重解析
