# 0004 - 术语英文化采用分层策略

日期:2026-09-16 | 状态:已采纳

## 背景

devflow 的正文长期中英混排:`diff`、`commit`、`barrel`、`AFK`/`HITL`、`model 后缀`、`reviewer` 早就是英文,而 `subagent`(子代理)、`seam`(接缝)、`tracer bullet`(曳光弹)这类有业界标准英文名的词仍写中文,造成同一份文档两套词汇——描述一个概念时要在心里做一次翻译,与上游原文对不上,检索也得转换。

## 决策

一次性英文化,范围含 `analysis/` 与根 `README.md`(否则两个术语体系分裂),分三层处理:

1. **正文(A 类)纯替换**为业界标准英文,22 项。自创词首次出现保留一次中文括注:`tracer-bullet(曳光弹)`、`mutation check(反向验证)`。
2. **技能与命令的 `description` 改中英并存**(如 `派 subagent(子代理)独立评审 diff`)。技能层与命令层两层 `description` 都要改。
3. **devflow 自造品牌词(轻/重/巨流程)保留中文**,只在斜杠连写处括注 `light/heavy/huge track` 供检索。

B 类通用译名(上下文、会话、访谈)与 C 类边界词(门、回退协议)保持不动。

## 为什么不用纯英文替换 description

`description` 不是文档,**是路由规则**:agent 决定要不要加载某个技能时,读不到正文,只看 `name` + `description`。所以把"反向验证"换成 `mutation check` 是**行为变更而非文本美化**——用户说"做个反向验证"就不再能触发 tdd。而 `description` 只有一行,是全文最便宜的地方,完全可以容纳同义词。负向触发约束("仅当用户显式调用 /dev 命令…普通开发请求不要自动加载本技能")逐字保留。

## 为什么不用「首现括注」处理全部 22 项

括注在中文句法里频繁嵌套(全角括号本就是现有风格的高频符号),会产出 `判轻(走轻流程(light track))信号` 这类嵌套,正文可读性反而下降。只有来源明确的自创词值得保留一次括注。

## 为什么不用全保留中文

代价已经显现(见背景),而且 devflow 是从两个英文上游蒸馏来的,保留中文会让与上游的对照永远需要一次转换。

## 后果

好处:

- 正文与上游原文对齐;`devflow/README.md` 新增术语表(中英对照)承担检索键职责,与根目录 `CONTEXT.md` 的语义定义分工
- 借这次替换统一了一处历史混用:「纵向切片」与「垂直切片」原是同指 `vertical slice` 的两个中文词,现统一
- 常驻层(`description`)顺带成了术语表——两种说法都在,不会因为改名让某条触发路径失效

代价:

- 25 个文件一次性改动,**改 `description` 等于改触发行为**,回退成本高
- 批量替换需要**两遍复查**:一遍查旧术语残留,一遍查新术语粘连(英-英相邻时没有 CJK↔Latin 空格规则兜底)。本次两次事故都出在这里,根因是含中文标点的正则里用了 `\s`(会吃掉换行),以及替换规则表未按长度降序排列导致长模式被短模式先吃掉
