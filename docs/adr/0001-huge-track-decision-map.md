# 0001 - 巨流程用无 tracker 的决策地图承载

日期:2026-09-16 | 状态:已采纳

## 背景

门 1 的自查红线是"seam 条目缺四件套之一、或穷举清单不完整,视同开放问题非空,不得呈报门 1"。而巨大需求(如"把单租户改成多租户")的本质恰恰是开放问题短期清不空——不是执行者偷懒,是它本来就装不进一次访谈。于是流程只有两条路:卡在门 1 前无限访谈,或在还有含糊时被迫过门;而后者正是 devflow 最想防的事。

上游 mattpocock/skills 的 `wayfinder` 正是为此而生:在 tracker 上建一棵"决策地图"、逐票解题。但它的形态强依赖 issue tracker。

## 决策

采纳它的**认知模型**,改造成无 tracker 的形态,作为第三层「巨流程」:

- 地图 = 单个文件 `docs/maps/<YYYY-MM-DD>-<slug>/map.md`,五节(destination / 备注 / 已定决策 / fog / out of scope),进 git
- ticket 一行一张,状态用 checkbox,解完回填 commit 哈希——与 plan.md 同一套记账法
- 分类器由二分扩为三分。判巨两条:**一次访谈装不下**、**有"还说不 sharp"的区域**;且判巨优先于判重
- 出口接回 `/dev` 门 1,不接 to-spec:地图产决策,design.md 从「已定决策」直接生成,访谈只补门 1 自查发现的具体空白

## 为什么不用 wayfinder 原版形态

它把地图做成一棵 issue、票做成子 issue、阻塞用 tracker 原生的依赖关系、并发靠 assignee 认领。devflow 完全没有 tracker 概念,状态一律落盘在 git 里——引入 tracker 等于把一个外部系统写进流程契约,并把"装 devflow"变成"先配 tracker"。

## 为什么不用「一律先访谈,谈不完就分批」

那正是 devflow 原有的状态,而它是失效的:开放问题装不满就过不去门 1;分批谈又没有任何地方记着"这次不做什么",跨会话的范围会持续蔓延。

## 为什么不用「把地图并进 design.md 的开放问题节」

两者语义不同。开放问题是"已知但还没定",fog 是"知道那儿有东西、但连问题都还说不出"。混在一节会让巨大需求把该节塞满不可判定的东西,而门 1 只看该节空不空,于是永远过不去。

## 后果

好处:

- 补上了 devflow 的结构性死角:巨大需求不再必然卡在门 1 前
- **fog 与 ticket 的判据**(能不能把问题说精确,**不是**能不能回答)是这条线里最锋利的一条,它拦住了把雾预切成票的冲动
- destination 与 out of scope 提供了**跨会话的范围边界**——这是重流程的"目标与非目标"给不了的,后者只在单个特性内有效
- 地图留在 `docs/maps/` 不删:destination 与 out of scope 的取舍是"当时为什么这么定"的第一手证据

代价:

- **认领机制降级**。没有 tracker 的 assignee,只能靠"每会话最多解一张 ticket + 解完即提交"防并发会话撞车,这比 assignee 弱
- 判巨的两条信号目前是描述性的、没有量化门槛,存在把"重"误判成"巨"、让地图层变成人人都要先交的一份作业的风险。已登记为 ROADMAP 观察点
- 分类器从二分变三分,`dev/SKILL.md` 与 `analysis/03` 的对应章节都变长
