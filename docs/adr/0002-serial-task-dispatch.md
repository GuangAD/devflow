# 0002 - 实现任务串行派发,不并行放飞多位 implementer

日期:2026-09-16 | 状态:已采纳

## 背景

阶段 3 把实现派给 subagent,是为了隔离工作记忆——状态与代码早已落盘,但 TDD 的红绿输出、验证的全量输出、评审处置过程、调试走过的弯路没有归宿,它们让 controller 的上下文随任务数单调增长。

一旦存在多个 implementer,自然的问题是能否并行:把 ready set 里互不依赖的任务同时派出去,总时长按并行度缩短。

## 决策

**串行**。每次准备做下一个任务前先重算 ready set,从中取**一个**派发;等它回报、controller 自己重跑验证、派 reviewer 评审、处置发现、提交、勾选,再重算 ready set 取下一个。

`plan.md` 的「依赖」字段用于**决定顺序**,不要求穷举隐性耦合;派发时把上游已完成任务的接口签名与开发记录里的相关结论贴进 implementer 简报的「上游已完成」节。

## 为什么不用并行放飞多位 implementer

三条形态约束各自独立地排除了它,没有一条是本次新引入的——它们早就把并行排除了,只是以前只有一个会话在干活,并行从来不是选项:

1. **任务是 tracer-bullet vertical slice**,天然贯穿各层;两个"互不依赖"的任务完全可能落在同一个注册文件、类型导出 barrel 或路由表上。
2. **devflow 明确舍弃了 worktree 隔离**(`analysis/04` 第二节)。没有隔离就没有并行的安全前提——两位 implementer 在同一工作区同时改动,冲突由谁解?
3. **「每任务一 commit」的线性历史是回退协议的前提**。并发提交会把它拆成需要 merge 的分叉,"爆炸半径可计算"随之失效。

## 为什么不用「只并行派发互不相关的模块」

因为"互不相关"在纵向切片下无法在计划期判定——任务形状是纵向的,横向的模块边界不是任务的边界。判定它需要穷举耦合,而那正是第 3 条约束已经否掉的事。

## 后果

好处:

- **串行本身就是最强的依赖保障**:上游提交后代码已真实存在于工作区,下游 implementer 读代码即可获得接口,隐性依赖不必声明也能被满足。「依赖」字段的职责因此从"保证下游能做"降级为"决定顺序"
- 回退协议与逐任务 revert 得以成立:线性历史使爆炸半径可计算
- 不引入 worktree 隔离,与 `analysis/04` 已有的取舍一致,不产生新的基建

代价:

- 放弃并行的时间收益,阶段 3 的时长线性于任务数
- 依赖信息必须由 controller 显式搬运(接口签名 + 上游结论),否则下游 subagent 只能靠猜;这使 implementer 简报的质量成为流程的软肋,已登记为 ROADMAP 观察点

边界:`dev-map` 的**调研 ticket 可以并行**。判据是**会不会写工作区**——调研 subagent 只读不改,不产生 commit、不碰工作区,三条约束一条都不适用。一旦进入 `/dev` 阶段 3,每个 subagent 都会产出代码和提交,并行窗口就此关闭。
