# 0006 - 决策地图并入 dev

日期:2026-11-01 | 状态:已采纳

## 背景

ADR-0001 在 2026-09 引入了独立的 `/dev-map` 命令与 `docs/maps/<日期>-<slug>/map.md`,用来装「巨大且模糊」的需求:一张地图五节(destination / 备注 / 已定决策 / fog / out of scope),一次会话解一张 ticket,只产决策不产代码。

它解决的问题是真的:门 1 要求开放问题清空,而巨大需求的开放问题短期清不空。但它引入了第二套记账法(ticket 与 task)、第二份文档(map 与 brief)、以及一次「地图走完再把已定决策汇总进设计文档」的翻译。

同时它的判据一直不好用:「一次访谈装不下」「存在说不 sharp 的区域」,这两条要求人在开工前判断访谈规模——而这恰恰要先试访谈才知道。ROADMAP 里登记过「存在把重误判成巨、让地图层变成必交作业」的风险。

## 决策

**删掉独立命令与 map.md,把探路并入 `dev`。**

- 大需求的分流点从「分类」移到 `intake` 的第二个判断:**我复述得出来吗**
- 探路的产物就是 `brief.md` 的草稿:终点写进「目标与非目标」,已定的事写进「选定方案」与「关键决策」,还说不精确的留在第 6 节「未定项」里
- 纪律保留、载体更换:一次只解一件、只产决定不产代码、看不清的别提前切碎
- 删除 `skills/dev-map/` 与 `prompts/dev-map.md`

## 为什么不用「保留 dev-map 作为独立第三层」

它带来的两份文档、两套记账法、一次翻译,换来的独占价值只有两条:AFK 调研可并行派发、中断恢复的记账单位更细。为一个自己都承认判不准的判据付这些代价,不划算。

更根本的问题是:**map 走完必须「翻译」成设计文档**,而翻译这一步必然损耗。brief 是同一份文件从草稿长到定稿,不存在翻译。

## 为什么不用「迁到 issue tracker」(上游 wayfinder 的做法)

上游 2026-10 把地图从 markdown 搬到了 tracker:地图是带 label 的 issue、票是子 issue、阻塞用 tracker 原生依赖、认领用 assignee。

这条路对 devflow 不成立:本仓库完全没有 tracker 概念,状态一律落盘在 git 里。引入 tracker 等于把外部系统写进流程契约,并把「装 devflow」变成「先配 tracker」。ADR-0001 拒绝过一次,这次结论不变。

## 后果

好处:

- 少一个命令、少一份文档、少一次翻译
- 判据从「访谈装不装得下」换成「能不能复述」——后者可以用两三句话试一下,不用预判访谈规模
- 探路与正常需求的产物是同一份文件,前者只是后者的草稿态

代价:

- `brief` 在探路期会很长(未定项表可能几十行)。缓解:真的长到不可读时,可以把未定项单开一份 `brief-items.md` 并在 brief 里引用——这是例外通道,不是常设结构
- 「一次只解一件」失去独立载体,只写在 `intake.md` 的大需求节里。这削弱了它的执行力:原来是一个技能的核心纪律,现在是一段说明
- 原地图的「destination 定死范围」在 brief 里变成「目标与非目标」,语义略弱——目标与非目标原本是给单个特性用的,而 destination 承担的是跨会话的范围边界

## 取代

取代 [0001](0001-huge-track-decision-map.md)。0001 中关于「fog 与 ticket 的判据是能不能说精确,不是能不能回答」这一条仍然有效,已写进 `intake.md` 的大需求节。
