# 0005 - 文档按批准层级划分,门 2 恢复

日期:2026-11-01 | 状态:已采纳

## 背景

原来的产物是 design.md(决策快照,冻结)+ spec.md(实现规格,演进)+ plan.md(任务与进度),三份按**主题**划分。这套划分带来三个真实病症:

1. **同一事实活在两处**。模块鸟瞰在 design、接口清单在 spec,两者必须一致,于是检查清单里专门有一条「架构图与文字鸟瞰一致」——靠检查项修补设计缺陷。
2. **边界不可判**。「数据结构定义该放 design 还是 spec」始终说不清,争议只能靠回退协议裁决。
3. **形态漂移**。spec.md 在门 1 呈报「骨架」、在门 2 呈报「用例详版」,同一份文件被批准两次、每次批的是不同形态。

同一时期还砍掉了门 2,理由是「它只是把已批准的决定拆成步骤,没有新的方向性判断」。2026-11-01 的端到端实测否掉了这个判断:agent 在门 1 之后一口气跑完切片、规格、契约、三个任务和整特性终审,直接停在门 3。中间几十个工具调用把切片结果彻底淹没,用户一次都没看到「切了几件、每件测什么」。

## 决策

**按批准层级划分文档**,而不是按主题:

| 层 | 文件 | 批准者 | 批准后的修改权 |
|---|---|---|---|
| 需求 | `brief.md` | 门 1 | 冻结,只能走回退 |
| 路径 | `plan.md` + `spec.md` + `tasks/T<n>.md` | 门 2 | 可改,每次登记到 plan 的开发记录 |
| 执行 | plan 的任务勾选与开发记录 | 无需批准 | agent 自治 |

「这条内容属于哪份文件」的判据变成机械的:**它被门 1 批过了吗?**

同时**恢复门 2**,呈报形态是「任务清单 + 每个任务的接缝与用例条数 + 覆盖标准档位 + 九条自查结果 + 三个问题」,文件在呈报时已写好在磁盘上,用户直接打开看。批准后立即提交这三层。

## 为什么不用三份(brief / contract / plan)

这是讨论中的中间方案。它仍有同步义务:接口与用例在 contract,验收标准在 plan,两边写的是同一件事的两面。四层方案把接口、用例、验收一起放进任务契约,同一事实只有一处。

## 为什么不用两份(design doc + plan,上游 superpowers 的形态)

上游只有一个设计文档加一份计划,接口写在计划每个任务的 Interfaces 块里。它跑得通,但放弃了本仓库实证有效的两件重装备:

- **覆盖标准**。`design-checklist` 里记着两条真实教训:环回断言曾只锁 11 个字段中的 5 个;builder 复用未清空缓冲区导致几何翻倍。这两类漏都靠「等价类矩阵 + 维度两两交叉」抓到,上游的「五条最可能咬人的输入」抽样盖不住。
- **接口面清单**。门 3 终审曾靠它抓出 self-review 漏登的 19 个类型导出。

所以保留这两节,放在 `spec.md` 里,但把它的体积压到一页半。

## 为什么不用节级冻结(一份文件内用节标记冻结与演进)

节级冻结没人会遵守。文件边界是可机械执行、可 git 追踪、可提交的边界;节边界只能靠自觉。三份文件分工混乱的教训已经证明,靠自觉的边界等于没有边界。

## 后果

好处:

- 边界机械可判,不再有「这算设计还是接口」的争论
- 没有形态漂移:`spec` 从诞生就是契约形态,`brief` 从诞生就是需求形态
- 门 2 让「切几件、每件测什么」在开发前可见,而这是判断不是机械分解
- 四份文件各有唯一读者:brief 给用户、plan 给用户看进度、spec 给评审看整体、任务契约给实施者

代价:

- 文件数从 3 增到 3 + N(每任务一份)
- 四层之间有同步义务,靠「任何一层改动都在 plan 的开发记录登记一行」兜住
- 门 2 增加一次停顿。这是刻意的:实测表明不停顿等于不通知
- 判据从「哪个文件被改」细化到「哪一节被改」——节级判据只在**回退协议**里还用到,日常靠登记制度兜

## 后续

`tasks/` 是否按任务分文件,取决于是否派发 implementer。全程会话内实现时可以合并成一份 `tasks.md`。
