# 任务契约模板

`tasks/T<n>.md`，一个任务一个文件。读者是**只会看到这一份的那个实施者**——派出去的子代理只拿到自己的契约和 `spec.md`，看不到别的任务。

## 骨架

```markdown
# T3 <名称>

> 依赖:T2 | 对应:brief 第 2 节、spec 的覆盖标准

## 实现方式

## 流程图(可选)

## 接口(伪代码)

## 数据结构(可选)

## 开发步骤

## 测试规格
```

## 第 1 节：实现方式

一段叙述：本模块的工作逻辑与处理方式——数据怎么进怎么出、状态怎么流转、关键分支怎么取舍。对应 `spec.md` 的「整体实现」，但只写本任务这一块，不复述整体。

## 第 2 节：流程图(可选)

mermaid。任务内有复杂分支或状态流转时画；直白流程不画，不画装饰图。图不复述「实现方式」的文字。

## 第 3 节：接口(伪代码)

节头部一行写文件落点：

```markdown
落点:`搜索/rank.ts`
```

然后写三样：数据结构、签名、调用形状。

```markdown
## 接口(伪代码)

落点:`搜索/rank.ts`

type RankedHit = { postId: PostId; score: number }

rank(index: SearchIndex, tokens: string[], limit: number): RankedHit[]
  // 调用形状:
  //   for token in tokens: hits = index.lookup(token)
  //   for hit in hits: score += 权重(命中位置)
  //   sort desc by score
  //   take(limit)
  // 纯函数,不改状态,不会失败
```

**伪代码只写调用形状，不写算法。** 看到 `sort` 可以，看到比较函数内部怎么算就过了。算法细节由测试逼出来，不由计划规定。

### 两行只在该写的时候写

- **副作用与重入**：这个函数改状态吗？同一个对象调两次是清空还是累加？
- **错误行为**：非法输入是抛错、夹紧，还是未定义？

**只在有状态或会失败时写。** 纯函数写一句「纯函数，不改状态，不会失败」即可。

硬规矩：**凡创建对象、持有缓冲、能累积的东西，一律必须写「副作用与重入」。** 判据不看感觉，看它是不是「新建了东西、或者能越攒越多」。

教训：builder 复用未清空缓冲区，几何翻倍，复审才抓到。

## 第 4 节：数据结构(可选)

本任务新增或修改的结构、表设计。与 `spec.md`「数据结构」节重复的部分只引用：「定义见 spec.md 数据结构节」，**不许在任务里改变它的形状**——要改形状就是 spec 要改。

## 第 5 节：开发步骤

每一步一个动作，结果可检查，可带文件落点。凡运行命令的步骤，写明命令和 `Expected:`；失败测试写预期失败原因，成功验证写关键结果与退出状态。

```markdown
## 开发步骤

1. 写测试:标题命中排第一(期望来源:手算)
2. 运行：`<指定单测命令>`；Expected: FAIL（exit 1），原因是 `rank` 尚未实现
3. 写最小实现(落点:`搜索/rank.ts`)
4. 运行：`<指定单测命令>`；Expected: PASS（exit 0），目标用例通过
5. 写测试:两篇都含时,出现次数多的在前(期望来源:手算)
6. 运行：`<指定单测命令>`；Expected: FAIL（exit 1），原因是出现次数排序尚未实现
7. 写最小实现(落点:`搜索/rank.ts`)
8. 运行：`<指定单测命令>`；Expected: PASS（exit 0），目标用例通过
9. 写测试:结果多于 limit 时只返回 limit 条(期望来源:brief 第 2 节)
10. 运行：`<指定单测命令>`；Expected: FAIL（exit 1），原因是 limit 尚未应用
11. 写最小实现(落点:`搜索/rank.ts`)
12. 运行：`<指定单测命令>`；Expected: PASS（exit 0），目标用例通过
```

**「写测试并跑绿」是三件事，要拆成三个步骤。** 步骤的定义：实施者能从中写出唯一一件确定的事。

有的地方不需要写实现细节——签名和测试已经确定了唯一的写法，就不必规定。只在签名与测试都留了选择的地方给一行提示（用哪个库调用、用哪种数据结构）。

## 第 6 节：测试规格

按接缝分组。一个任务只有一个接缝时，可以省掉小标题。

```markdown
## 测试规格

### 接缝 rank

| # | 输入 | 期望 | 期望值来源 |
|---|---|---|---|
| 1 | 标题含关键词、正文不含 | 排第一 | 手算 |
| 2 | 两篇都含,一篇 3 次一篇 1 次 | 3 次的在前 | 手算 |
| 3 | 结果 25 条,limit 20 | 返回 20 条 | brief 第 2 节 |
| 4 | 空查询词 | 返回空数组,不报错 | 约定 |
```

**期望值来源必须是独立的事实**：手算字面量、外部参照、brief 里写死的值、构造的反例。

**不许写「按实现算」「参考代码」** —— 那是自证，测试和实现一套逻辑，永远测不出错。

**为什么要按接缝分组**：评审要能一眼看出「这个接缝测到了什么」。混成一张表，得靠读输入去猜哪一行属于哪个接缝。

## 接缝的归属规矩

- **一条接缝的用例，只在实现它的那个任务里写全。** 别的任务用它就复用，不重写
- 后续任务发现新边界 → 补到原任务文件里，并在 `plan.md` 开发记录登记一行
- 契约里没写、实现时发现必须新开接缝 → **停手报告**。那不是实现问题，是契约漏了
- 契约里写了「这条是新开接缝」→ 正常做，并在开发记录记一行「新增接缝 X」

## 硬规矩

- 实现方式必写；流程图按需
- 接口节头部必写文件落点
- 伪代码只写调用形状，不写算法
- 每步一个动作，结果可检查
- 期望值来源不许是「按实现算」
- 本节出现的每个接口，都必须在 `spec.md` 的接口面清单里
- 接口名与相邻任务对齐（这里叫 `rank`，隔壁就不能叫 `rankResults`）
- 用例表的 `#` 列供 `spec.md` 覆盖标准引用。改编号要同步改 spec
- 重复声明的类型必须紧跟一句「定义见 `spec.md` 数据结构节」，**不许在任务里改变它的形状**——要改形状就是 spec 要改
