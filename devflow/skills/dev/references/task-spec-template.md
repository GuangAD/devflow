# 任务契约模板

`tasks/T<n>.md`，一个任务一个文件。读者是**只会看到这一份的那个实施者**——派出去的子代理只拿到自己的契约和 `spec.md`，看不到别的任务。

## 骨架

```markdown
# T3 <名称>

> 依赖:T2 | 对应:brief 第 2 节、spec 的覆盖标准

## 实现方式

## 流程图(可选)

## 接口(伪代码)

## 数据结构(可选)

## 开发步骤

## 测试规格
```

## 第 1 节：实现方式

固定四行，不许写成一段：

- **干什么**：一句话，这个模块解决什么问题
- **输入**：数据从哪来、谁调用它
- **处理**：逻辑顺序用编号列表，一步一行；有状态的在这里说清增、删、清空
- **失败与退出**：什么情况下失败、失败后谁兜底

```markdown
## 实现方式

**干什么**：管 PTY 全生命周期——创建、转发、写入、改尺寸、单杀与全量清理。

**输入**：`AgentDefinition`（定义表）、项目目录、渲染层的按键与尺寸。

**处理**
1. spawn：按定义构造命令，cwd 落项目目录，登记进内表
2. 字节流：单会话独占一条流，经 `pty:data` 推渲染层
3. kill：杀进程并删条目，exit 事件照常发出
4. killAll：应用退出时全量清空，不留孤儿

**失败与退出**：spawn 失败直接抛出，由 IPC 域转成错误响应；采样开关未开启时旁路，不产生副作用。
```

这一段是实施者读到的第一节，决定他理解得对不对。写成一段话最典型的后果是：读完仍说不出「这个模块管到哪、不管到哪」。实测同一特性里五个任务的「实现方式」都在 488-876 字节之间，全部是单段。排版规则见 `self-check.md` 第 9 条。

## 第 2 节：流程图(可选)

mermaid。任务内有复杂分支或状态流转时画；直白流程不画，不画装饰图。图不复述「实现方式」的文字。

## 第 3 节：接口(伪代码)

节头部一行写文件落点：

```markdown
落点:`搜索/rank.ts`
```

然后写三样：数据结构、签名、三行问句注释。

**每个签名下面按固定顺序写，能写才写，没有的行省掉：**

| 行 | 必写 | 写什么 |
|---|---|---|
| `// 用途：` | 是 | 一句话：这东西解决什么问题、为什么存在 |
| `// 怎么用：` | 视情况 | 调用方必须知道的顺序、前置条件、并发注意 |
| `// 出错时：` | 有状态或会失败时 | 失败怎么表现、谁兜底、会不会改状态 |

规矩：

- **注释写成句子，不许只写字段名。** `// 副作用与重入：…` 可以作补充行保留，但不能是唯一内容——读者不该为了看懂注释先去读本模板。
- **「怎么用」只写调用方视角**：必须满足的顺序（`先 load 再 save`）、能否重复调用、并发是否安全。逐步实现属于「开发步骤」与「测试规格」，不写进注释。
- **凡创建对象、持有缓冲、能累积的东西，一律必须写清它与重入的关系**（写进「怎么用」或「出错时」）。判据不看感觉，看它是不是「新建了东西、或者能越攒越多」。

落点：`src/main/store/persistence.ts`

```ts
type AppStore = { projects: Project[]; sessions: Session[]; settings: Settings }

loadStore(file: string): Promise<AppStore>
  // 用途：启动时把 store 文件读进内存，文件坏了也不能让应用起不来
  // 怎么用：直接 await，不要在外面再包 try/catch；返回的永远是可用对象
  // 出错时：任何解析失败都不抛，改用 DEFAULT_STORE，并把原文件改名 <file>.corrupt-<ts> 留存

saveStoreAtomic(file: string, store: AppStore): Promise<void>
  // 用途：把内存里的 store 整体落盘
  // 怎么用：每次调用整体覆盖，不累积；与 loadStore 之间没有顺序约束
  // 出错时：先写 <file>.tmp 再 rename；失败时临时文件残留可忽略；不修改传入对象

rank(index: SearchIndex, tokens: string[], limit: number): RankedHit[]
  // 用途：给命中的文章打分排序，决定结果顺序
  // 怎么用：可重复调用，不写 index，并发安全；limit 小于 0 按 0 处理
  // 纯函数，不改状态，不会失败
```

**伪代码只写调用形状，不写算法。** 看到 `sort` 可以，看到比较函数内部怎么算就过了。算法细节由测试逼出来，不由计划规定。

教训：builder 复用未清空缓冲区，几何翻倍，复审才抓到——这类状态累积只要漏一行注释，读契约的人就判断不出来。

## 第 4 节：数据结构(可选)

本任务新增或修改的结构、表设计。与 `spec.md`「数据结构」节重复的部分只引用：「定义见 spec.md 数据结构节」，**不许在任务里改变它的形状**——要改形状就是 spec 要改。

## 第 5 节：开发步骤

每一步一个动作，结果可检查，可带文件落点。凡运行命令的步骤，写明命令和 `Expected:`；失败测试写预期失败原因，成功验证写关键结果与退出状态。**`Expected:` 必须写本步骤实际跑测条数**（如 pytest 的 `1 passed` / `1 failed`、unittest 的 `Ran 1 test`）；过滤或指定用例的命令不得只写 exit 0——测试运行器报告 0 条时也可能输出 OK 且退出 0，那是未验证，不是通过。

**命令粒度**：红绿循环中跑目标用例（如 `pytest tests/test_csvio.py::test_invalid_age` 或 `-k` 过滤）；任务收尾跑相关模块（如 `pytest tests/test_csvio.py`）；不要在每步都跑全量 `discover`。全量测试由 controller 在任务完成时统一执行。指定用例 / `-k` 命令必须核对测试运行器报告的用例数；0 条视为未验证，不算绿。

```markdown
## 开发步骤

1. 写测试:标题命中排第一(期望来源:手算)
2. 运行：`pytest tests/test_rank.py::test_title_hit -v`；Expected: FAIL（exit 1），`1 failed`，红因是 `rank` 尚未实现
3. 写最小实现(落点:`搜索/rank.ts`)
4. 运行：`pytest tests/test_rank.py::test_title_hit -v`；Expected: PASS（exit 0），`1 passed`，且不是 `0 passed`
5. 写测试:两篇都含时,出现次数多的在前(期望来源:手算)
6. 运行：`pytest tests/test_rank.py::test_count_sort -v`；Expected: FAIL（exit 1），`1 failed`，红因是出现次数排序尚未实现
7. 写最小实现(落点:`搜索/rank.ts`)
8. 运行：`pytest tests/test_rank.py::test_count_sort -v`；Expected: PASS（exit 0），`1 passed`，且不是 `0 passed`
9. 写测试:结果多于 limit 时只返回 limit 条(期望来源:brief 第 2 节)
10. 运行：`pytest tests/test_rank.py::test_limit -v`；Expected: FAIL（exit 1），`1 failed`，红因是 limit 尚未应用
11. 写最小实现(落点:`搜索/rank.ts`)
12. 运行：`pytest tests/test_rank.py::test_limit -v`；Expected: PASS（exit 0），`1 passed`，且不是 `0 passed`
```

**「写测试并跑绿」是三件事，要拆成三个步骤。** 步骤的定义：实施者能从中写出唯一一件确定的事。

有的地方不需要写实现细节——签名和测试已经确定了唯一的写法，就不必规定。只在签名与测试都留了选择的地方给一行提示（用哪个库调用、用哪种数据结构）。

## 第 6 节：测试规格

按接缝分组。一个任务只有一个接缝时，可以省掉小标题。

每组头部写一句职责说明，标明这是模块行为还是特性流程：

```markdown
### 接缝 csvio.parse_csv（模块行为）
穷举输入组合与边界，不经过 HTTP 层。

### 接缝 POST /preview（页面接线）
只验证错误显示与确认按钮状态，不重复解析规则。
```

**职责划分的判据**：模块行为（输入组合、字段校验、边界）主测在函数级接缝；跨模块流程（状态变化、用户路径、round-trip）主测在 HTTP 接缝。同一行为在多个接缝出现时，第二层必须验证的是接线、状态或用户结果，而不是把同一规则重新测一遍。

```markdown
## 测试规格

### 接缝 rank（模块行为）
穷举排序输入组合与边界，不经过 HTTP 层。
| # | 输入 | 期望 | 期望值来源 |
|---|---|---|---|
| 1 | 标题含关键词、正文不含 | 排第一 | 手算 |
| 2 | 两篇都含,一篇 3 次一篇 1 次 | 3 次的在前 | 手算 |
| 3 | 结果 25 条,limit 20 | 返回 20 条 | brief 第 2 节 |
| 4 | 空查询词 | 返回空数组,不报错 | 约定 |
```

**期望值来源必须是独立的事实**：手算字面量、外部参照、brief 里写死的值、构造的反例。

**不许写「按实现算」「参考代码」** —— 那是自证，测试和实现一套逻辑，永远测不出错。

**为什么要按接缝分组**：评审要能一眼看出「这个接缝测到了什么」。混成一张表，得靠读输入去猜哪一行属于哪个接缝。

## 接缝的归属规矩

- **一条接缝的用例，只在实现它的那个任务里写全。** 别的任务用它就复用，不重写
- 后续任务发现新边界 → 补到原任务文件里，并在 `plan.md` 开发记录登记一行
- 契约里没写、实现时发现必须新开接缝 → **停手报告**。那不是实现问题，是契约漏了
- 契约里写了「这条是新开接缝」→ 正常做，并在开发记录记一行「新增接缝 X」

## 硬规矩

- 实现方式必写；流程图按需
- 接口节头部必写文件落点
- 伪代码只写调用形状，不写算法
- 每个签名必须有「用途」行,且注释写成句子——只写 `调用形状` / `副作用与重入` 这类字段名不算
- 排版按 `self-check.md` 第 9 条:叙述段 ≤3 句、单句 ≤60 字,「实现方式」落成固定四行
- 每步一个动作，结果可检查
- 期望值来源不许是「按实现算」
- 本节出现的每个接口，都必须在 `spec.md` 的接口面清单里
- 接口名与相邻任务对齐（这里叫 `rank`，隔壁就不能叫 `rankResults`）
- 用例表的 `#` 列供 `spec.md` 覆盖标准引用。改编号要同步改 spec
- 重复声明的类型必须紧跟一句「定义见 `spec.md` 数据结构节」，**不许在任务里改变它的形状**——要改形状就是 spec 要改
