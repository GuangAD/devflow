# intake — 接到需求

dev 阶段 0 的全部动作。产出是下一阶段要写的 `brief.md` 的内容素材,以及一个明确的大小判断。

## 第一件事:先看,不回复

用户给的可能是**一句话**,也可能是**一份需求文档**。两种都要先把下面四类读完,再开口:

- 需求本身(一句话就一句话,文档就全文)
- 它涉及的代码,读到能说清「这块现在怎么跑、这次会碰到什么」
- 项目已有约定:`CONTEXT.md` 的用词、`docs/adr/` 里相关的决策、既有命名与目录习惯
- `docs/plans/` 下有没有做过的类似特性

同时把**自己能查的事实查完**:某个库支不支持、项目里有没有现成实现、惯例是什么。查不完的只挡住依赖它的问题,不挡住整轮提问。

永远不要问项目或用户给的上下文已经回答过的问题。

## 第二件事:两个判断

### 判断 A:要做事,还是有东西坏了

| 是 | 走 |
|---|---|
| 有新东西要建、现有行为要改 | 本流程继续往下 |
| 有东西坏了(报错、结果不对、卡住) | 读 `debugging` 技能,走复现—根因—回归测试,不走本流程 |

修 bug 不走需求流程,它的问题不是「你要什么」,而是「它在哪坏了」。只有当修复暴露设计级改动时才升级到本流程。

### 判断 B:我复述得出来吗

试着用两三句话说出用户要什么。判据很硬:

| 结果 | 走 |
|---|---|
| 复述得出来 | 继续 |
| 复述不出来,但用户说得出一堆想做的事 | 大需求:先定「走到哪算完」,把能看清的列成单子,一次解一件 |
| 其实是几件独立的事捆在一起 | 停,说「这是三件事」,排个序,一次聊一件 |

**大需求那条路的纪律**:只产决定,不产代码;一次只解一件,从最好解的开始;解完写下来,再看原来的模糊处是否变清晰;看不清的别提前切碎。全部清晰后才回到本流程,已定的事直接作为既有共识,不再重谈。

## 第三件事:分析

四件,做完才有资格提问:

- **现实允不允许**:要碰哪些文件、有什么限制、代价大概多大
- **哪里打架**:需求说的和代码现在做的对不上。对不上的事**摆给用户裁决**,不自己选边
- **还有哪几条路**:至少两条真实备选,各自代价是什么
- **用户可能没想到的一件事**:一个约束、一个冲突、一条更便宜的路。只说一条真会改变做法的,不做泛泛评论

## 第四件事:提问

### 先过滤,只问该问的

| 类别 | 例子 | 处置 |
|---|---|---|
| **用户的事** | 搜不到时显示什么、要不要支持错别字容错、先做哪个 | 必须问 |
| **我的事** | 函数叫什么、放哪个目录、用哪个库、内部怎么拆 | 自己定,在 `brief` 第 5 节标 `[我]` |
| **代码的事** | 现在怎么跑的、有没有现成的、项目定过什么规矩 | 自己查,不许问 |

一轮里如果后两类占了多数,说明分析阶段没做完,回去补。

### 一轮问完,3-6 个

按轮次走。每一轮问的是「前置条件已落定、现在就能问」的全部问题,不硬塞依赖其它未答问题的问题。

- **一轮 3-6 个**。超过 6 个说明要么该拆需求,要么层次太深、该先问更上层
- 当前能问的有 7-12 个 → 分两批,先说明「这一层大概 N 个,分两次问」
- 超过 12 个 → 停下,说明「这事儿比我想的大」,重看边界

### 每题附推荐答案,措辞让「好」等于同意

```
❓ Q1 - <问题标题>:<题干>

➡️ <推荐答案与一句理由>

---
❓ Q2 …
```

写「模糊匹配我打算做成输一部分就能匹配,对吗?」而不是「你想用哪种匹配方式?」。

用户的回答可以是逐条、整轮接受、或部分回答。答不了的留在树上,下一轮再问。

### 什么时候停止提问

不是所有问题都有答案,而是**没有会影响方向的未知了**:

- 剩下的只影响「怎么做」,不影响「做什么」→ 停
- 剩下的答错了可以事后调 → 停
- 剩下的不定就做不下去 → 继续问

### 没缺口就不提问

文档已经写全、和代码现实对得上、没有冲突项 → 直接说「我看明白了,这就去做」,跳过提问与后续全部文档。

## 第五件事:定大小

所有该问的问完才判。依据是可测量的东西:

| 判断 | 产出 |
|---|---|
| 该说的都清楚,没缺口 | 直接做,做完汇报做了什么 |
| 缺口少、只碰一两个地方 | 一页纸 brief |
| 要动数据结构、碰好几个模块 | 完整设计 brief |
| 复述不出来 | 大需求那条路(见判断 B) |

**由 agent 给出判断并说明理由,用户一句话确认或改。** 判小了是返工,判大了只是多花一轮,两个方向代价不对称。

中途发现变大(聊到一半牵出一个更大的未定决定)→ 停下说明,升一档,不硬往下推。

## 第六件事:写 brief

按 [references/brief-template.md](brief-template.md) 写。规模按上一步的判断。
