# intake — 接到需求

dev 阶段 0 的入口：先看清，再决定走哪条路；进入 brief 路径后，再定文档档位。访谈纪律的唯一真值在 `grilling`，本文不复制。

## 第一件事：看清

第一次正式回复前，先读完：

- 需求本身：一句话就一句话，文档就全文
- 涉及的代码：读到能说清「现在怎么跑、这次会碰什么」
- 项目已有约定：`CONTEXT.md` 的用词、相关 `docs/adr/`、既有命名与目录习惯
- `docs/plans/` 下有没有做过的类似特性

同时把**自己能查的事实查完**：某个库支不支持、项目里有没有现成实现、惯例是什么。查不完的只挡住依赖它的问题，不挡住整轮提问。

永远不要问项目或用户给的上下文已经回答过的问题。

除「直接做」外，第一次回复先给一段简短回述：

- 我理解你要什么、给谁、为什么
- 我查到的相关现状
- 一件可能改变做法的约束、冲突或更便宜的路
- 邀请你纠正

## 第二件事：按顺序判断入口

### 判断 A：是有东西坏了吗

现有功能报错、结果不对或卡住，目标是恢复既有行为 → 读 `debugging` 技能，走复现—根因—回归测试，不写需求文档。

行为变更不是 bug。修复暴露设计级改动时，才回到本流程重新判断。

### 判断 B：信息是否完整到可以直接做

三个条件同时满足：

1. **行为明确**：要改成什么样，没有产品方向上的备选
2. **边界明确**：不做什么也能从请求或项目约定中确定
3. **完成标准明确**：怎样算做对，可以直接验证，不需要再讨论验收口径

全部满足 → 直接做，做完汇报做了什么、验证证据、所做假设与 TDD waiver（若有）。

改动小但存在方向性选择，不能直接做。

### 判断 C：能向用户复述清楚吗

用两三句话向用户说清「要什么 / 不要什么 / 怎样算失败」，并请用户确认。不是 agent 自己觉得明白就算通过。

| 结果 | 走 |
|---|---|
| 能复述，用户确认 | 进入 brief 路径 |
| 不能复述，需求边界未成形 | 大需求探路 |
| 其实是几件独立的事 | 拆开排序，逐件重新判断 |

## 大需求探路

判据不是工程量大，而是需求边界尚未成形：用户能列出一批想做的事，但共同终点或优先级不清，继续问实现细节会变成猜。

纪律：

- 先定「走到哪里算告一段落」
- 一次只解一件，从最好解的开始
- **只产决定，不产代码**
- 已确定的事直接作为后续访谈的既有共识，不再重谈
- 清晰后重新判断一页纸或完整 brief

## 几件独立的事：先拆包，不新增入口

「拆开排序」不是第五条路径。各自能单独说清目标与验收、一件不做不阻碍另一件交付、一件的方案不决定另一件的方案，才算独立。

拆开后由 agent 推荐顺序、用户确认，一次处理一件。每件重新判断：直接做、走 brief、走 debugging，或进入大需求探路。

这里拆的是**需求边界**，不是实现任务；任务切片仍在同一份 brief 批准后进行。

## 第三件事：进入 brief 路径后定档

只有两档：**一页纸 brief、完整 brief**。

出现以下任一信号，选完整 brief：

- 新增或修改核心数据结构
- 多模块协调，任务边界不能一眼看清
- 多个真实方案的取舍明显影响实现
- 多个测试接缝或复杂验收
- 有必须现在解决的结构级约束或兼容问题

以上都没有，只是局部行为缺口，选一页纸 brief。

文件数、代码行数、预计耗时都不是判据。两档的八节结构、三道门与后续开发纪律完全相同，只有展开度不同。

入口给的是初判；访谈中出现完整档信号，停下说明并升档。用户可以改判，但会留下结构级缺口时必须指出。

## 第四件事：访谈与方案对比

读 `grilling` 技能并严格执行：固定整轮提问，一轮提出当前不依赖其他未答问题的全部问题；回答后回述本轮变化、重算下一轮，直到影响方向的未知清零，或用户明确叫停。

访谈全程读 `domain-docs` 并执行其纪律：术语就地写入 `CONTEXT.md`；满足 ADR 三关的决策先标记，门 1 呈报，批准后落盘。

理解「要什么」之后、写 brief 之前，如仍有多种会改变交付结果或后续成本的实现路径，**单独一条消息**做方案对比：

- 只列 2-3 个真实可行的方案，说清各自代价
- 推荐一个并说明理由，等用户选定
- 只有一个合理方案或用户已指定路线时，不硬凑备选，说明理由即可
- 选定方案若引出新的需求问题，回到访谈再来一轮

方案选择是用户的事；函数名、目录、内部拆分等实现选择是 agent 的事，标 `[我]`，不拿去占用用户的决策精力。

## 第五件事：写 brief

按 [brief-template.md](brief-template.md) 写。brief 只记录已经决定的内容，不产生新决策；出现用户没说过、也没有标为 agent 判断的内容，视为缺陷。
