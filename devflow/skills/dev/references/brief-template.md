# brief 模板

需求与方案文档。**只记录访谈与方案对比已经决定的内容，不在写文档时产生新决策。** 门 1 批准后冻结，开发期发现方案错误走回退协议，不就地修改。

验收标准一句话:**一个内行的构建者拿着它,不需要再回来问用户,就能列出一份靠谱的施工计划。**

达不到是写少了;写到函数签名和文件路径是写多了。

---

## 骨架

```markdown
# <特性名> · 设计说明

> <YYYY-MM-DD> | 状态:草稿 / 已批准 | 档位:一页纸 / 完整

## 1. 背景与问题

## 2. 目标 · 非目标 · 失败形态

**目标**

**非目标**

**失败形态**

## 3. 选定方案

## 4. 约束

## 5. 关键决策

## 6. 未定项

| 未定的事 | 波及哪里 | 不定会怎样 |

## 7. 验收标准

### 7.1 验收条目

### 7.2 测试接缝

## 8. 授权项
```

## 逐节要求

### 1. 背景与问题

用户视角的问题陈述:现在什么不好、为什么非改不可。不写技术。

### 2. 目标 · 非目标 · 失败形态

- **目标**:这次达到什么,可验证的表述
- **非目标**:明确不做的,一行一个
- **失败形态**:技术上能跑、但实际是失败的形态。例:「页面做出来了,但没人会在上面点任何按钮」

第三条最容易漏,也最有用——它定义的失败形态会被「功能都实现了」掩盖过去。

### 3. 选定方案

一段话说清选的是哪条路。**只能有一个活方案。** 被否掉的各一行:名字 + 为什么不用。

两个都行等于没定。

### 4. 约束

技术栈与版本下限、平台要求、命名与用词规矩、不能违反的既有决定、视觉约束(有 DESIGN.md 时以引用写入,不复述 token 值)。

**逐条抄自项目既有约定,不改写。** 这节会被原样继承进实现者的简报,此处自己发挥会让后面全部走样。

### 5. 关键决策

每条附来源标记:

```markdown
- 搜索独立成一个模块,不塞进文章模块 [你]
- 索引放内存不落盘 [我]
- 结果最多 20 条 [你]
```

**规矩:agent 自己做的选择写成「我的判断」,绝不许写成「用户同意过的」。** 用户扫一遍就能挑出自己没参与的那些。


写入前先分流，别让本节成为所有内容的默认落点：

| 内容 | 去向 |
|---|---|
| 项目领域术语 | `CONTEXT.md`，定义落定时已写入 |
| 同时满足 ADR 三关的难逆转决策 | 门 1 呈报，批准后写入 `docs/adr/` |
| 参数、取值、普通实现决定 | 本节，标 `[你]` 或 `[我]` |
| 纯讨论过程 | 不另造文件，由回述与本 brief 的成品记录承接 |
### 6. 未定项

三列:未定的事 / 波及哪里 / 不定会怎样。

**准入:波及整个特性、要动数据结构、跨多个模块的,不许留。** 只波及一个函数、改起来很快的可以留,但后续计划里要排到最后,并写明依赖。

### 7. 验收标准

**7.1 验收条目** —— 用户视角的验收:用起来能看到什么、能做什么。一条一行,可观察。不写测试怎么写。

**7.2 测试接缝** —— 技术视角的测试落点。三条取舍原则:

- 优先用已有的接缝,别开新的
- 尽量在最高的地方测
- 新接缝越少越好,理想是整段改动只有一个

要新开接缝时,在此明说,并写清为什么已有接缝不够用。

### 8. 授权项

以下地方**不做规定**,由实施者自行决定,不用回来问。逐条列。

与第 6 节的区别:第 6 节是**欠账**(需要定,现在先放着,后面必须定);第 8 节是**授权**(本来就不该由需求阶段决定)。

## 一页纸档的写法

八节一个不少,每节压到一两句话。

压的是展开度,不是确定性——每一条仍然必须是决定。对比:

- 完整档:`| 排序要不要考虑同义词(前端 / frontend) | 排序这一个函数 | 半小时 |`
- 一页纸:`同义词 -- 不影响做法,排在最后做`

第二种短,但仍给了判断(不影响做法、可后置)。写成「同义词问题待讨论」就是把问题丢回给用户,不合格。

## 硬规矩

- 不写函数签名、参数类型、返回结构
- 不写文件路径、目录结构
- 不写字段定义、表结构
- 第 3 节只有一个活方案
- 第 6 节不留结构级欠账

数据结构只写「业务说法」不写「技术说法」:

- 写:「文章有草稿、已发布、已归档三种状态」「一个标签能挂多篇文章」
- 不写:「articles 表加 status varchar(16)」「tag_id 建索引」

## 排版纪律(读者是人)

- 一个 bullet 一个事实;超过 2 个子句拆成子 bullet,禁止用「;」把 3 个以上独立事实焊进一条
- 编号项(①②③)分行成子 bullet,不许挤在同一段
- 标题只放标识符(模块名/函数签名/名称),职责说明移到下一行普通文字
- 超过 2 组的「输入 → 期望」对照一律用两列表格,不写行内箭头链
- 多步处理顺序写成编号步骤列表,每步一行,箭头只许出现在单步内部

教训:呈报文档曾按 agent 解析偏好写成巨型单段 bullet 与管道符流水账,人无法扫读,门点形同虚设。
