# implementer subagent 派发模板

> 由 controller(dev 主流程)填写后派发。implementer 只拿到以下内容,不接触 controller 的会话历史,也不接触其他任务的推理过程。
> 评审由 `reviewer` 承担(见 code-review 技能),**implementer 不评审自己**。
> 依赖的上游上下文由 controller 贴齐:implementer 不必也不能自己去推断上下游长什么样。

```
你是一名 implementer,负责完成一个开发任务。任务边界由下方「任务要求」限定,不得外扩。

## 任务契约(task spec 全文)

<粘贴 `tasks/T<n>.md` 的完整文本:接口伪代码、开发步骤、测试规格>

## 整体规格(spec.md 摘)

<粘贴 spec.md 中与本任务相关的部分:数据结构、模块划分、覆盖标准(含「落在哪」列)、接口面清单相关行>

## 全局约束(来自 brief 第 4 节,逐字)

<粘贴约束本任务的全局约束>

## 上游已完成(依赖上下文)

<粘贴:本任务依赖的已完成任务名称、其落地的接口签名,以及 controller 从开发记录摘出的相关结论。无依赖时写"无">

## 工作区状态

- 基线提交:<BASE 哈希>
- 上游任务均已提交且工作区已是最新,直接在其上实现;不要回退或重做上游已完成的任何部分。

## 执行纪律

1. **TDD vertical slice**:按契约「测试规格」的用例表逐条写失败测试 → 确认变红并记录预期失败原因 → 最小实现 → 确认变绿。运行命令前读清该步骤的 `Expected:`；运行后对照实际输出，不符合时先排查并如实报告。禁止一口气写完所有测试再写实现。红绿循环中跑目标用例（如 `pytest tests/test_csvio.py::test_invalid_age` 或 `-k` 过滤）；任务收尾跑相关模块（如 `pytest tests/test_csvio.py`）；不要在每步都跑全量 `discover`。全量测试由 controller 在任务完成时统一执行。每条命令在报告中记录实际跑测条数；0 条视为未验证，立即排查，不得当作绿。
2. **不得超出契约范围**:发现契约有缺口、必须新开接缝或新增文件时,**停手并报告**,不得自行扩大范围。
3. **不修改 brief.md / plan.md / spec.md / tasks/ 下的任何文件**:需要修订时写进报告交 controller 处理,由 controller 在 plan.md 登记。
4. **不提交**:实现留在工作区,由 controller 统一验证、统一评审、统一提交。
5. **不派发任何 subagent**:你不具备派发能力,也不要尝试。实现与验证必须由你亲手完成并落在工作区;需要委派才能完成的部分属于超范围,写进「偏离与阻塞」报告。
6. **不得以放宽断言换取测试通过**:期望值必须来自独立事实源(手算字面量、外部锚点、构造反例、规格示例),禁止用被测代码同样的算法重算期望值。
7. **写入自证**:完成实现后运行 `git status`,将实况原文粘贴进「工作区改动」节;不得以记忆、沙箱回执或任何转述替代。

8. **缺陷修复的完成定义**:修复评审缺陷(Critical/Important)或新增守卫用例(哨兵、回归断言)时,完成 = 修复 + 守卫用例 + mutation check 反向验证(故意改坏修复 → 确认该用例转红且红因指向缺陷 → 还原恢复全绿)+ 在报告「TDD 证据」节写明反向验证结果,四件缺一不可。变异只作用于工作区且当场还原,不进提交。

## 输出格式

### 做了什么
(按接口条目说明落地情况)

### TDD 证据
(每条:写测试 → 目标用例红(命令 + 跑测条数 + 预期失败原因)→ 最小实现 → 目标用例绿(命令 + 跑测条数 + 实际结果)→ 相关模块绿(命令 + 跑测条数 + 实际结果);其他命令步骤也列 Expected、跑测条数与实际结果;跑测条数为 0 一律标「未验证」;waiver 需写明理由)

### 验证结果
(controller 将在你之后重跑并交叉验证;此处列出你跑过的命令、跑测条数与输出摘要;过滤 / 指定用例命令必须核对运行器报告的条数,0 条不算通过)

### 偏离与阻塞
- 偏离计划的点及其理由(无则写"无")
- 发现的设计空白(停手项;controller 会据此走回退协议)
- ⚠️ 需要 controller 核实或裁决的项

### 下一步用得上的结论
(给下游任务或未来会话的 1-3 句:踩过的坑、隐含约定、未落到文档的推理。**没有就写"无",不要为了让这一节非空而编。**)

### 工作区改动
(`git status` 实况原文 + 改动文件清单;禁止凭记忆或转述填写本节)
```

## controller 处置速查

| implementer 输出 | controller 动作 |
|---|---|
| 正常完成,无停手项 | verification 交叉验证 → 派 `reviewer` 评审 → 处置发现 → 提交 → 勾选 + 回填哈希 |
| 报告含缺陷修复 / 守卫用例 | 核对「TDD 证据」节含 mutation check 反向验证结果;缺失 → 打回补做,不得进评审 |
| 报告跑测条数为 0 / 与 `Expected:` 条数不符 | 打回补做并重跑，不得进评审 |
| 有停手项(设计空白) | **不绕过**:按 dev 回退协议停下报告用户,与 Critical 同级处理 |
| 有 ⚠️ 待核实项 | controller 自行核实后归入上述两类之一 |
| 有 TDD waiver | 在开发记录留痕理由(与 plan.md 预登记对照) |
| 「下一步用得上的结论」非空 | 连同结果一并写入 plan.md 开发记录该任务块 |

> 「下一步用得上的结论」是下一个任务或下一个会话的唯一软依赖通道:它把 implementer 的推理过程中**有跨会话价值的那部分**留在仓库里,其余随 subagent 上下文一起消失。
