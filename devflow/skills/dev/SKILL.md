# dev — 主开发工作流

命令启动、人守关键门、agent 在门之间自治。

底层纪律技能,按名称在可用技能列表中找到并读取其 SKILL.md 后严格执行:`grilling`(访谈)、`tdd`、`verification`、`code-review`、`debugging`、`domain-docs`。

## 阶段 0:接到需求

读 [references/intake.md](references/intake.md) 执行：先看清（读需求、读代码、读约定、查事实），再按顺序判断入口，最后才定 brief 档位。入口是判断的结果，不是任务大小的标签。

| 判断结果 | 走 |
|---|---|
| 有东西坏了 | 读 `debugging`，走复现—根因—回归测试。**不写需求文档** |
| 行为、边界、完成标准都已明确 | 直接做，跳过后续全部文档，做完汇报假设与验证 |
| 需求边界未成形 | 大需求探路：先定终点，一次解一件，只产决定不产代码 |
| 几件独立的事 | 拆开排序，逐件重新判断，不混进同一份 brief |
| 进入 brief 路径 | 读 `grilling` 整轮访谈 → 方案对比 → 阶段 1 |

进入 brief 路径后只有**一页纸 / 完整**两档。两档的八节结构、三道门与后续开发纪律相同，只有展开度不同。访谈与方案对比按 `intake.md` 的指针执行；发现完整档信号就停下升档。

## 阶段 1:需求文档 + 门 1

按 [references/brief-template.md](references/brief-template.md) 写 `docs/plans/<YYYY-MM-DD>-<slug>/brief.md`，档位按 intake 的复核结果（一页纸 / 完整）。brief 只记录访谈与方案对比已经决定的内容，不产生新决策。

### 门 1

呈报时按 [references/self-check.md](references/self-check.md) 末尾的「呈报给用户时给什么」执行:给摘要 + 三个问题(范围对不对 / 我替你拍板的认不认 / 留着的欠账能不能留),停下等明确批准。有意见→修订→再呈现,迭代到批准。

**此门前一行代码都不写**,包括搭架子、装依赖、建目录。看和查可以。

**门 1 批准的 ADR 此时落盘，随后立即提交 `brief.md` 与这些 ADR。** 之后 brief 冻结：开发期发现方案错误走回退协议，不就地修改。

## 阶段 2:切片

读 [references/slice.md](references/slice.md),按其中的切片规则把 `brief` 切成任务,写 `plan.md` 到同一目录。

**切片结果不在这里通知用户**,等阶段 3 写完 spec 与契约、跑完自查,在门 2 一次性呈报。

## 阶段 3:技术规格与任务契约

**技术规格**:按 [references/tech-spec-template.md](references/tech-spec-template.md) 写 `spec.md`——整体实现、按需流程图、数据结构、带模块路径的模块划分、技术选型、覆盖标准、接口面清单。不设篇幅上限。

**任务契约**:按 [references/task-spec-template.md](references/task-spec-template.md) 为每个任务写 `tasks/T<n>.md`——实现方式、按需流程图、接口伪代码与文件落点、可选数据结构、开发步骤、测试规格。实现方式描述本任务模块的逻辑处理方式；伪代码只写调用形状，不写算法。

全部写完后跑 [references/self-check.md](references/self-check.md) 的十条自查,就地修完,然后呈报门 2。

### 门 2

按 [references/self-check.md](references/self-check.md) 的「门 2 呈报」执行:任务清单与依赖、每个任务的接缝与用例条数、覆盖标准的档位、十条自查结果，加五个问题,**停下等一句确认**。

**批准后立即提交 `plan.md`、`spec.md` 与 `tasks/`。** 此门之后不再停顿,直到门 3。

一道门只在这一处:切片与契约是判断(切几件、任务粒度与依赖是否合理、接缝开在哪、用例够不够),不是机械分解。只给清单看不出对不对,得连每个任务测什么一起给。

## 阶段 4:逐任务开发(自治,任务间不停顿)

**开始 T1 前做一次任务间接口预检**，再记录 BASE。逐个核对任务契约中跨任务生产/消费的接口：生产方与消费方的名称、签名、数据形状及其和 `spec.md` 定义是否一致；同时核对文件落点归属。再核对各任务契约里测试命令的可解析性：T1 是否含测试基座创建动作、跨任务测试模块命名与 `-k` 模式是否一致、过滤类命令的 `Expected:` 是否写了跑测条数。将结果记入 `plan.md`「开发记录」的「开工前接口预检」块；没有共享接口时写「无共享接口」。发现契约间不一致，先按回退协议修订并复检；若涉及 `brief` 的方向或行为，则回门 1。
任务顺序由依赖决定。每个任务按序走:

1. 记录 `BASE=$(git rev-parse HEAD)`。
2. **实现**——两种形态:
   - **优先派 implementer subagent**:按 [references/implementer-prompt.md](references/implementer-prompt.md) 填简报派发。要求实现留在工作区、**不提交**、不改四层文档、发现契约缺口即停手报告。
   - **fallback 会话内实现**:读 `tdd` 技能,按任务契约的测试规格逐条写失败测试 → 亲眼看红 → 最小实现 → 看绿。waiver 需留痕。
3. 读 `verification`:**自己重跑验证**。核对 implementer 报告中每个命令步骤的实际结果是否符合契约 `Expected:`，并亲自重跑最终验证命令、对照其预期；subagent 回报的结果本身不算验证证据。把它声称的改动清单与 `git status` 实况逐项核对,并对照契约里「涉及」的文件数——多出来的就是越界。不符即整体降信。
4. 读 `code-review`:按其方法派 subagent 评审本任务 diff(无 subagent 时按其 fallback 做 self-review 并标注「非独立」)。简报的规格来源是 `tasks/T<n>.md` + `spec.md` 的覆盖标准与接口清单。
5. 处置发现:**Critical 或方案性偏离计划 → 暂停询问用户**;Important 修完继续并重跑覆盖测试;Minor 记入开发记录。同一发现两轮修复不过 → 升级为用户决策。
6. 提交:commit message 引用任务号。
7. 记账:在 `plan.md` 勾选、回填 commit 哈希、按 [references/slice.md](references/slice.md) 的「开发记录格式」追加一块(**含 implementer 回报的「下一步用得上的结论」与所有文档变更登记**),删除本轮 `.review/` diff 文件。
8. 更新已完成任务集,重算 ready set,调用 `context_usage` 读一次上下文占比,按「上下文预算」决定继续还是提示换会话。

**开发中状态一律落盘**:进度在 `plan.md`,不在会话上下文里。上下文被压缩后,先重读 `brief`、`spec`、`plan` 与当前任务的契约再继续;信文档与 git 历史,不信记忆。

### 依赖与派发顺序

`plan.md` 的「挡谁」字段构成一张 DAG。每次准备做下一个任务前**先重算 ready set**:所有硬依赖已完成、且自身未完成的任务。

**串行执行,不并行。** 理由是形态决定的:任务是纵向贯穿各层的切片,两个"互不依赖"的任务可能落在同一个注册文件、类型导出 barrel 或路由表上;每任务一 commit 的线性历史是回退协议的前提。串行本身即依赖保障——上游提交后代码已真实存在,下游读代码即可拿到接口。

派发时把上游已完成任务的接口签名与开发记录里的相关结论贴进简报的「上游已完成」节,别让下游 subagent 自己猜。

### 上下文预算

每个任务提交后调用 `context_usage` 工具读一次占比(只报数、不判阈值)。**≥ 45% → 在任务边界提示换会话;低于 45% → 直接做下一个任务,零打断。**

工具不可用时退回三条可数信号,任一为「是」即提示:

1. 本次会话内同一节文档是否已第三次重读
2. 最近两个任务是否都需要回头翻前文才能确认接口
3. 是否已记不清早前某个任务的决定,只能靠 git 或文档反查

**底线**:完成 4 个任务后不论感觉如何都至少检查一次。

提示切换时:在任务边界停下,写明「建议开新会话,运行 /dev-resume 继续」,把本任务的结论写进开发记录后再停。

## 阶段 5:收尾与门 3

1. **跑全量测试。** 红了就报失败项,不给后续选项。
2. **整特性终审**:按 `code-review` 的「整特性终审」执行。给 reviewer 的输入是**接缝导航包**（跨任务接缝清单 + 覆盖矩阵 + 挂起 Minor 清单），而非全量 diff；完整 diff 保留可查，但不要求从头重读。有发现→派**一个**修复代理带完整清单,修完做**一次**范围收窄的复审,不搞第二波。
3. **最终报告**,六块:
   - `brief` 第 7.1 节验收逐项结果(通过 / 未验证 / 本机不可达,不可达不许用替代测试假装修好)
   - 各任务评审记录
   - TDD waiver 清单
   - 完整提交列表
   - 遗留事项(记录在案的 Minor)
   - **我替你做过的判断**(第 5 节所有 `[我]` 项 + 实施期自己拍板的处置)
4. **门 3**:停下等确认。报告只报状态,不下「全部通过」的总结论——有些验收项根本没验过。
5. 收尾:清 `.review/` 目录、写收尾总结（**对账**本次已写入的 `CONTEXT.md` 词条与 ADR，清单与文件实况不符先补齐说明）、处理开发记录(过长时折叠为摘要并注明完整记录见 git 历史)、提交。

## 回退协议

- **任何阶段发现 `brief` 里的方向站不住** → 停下报告(缺陷是什么、影响哪些已完成任务、建议的修订方向),在 `brief` 上改,**重过门 1**。代码不存在时回退零成本;代码已存在时先说明影响范围。
- **`plan` / `spec` / 任务契约要改** → 直接在 `plan.md` 开发记录登记一行,不重过门。触及 `brief` 决策的修订不得在此发生,走上一条。
- **`spec` 与 `brief` 冲突** → 以 `brief` 为准。
- **设计变更推翻某条 ADR** → ADR 不可修改只可被取代:旧 ADR 标注「已被 NNNN 取代」,新决策写新 ADR。`CONTEXT.md` 术语就地更新。
- **你的义务**:任何阶段发现设计缺陷,停下来报告,不将错就错、不在计划里偷偷绕过。
