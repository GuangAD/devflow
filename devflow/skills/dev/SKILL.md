# dev — 主开发工作流

个人开发工作流:命令启动、人守关键门、agent 在门之间自治。
底层纪律技能:grilling(访谈)、domain-docs(知识沉淀)、tdd、code-review、debugging、verification——按名称在你的可用技能列表中找到并读取其 SKILL.md 后严格执行。

## 第一步:分类

收到任务描述后,先分类并把分类结果告知用户:

**判重(走重流程)信号**:新功能/新模块/新项目;需要改动数据结构;预计新建文件较多;用户说"做个/加个/实现一个";该领域尚无设计文档覆盖。

**判轻(走轻流程)信号**:修 bug;调文案;改配置;重构既有函数;docs/plans/ 下已有计划中的对应任务。

**判巨(走 /dev-map 决策地图)信号**:一次访谈装不下(设计树一轮收不住,预计要跨多个会话才谈得清);存在"连问题都说不 sharp"的区域(不是缺答案,是缺问题);工作量大到现在列不出完整的设计树。

**判巨优先于判重**:先看是不是一次访谈装不下,再谈轻重。

**拿不准**:问一句并给出推荐——轻/重之间问"这个走完整设计流程,还是直接改?";重/巨之间问"这个一次访谈能谈清,还是要先建地图探路?"

## 轻流程(零门)

1. 有歧义且不问就会做错 → 单句澄清;否则按最合理理解干,完成后汇报假设。
2. 修 bug → 读取 debugging 技能并遵守:根因先行,禁止症状式糊补;疑难 bug(偶发/难复现)升级为其完整诊断回路。
3. 涉及行为改动 → 读取 tdd 技能:默认先写失败测试再看它变绿;豁免必须留痕。
4. 宣称完成前 → 读取 verification 技能:本回合跑过验证命令并读全输出。
5. 提交,汇报:做了什么、验证证据、TDD 豁免及理由、所做假设。

**升级棘轮**:中途发现实为设计级改动(如修 bug 时发现根因在数据结构)→ 停下,说明发现,转入重流程;若发现是一次访谈装不下的大改造 → 转入 /dev-map 建地图。只可往自律的方向升(轻→重→巨),不可反向降。

## 重流程

### 阶段 1:访谈

读取 grilling 技能,按其方法访谈(设计树、轮次、批量提问、每题附推荐答案)。事实自己查(必要时派子代理),决策交用户。

**已有地图时**(`docs/maps/` 下存在本次的 map.md):先读其「已定决策」节与「目的地」,这些决策不必重谈,直接作为访谈的既有共识;访谈只补门 1 自查发现的具体空白。

访谈全程同时执行 domain-docs 技能:术语当场写入 CONTEXT.md;满足三条件(难逆转+缺上下文会令人困惑+真实权衡)的决策,当场提议写 ADR。

**结束条件**:设计树每个分支都走过,没有任何默默假设;向用户总结共识,获得确认后才能进入下一步。

随后过一遍 [references/design-checklist.md](references/design-checklist.md),写两份文档到 `docs/plans/<YYYY-MM-DD>-<特性slug>/`:

- 按 [references/design-template.md](references/design-template.md) 写 `design.md`(决策快照:背景/目标/方案/技术栈与依赖约束/权衡/开放问题)。
- 按 [references/spec-template.md](references/spec-template.md) 写 `spec.md` 骨架:数据结构说明、接缝接口规格(每条目四件套:签名/后置条件/副作用与可重入性/错误行为,且至少 1 条钉住用例)、接口面穷举清单(全部模块公共导出一行一个,标注接缝/非接缝)、非接缝模块与视觉验收(数值预算逐条附机检方案)、编码方向、空「变更记录」节。

**自查红线**:两份文档均不得出现访谈未覆盖的内容;写实现细节层面以下的完整代码(数据结构定义与接口签名要具体,函数体不要)。接缝条目缺四件套之一、或穷举清单不完整,视同开放问题非空,不得呈报门 1。

### 门 1:设计文档确认

向用户呈现两份文档(design.md + spec.md 骨架)的路径与各节摘要,**停下等待明确批准**。有意见→修订→再呈现,迭代到批准为止。此门前一行代码都不写。

**批准后立即提交 design.md 与 spec.md**(此时停止的用户,后续可经 /dev-resume 从阶段 2 接续)。

### 阶段 2:计划(不跑访谈,机械分解)

设计已确认,先把 spec.md 从骨架补全为用例详版:每个接缝条目 3-8 条用例(典型+边界+反例,期望值附事实源)。再切任务、排依赖、定验收标准——这是你的执行专业,按 [references/plan-template.md](references/plan-template.md) 写 `plan.md` 到同一目录。要求:

- 曳光弹切片:每任务纵向贯穿各层、可独立验收、单个会话可容纳
- 任务 = spec.md 的一组接缝条目从红到绿(任务详情引用接口组);含编码方向与数据结构落地说明;大任务在此拆分
- 任务间依赖显式声明;独立任务的先后顺序若属用户偏好,给推荐排序供门 2 一并确认

**边界规则**:①切任务时暴露设计级空白 → 回退(见回退协议),禁止在 plan.md 夹带设计决策;②纯执行细节自己定,不再问用户。

### 门 2:计划文档确认

呈现 spec.md 用例详版与任务清单(每个任务:名称、端到端行为、接口组、依赖),修订循环至批准。批计划即批拆分与用例详版,不另设门。**批准后立即提交 spec.md 与 plan.md。**

### 阶段 3:开发(自治,任务间不停顿)

对每个任务,按序执行:

1. 记录 `BASE=$(git rev-parse HEAD)`。
2. 读取 tdd 技能:按 spec.md 该接口组的用例表写失败测试 → 亲眼看红(预期原因)→ 最小实现 → 看绿。豁免需留痕:"本任务豁免 TDD,理由是……"(已在 plan.md 预登记的豁免,注明预登记)。
3. 读取 verification 技能:以新鲜验证证据确认验收标准逐项达成。
4. 读取 code-review 技能:按其方法派子代理评审本任务 diff(环境无子代理能力时按其降级程序自审并标注"非独立")。
5. 处置发现:**Critical 或方案性偏离计划 → 暂停询问用户**;Important/Minor 记入开发记录后续行。
6. 提交:commit message 引用任务号与要点。
7. 在 plan.md 任务清单勾选该任务并回填 commit 哈希;"开发记录"节追加一行(结果/评审发现/豁免/哈希,凡动过 spec.md 注明"变更记录已登记");删除本轮评审的 `.review/` diff 文件。
8. 下一任务。

**开发中状态一律落盘**:进度在 plan.md,不在会话上下文里。上下文被压缩后,先重读 design.md、spec.md(含变更记录)与 plan.md 再继续;信文档与 git 历史,不信记忆。

### 门 3:最终确认

全部任务完成后,呈现最终报告:**验收清单逐项结果、各任务评审记录、TDD 豁免清单、完整提交列表、遗留事项(记录在案的 Minor)**。停下等待用户确认。确认后收尾:清理临时产物(含 `.review/` 目录)、写一段收尾总结(含本次沉淀的 CONTEXT.md/ADR 清单)。

## 巨流程(路由到 /dev-map)

判巨时不在此展开:读取 dev-map 技能并遵守。它用一张 `docs/maps/<YYYY-MM-DD>-<slug>/map.md` 分批探路,一次会话解一张票,把说不清的雾变成已定决策。

**它补的是本流程的结构性死角**:门 1 要求"设计树无含糊分支",而巨大需求的开放问题短期清不空——硬进重流程只会卡在门 1 前无限访谈。地图层替重流程把这一步做掉,自己不碰代码。

地图走完(雾散、前线空)→ 回到本技能的**重流程**,已定决策直接喂 design.md,访谈只补门 1 自查发现的具体空白。

## 回退协议

- **计划阶段发现设计错误**(你发现,或用户在门 2 提出):回到访谈,只重开设计树上受影响的分支;修订 design.md 与 spec.md 骨架重过门 1;补全用例详版、重写 plan.md 重过门 2。此时代码不存在,回退零成本。
- **设计变更推翻某条 ADR**:ADR 不可修改只可被取代——旧 ADR 标注"已被 NNNN 取代",新决策写新 ADR。CONTEXT.md 术语就地更新。
- **spec.md 与 design.md 冲突**:以 design.md 为准。spec.md 的开发期修订一律登记其「变更记录」节;触及 design.md 决策的修订不得就地发生,按上述回退线走。
- **你的义务**:任何阶段发现设计缺陷,停下来报告,不将错就错、不在计划里偷偷绕过。报告须含:缺陷是什么、影响哪些已完成任务、建议的修订方向。
