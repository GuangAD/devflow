# domain-docs — 知识沉淀纪律

项目的长期记忆分两层:**词汇表管"词是什么意思",ADR 管"为什么长这样"**。两者都在仓库里、进 git,是 agent 跨会话理解项目的根据。

## 消费规则(任何时候都适用)

**读 `CONTEXT.md` 取词不算本技能**——那是任何技能一行就能做的事。本技能用于**改变**领域模型时：新增或修正术语、记录难逆转决策。

在设计或编码前,读取根目录 `CONTEXT.md`(若存在)以获得领域词汇;查看 `docs/adr/` 中与所改区域相关的 ADR,不得重新争论已有决策。

## CONTEXT.md 词汇表

- **纯词汇表,零实现细节**:不是 spec,不是草稿纸。每条回答"这个词在我们的领域里指什么"。
- 惰性创建:第一个词条出现时才建文件。
- 词条格式:
- 只收项目特有的词，过两道判据：先排掉通用编程概念（超时、错误类型、工具函数模式）；再问「这个词定义不清，两个人各按自己的理解实现，会不会做出不一样的东西？」会才收。参数与取值留在 `brief`，不进词汇表。

```markdown
## <术语>

<一句话定义>。<触发点/边界>(若适用)。

反义/易混淆:<X 指 A,Y 指 B,不要混用>。(若适用)
```

## 会话中的五个动作

1. **对照挑战**:用户用词与词汇表冲突时立即指出——"词汇表定义 X 是 A,你现在的意思像 B,是哪个?"
2. **锐化模糊词**:用户用了含糊或一词多义的词,提议精确的规范术语——"'account' 指 Customer 还是 User?这是两个东西。"
3. **场景压测**:讨论领域关系时,构造具体场景逼出概念边界。
4. **与代码交叉验证**:用户陈述与代码现状矛盾时当场摆出——"代码是整单取消,你说支持部分取消,哪个对?"
5. **就地更新**:术语落定的那一刻写入 CONTEXT.md,不攒批。

## ADR 架构决策记录

**三条件门槛,全满足才提议**,缺一不写:难以逆转(改主意代价大)、缺上下文会令人困惑(未来读者会问为什么)、真实权衡的产物(当时确有别的选项)。

文件:`docs/adr/NNNN-<短名>.md`,编号递增。格式:
在 dev 访谈中，满足三关的决策先标记，门 1 呈报时逐项提议，门 1 批准后落盘。术语是记录，定下来就写；ADR 是承诺，经过门 1 再写。

```markdown
# NNNN - <决策标题>

日期:<YYYY-MM-DD> | 状态:已采纳

## 背景
为什么需要做这个决定。

## 决策
选了什么。

## 为什么不用 <被放弃的方案>
真实的理由,逐条。

## 后果
好处与代价都写。
```

**取代协议**:ADR 不可修改,只可被取代——旧文件状态改为"已被 NNNN 取代",新决策写新文件,推理链永久保留。

**别再提了清单**:后续工作(计划、评审、巡检)提出的建议若与某 ADR 冲突,必须标注"与 ADR-N 冲突"并给出值得重开的理由;否则直接不再提出。
