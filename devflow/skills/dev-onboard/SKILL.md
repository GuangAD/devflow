# dev-onboard — 项目入职

给「手里还没有需求」的 agent 一条确定的读法:**读什么、读到哪停、怎么证明读懂了。**

进展顺利的标志不是「读完了」,而是用户看完回述后**指不出一处理解错误**。

## 产物只有认知

不写代码、不产出 `brief` / `plan` / `spec` / 任务契约、不新建项目地图类文档。项目已有六份长期文档(见下),加第七份必然与它们漂移。

## 与其它命令的边界

| 你在哪 | 用 |
|---|---|
| 没需求,先读懂项目 | 本命令 |
| 有需求,要改代码 | `/dev` |
| 有未完成的计划,要接着做 | `/dev-resume` |
| 想找架构摩擦点 | `/dev-review` |
| 要沉淀术语或决策 | `/dev-doc` |
| 要盘点遗留项与未完成事项 | `/dev-backlog` |

**分流口径**:开工前先扫 `docs/plans/*/plan.md` 里有没有未勾选任务。有 → 在呈报第 3 块列出来并问用户「接着做,还是只建底图」;用户要接着做,转 `/dev-resume`,本命令不碰那个计划的执行。

## 传进来的参数怎么处理

`/dev-onboard` 的参数字段叫「关注方向」,不是通用请求框。三种输入三种处置:

| 你传的 | 处置 |
|---|---|
| 模块 / 区域 / 主题(「终端渲染」「支付流程」) | 影响 L1、L2 的取景与 L4 的深挖范围,**不改变八块呈报** |
| 动作请求(「帮我加 X」「改掉 Y」) | 停手,告知「这是 `/dev` 的事」,不在本条命令里动手 |
| 盘点类(「统计遗留未做的项」「还剩什么没做」) | 告知「这属于 `/dev-backlog`」,不在本条命令里临时发挥 |

判据很简单:**本命令改变的是理解,不改变任何文件。** 任何要写文件的请求都不属于这里。

## 分层阅读

四层按序读。读到能答出下文「验收判据」就停,不是读完。

| 层 | 读什么 | 回答什么问题 |
|---|---|---|
| **L0 底图**(必读) | `AGENTS.md`、`README`(构建与测试命令原文)、`ROADMAP` 的当前阶段、`CONTEXT` 的词条名清单 | 什么规矩、怎么跑、做到哪了 |
| **L1 判断** | `DECISIONS.md` 的 `有效` 条目(`grep '状态：有效'`);当前关注区域相关的 ADR | 现在按哪些判断在跑、为什么 |
| **L2 历史** | `docs/plans/` 最近 2-3 个特性的 `brief` 第 2 节,以及各自 `plan.md` 开发记录里的「结论」 | 最近在做什么、留了什么坑 |
| **L3 代码鸟瞰** | 目录树、入口文件、测试文件的实际位置 | 代码怎么组织、测试在哪 |
| **L4 点状深挖** | 只在带了具体关注方向时进入 | 开工准备;深挖的规则归 `/dev` 的 `intake` |

两条限制:

- **预算**:整轮不超过上下文 **20%**(可用 `context_usage` 读数)。到线即停,并在第 7 块写明「因预算停止」。
- **L3 只读鸟瞰层**:目录树、入口、配置、一个代表性模块的头部。不逐文件通读——真正的实现理解属于 `intake`。L3 之后仍答不出验收判据,说明缺的是 L1/L2,不是代码。

## 停止条件

同时满足即停:

1. L0 四份读完,L1 的有效判断扫过一遍
2. 能说出构建与测试命令**原文**
3. 能引用 3 条当前有效判断并指出 `J` 编号
4. 第 7 块「我还没搞清的」写得出来(写「无」要说明理由)

## 呈报:八块,固定顺序

八块顺序固定,是为了让人按位置扫,而不是按文字找。

```markdown
## 1. 这是什么项目

三句,用户视角:给谁解决什么问题、靠什么形态跑。

## 2. 怎么跑、怎么测

命令原文,从 `README` 或 `AGENTS.md` 抄,不改写、不意译。

## 3. 当前进度

`ROADMAP` 当前阶段一句话 + 未完成计划清单(含未勾选任务的 `docs/plans/*/plan.md`)。
有未完成的就加一句:接着做走 `/dev-resume <名称>`。

## 4. 六份文档各管什么

一行一个,带路径:`AGENTS.md` / `README.md` / `ROADMAP.md` / `CONTEXT.md` / `DECISIONS.md` / `docs/adr/`。

## 5. 现在按哪些判断在跑

`DECISIONS.md` 有效条目 3-5 条,一条一句,带 `J` 编号。

## 6. 最近三个特性

一行一个:做了什么 / 为什么(理由追到 `brief` 第 3 节或 ADR 编号)。

## 7. 我还没搞清的

诚实清单。写「无」要说明为什么无——无例外的项目不常见,写「无」通常意味着还没读到位。

## 8. 建议下一步

`/dev <需求>`(要动手)| `/dev-resume <计划>`(接历史)| 直接问(只需了解)。
```

## 验收判据

| 判据 | 怎么验 |
|---|---|
| 构建与测试命令**原文** | 逐字对照 `README` / `AGENTS.md`,不许写「大概是 pnpm test」 |
| 当前进度与未完成计划数 | 与 `ROADMAP`、`docs/plans/` 实况一致 |
| ≥3 条当前有效判断并指出编号 | 对照 `DECISIONS.md` |
| 最近某个特性的一个「为什么」 | 必须追得到 `brief` 第 3 节或 ADR,不许自己编 |
| 第 7 块非空且具体 | 「可能有坑」这类写法不合格 |

**抽问**:呈报后停下等用户抽问三题。答不上来 → 回读对应层 → 重报受影响的那几块。抽问之前不算完成。

## 写入边界

- **不新建任何文件。** 项目该有 `AGENTS.md` 却没有时,在呈报里报这个缺陷,不替它现编一份。
- **只提议,不改。** 本轮发现值得长期保留的规矩(构建命令、目录约定、已知坑),写成提议交用户;用户确认后由用户或 `/dev-doc` 写入 `AGENTS.md`。
- **不动判断。** `ROADMAP`、`CONTEXT`、`DECISIONS` 一次都不改:第一次进场没有资格改判断。

## 反例

- 只复述 README 的项目简介就算交差
- 把「最近改了 X」说成「项目目标是 X」
- 声称「已通读全部文档」却答不出测试命令
- 顺手把项目地图写进 `AGENTS.md`——用户没确认的就不是规矩
- 先把代码全读一遍再回来——那是 `/dev-review`,不是入职

## 硬规矩

- 命令原文照抄,不改写
- 每条结论都能追到出处:ADR 编号 / `brief` 节号 / `J` 编号 / 文件路径
- 不确定的只写进第 7 块,不混进前面几块
- 有未完成计划时先问方向,不默认接管
