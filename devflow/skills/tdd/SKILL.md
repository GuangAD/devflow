# tdd — 测试驱动开发

## 默认制

每个涉及行为改动的任务,先写测试再写实现:

1. **写一个失败测试**:在 spec.md 的接缝接口条目上,断言其用例表中的行为(用例表已随门 2 批准)。期望值及其事实源(手算字面量、外部锚点、构造反例、规格示例)已在表中声明,禁止用代码同样的算法重算期望值。
2. **亲眼看它失败**:运行测试,确认失败且失败原因是预期的(功能缺失,而非拼写/导入错误)。这一步不可跳过——没看过它红,就不知道它能不能抓住问题。
3. **写最小实现**:刚好让测试通过的代码,不多写。
4. **亲眼看它变绿**:运行测试;顺带确认没有破坏其他测试,输出干净(无报错无警告)。
5. 下一片。

数值预算类验收(性能/规模/体积)必须落成测试断言或构建期脚本,不接受「运行时打印人工核对」——预算有机检方案是 spec.md 的门 1 要求,实现期兑现它。
一次一个切片:一个测试 → 一段实现 → 重复。重构清理在任务收尾做,保持绿,不加行为。

## 豁免白名单

以下任务可不走 TDD 直接实现:**纯配置或文案改动;无逻辑的静态样式调整;一次性脚本;文档**。

裁量权在执行者,但**必须留痕**:在开发记录(或轻流程的完成汇报)中写明"本任务豁免 TDD,理由是……"。重流程中可预判的豁免段(如渲染任务)可在 plan.md 全局约束**预登记**(豁免范围+验收替代方式),随门 2 一并批准,执行时逐任务注明预登记。豁免不得成为默认;连续多个任务豁免时,回头检查分类是否错了。

## 三种反模式(写测试时自查)

- **实现耦合**:mock 内部协作者、测私有方法、绕过接口验证(直接查库而不过公共接口)。判据:重构就挂但行为没变。
- **同义反复**:断言用被测代码同样的方式计算期望值(如 `expect(add(a,b)).toBe(a+b)`)。永远发现不了错误。
- **水平切片**:一口气写完所有测试再写全部实现——验证的全是想象中的行为。必须垂直切片,让每个测试回应上一个切片的发现。

## 卡住对照表

- 不会写测试 → 先写你希望存在的那个调用(愿望式 API),断言先行;仍不行,问用户。
- 测试特别难写 → 说明设计有问题:耦合过重或接口不清晰。听测试的话,反馈给用户或记入开发记录。
- 只能靠 mock 一切才能测 → 依赖注入缺失的信号。
