# tdd — 测试驱动开发

## 默认制

每个涉及行为改动的任务,先写测试再写实现:

1. **写一个失败测试**:在 spec.md 的 seam 接口条目上,断言其用例表中的行为(用例表与覆盖声明均已随门 2 批准)。期望值及其事实源(手算字面量、外部锚点、构造反例、规格示例)已在表中声明,禁止用代码同样的算法重算期望值。覆盖声明同样照单兑现:矩阵逐行有测试、铁律有断言、枚举范围有生成器——兑现的是已批准的标准,不是自选的覆盖。
2. **亲眼看它失败**:运行测试,确认失败且失败原因是预期的(功能缺失,而非拼写/导入错误)。这一步不可跳过——没看过它红,就不知道它能不能抓住问题。
3. **写最小实现**:刚好让测试通过的代码,不多写。
4. **亲眼看它变绿**:运行测试;顺带确认没有破坏其他测试,输出干净(无报错无警告)。
5. 下一片。

数值预算类验收(性能/规模/体积)必须落成测试断言或构建期脚本,不接受「运行时打印人工核对」——预算有机检方案是 spec.md 的门 1 要求,实现期兑现它。
一次一个切片:一个测试 → 一段实现 → 重复。重构清理在任务收尾做,保持绿,不加行为。

## waiver allowlist

以下任务可不走 TDD 直接实现:**纯配置或文案改动;无逻辑的静态样式调整;一次性脚本;文档**。

裁量权在执行者,但**必须留痕**:在开发记录(或轻流程的完成汇报,即 light track)中写明"本任务 TDD waiver,理由是……"。重流程中可预判的 waiver 段(如渲染任务)可在 plan.md 全局约束**预登记**(waiver 范围+验收替代方式),随门 2 一并批准,执行时逐任务注明预登记。waiver 不得成为默认;连续多个任务 waiver 时,回头检查分类是否错了。

## 三种反模式(写测试时自查)

- **实现耦合**:mock 内部协作者、测私有方法、绕过接口验证(直接查库而不过公共接口)。判据:重构就挂但行为没变。
- **同义反复**:断言用被测代码同样的方式计算期望值(如 `expect(add(a,b)).toBe(a+b)`)。永远发现不了错误。
- **horizontal slice**:一口气写完所有测试再写全部实现——验证的全是想象中的行为。必须 vertical slice,让每个测试回应上一个切片的发现。

## mutation check(pinned case 必做)

**归属**:变异操作由正在改动这些文件的 implementer 在其红绿循环内完成;controller 不代做变异——controller 层面遇「评审声称 vs 源码实况」分歧,走「读源码静态路径证明 + 交复审者复核裁决」链(见 code-review 的 controller 处置速查)。

**触发**:为已发现的缺陷补写 pinned case 时——评审发现的处置、Important/Minor 修复、以及任何「加个守卫防复发」的用例。常规 vertical slice 不必做;专为某个缺陷写的用例必须做。

写完用例并看它变绿之后,回去撤销(或改坏)那一行修复,读数:

1. 这条用例**确实转红**,失败原因指向该缺陷而不是笔误。
2. **红的是这一条**。若是另一条既有用例转红,说明真正钉住缺陷的是那条老用例,新写的这条在搭便车——同样不合格。
3. 改回来后**恢复全绿**,这条用例才算留得住。

三条都过,才算这条断言有鉴别力。

**改坏了却仍然全绿,说明断言是空心的**,回头对照上面的三种反模式重写。最常见的修法:把「断言它存在」换成「真的调用它并核对产出」——`toBeDefined()`、`typeof === "function"` 这类断言对「字段存在但接错」完全无效,要把它当函数调、把值当值比。

**留痕**:在 plan.md 该任务的开发记录行(或轻流程的完成汇报)写明结果,一句话即可:`mutation check:删 X 后 <用例名> 转红`。不留证据视为没做。

它与默认制第 2 步是一体的两端:「亲眼看它失败」证明这条用例不是一开始就绿;mutation check 证明它不会在别的代码兜底之后退化成永远绿。两端夹住,测试才是活的。

## 覆盖兑现与回填

spec.md 的覆盖声明(等价类矩阵、机检铁律、枚举范围)是门 2 批准的覆盖标准,实现期照单兑现:

1. **矩阵逐行有测试,铁律有断言,枚举有生成器**。枚举不是手写几万条 it(),是生成代码循环断言;铁律的 oracle 与被测实现必须方向独立(逆方向实现,如 round-trip 解析器;同算法重算不算)。
2. **生成器与铁律创建时验证一次鉴别力**:临时改坏一行实现,枚举或铁律必须转红;全绿说明断言空心,对照三种反模式重写。为钉住缺陷补写的矩阵行,走上面的 mutation check。
3. **实现中发现覆盖声明没列的边界 → 走 spec.md 变更记录回填维度或代表行,再补测试**。不许只在测试文件里默默加用例——spec 是覆盖的唯一事实源,门 2 批了什么,评审就按什么查。

## 卡住对照表

- 不会写测试 → 先写你希望存在的那个调用(愿望式 API),断言先行;仍不行,问用户。
- 测试特别难写 → 说明设计有问题:耦合过重或接口不清晰。听测试的话,反馈给用户或记入开发记录。
- 只能靠 mock 一切才能测 → 依赖注入缺失的信号。
