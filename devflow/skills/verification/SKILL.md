# verification — 证据先于声称

**铁律:本回合没有运行过验证命令并读取完整输出,就无权声称任何"完成/通过/修复"。**

## 门(每次声称前过一遍)

1. **识别**:什么命令能证明这个声称?
2. **运行**:完整地、新鲜地跑一遍。过去的运行、记忆中的结果、"应该会过"都不算。
3. **读取**:完整输出 + 退出码,不是只看最后一行。
4. **核对**:输出真的支持声称吗?不支持 → 如实报告实际状态与证据。
5. **然后**才开口。

## 声称 ↔ 证据对照表

| 想声称 | 必须拿出 | 不算数 |
|---|---|---|
| 测试通过 | 本回合测试命令输出:0 失败 | 上次运行、"逻辑上应该过" |
| 构建成功 | 构建命令退出码 0 | lint 通过、日志看起来正常 |
| bug 修好 | 原始症状的复现信号变绿 | "代码改了,应该好了" |
| 回归测试有效 | 红→绿都亲眼看过的记录 | 只看到它绿过一次 |
| 任务完成 | plan.md 验收标准逐项核对 + git 里的实际变更 | subagent 或自己的"我觉得做完了" |

## 不可达验收项

验收项在本机不可达时(平台差异、权限、环境缺失),显式标注「本机不可达、未验证」并保留为遗留事项呈报;禁止以不等价的替代测试关闭验收项——替代测试只能作旁证,不能作关闭依据。

## 禁用表述

任何形式的"应该可以了""大概没问题""看起来对了"。验证之前表达满意("搞定了!")同样违规——先跑,再说话。

## 委托场景

subagent 报告"已完成"不算完成:检查 git diff 与其报告的提交是否一致、测试证据是否在报告中齐全。核实过,才有资格向用户转述。
