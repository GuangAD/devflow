# grilling — 访谈原语

把用户的想法访谈成一份没有含糊分支的设计。

## design tree

把讨论建模为一棵**design tree**:每个决策分支出挂在它下面的子决策。根是"要做什么",往下分出方案选择、边界行为、优先级等分支。

## round 与 frontier

按 round 工作。每一轮的**frontier** = 所有前置条件已落定、现在就能问的问题。

- **一轮问 3-6 个。** 超过 6 个说明要么该拆需求,要么层次太深、该先问更上层
- 当前能问的有 7-12 个 → 分两批,先说明「这一层大概 N 个,分两次问」
- 超过 12 个 → 停下,说明「这事儿比我想的大」,重看边界
- 每题编号并附**推荐答案**,措辞让「好」等于同意
- 用户回答会解锁下游问题 → 重新计算 frontier,进入下一轮
- **同一轮内互相依赖的问题,靠后的属于下一轮**,不硬塞
- 访谈结束时,design tree 没有任何分支是被默默假设的

格式:

```
❓ Q1 <问题标题>:<题干,可含选项>

➡️ 推荐:<你的答案与一句理由>

---
❓ Q2 …
```

写「模糊匹配我打算做成输一部分就能匹配,对吗?」而不是「你想用哪种匹配方式?」。

用户的回答可以是逐条、整轮接受(「都按你推荐的来」)、或部分回答。答不了的留在树上,下一轮再问。

## 先过滤,只问该问的

| 类别 | 例子 | 处置 |
|---|---|---|
| **用户的事** | 搜不到时显示什么、要不要支持错别字容错、先做哪个 | 必须问 |
| **我的事** | 函数叫什么、放哪个目录、用哪个库、内部怎么拆 | 自己定,在文档里标 `[我]` |
| **代码的事** | 现在怎么跑的、有没有现成的、项目定过什么规矩 | 自己查,不许问 |

一轮里如果后两类占了多数,说明事实查得不够,回去补。

## 分工铁律

- **事实是你的活**:frontier 问题需要代码库或环境事实时,自己去查或派 subagent,绝不反问用户任何"查一下就知道"的东西。探索未完成只阻塞其下游问题,其余照常问。
- **决策是用户的活**:每个决策点都要交付给用户并等待回答。禁止自己替用户拍板设计决策。
- **自己做的选择必须标出来**:凡是自己拍的决定,写成「我的判断」,**绝不许写成「用户同意过的」**。

## 什么时候停

不是所有问题都有答案,而是**没有会影响方向的未知了**:

- 剩下的只影响「怎么做」,不影响「做什么」→ 停
- 剩下的答错了可以事后调 → 停
- 剩下的不定就做不下去 → 继续问

## 没缺口就不访谈

用户给的文档已经写全、和代码现实对得上、没有冲突项 → 直接说「我看明白了,这就去做」,跳过访谈。

## 结束与确认

frontier 为空时:向用户完整总结共识(目标、不要什么、方案、留着的欠账、非目标),声明"design tree 已无含糊分支",**等用户确认达成共识**。确认之前不写任何设计文档、不碰任何代码。

用户中途改变想法或给出否定了前面某轮答案的新信息时:更新 design tree 上受影响的分支,重算 frontier,把受波及的已"定"决策重新交付确认。
