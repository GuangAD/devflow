# grilling — 访谈原语

把用户的想法访谈成一份没有含糊分支的设计。产出将用于撰写设计文档,访谈必须覆盖:背景与问题、目标与非目标、方案取舍、数据结构、接口与测试接缝、编码方向。

## 设计树

把讨论建模为一棵**设计树**:每个决策分支出挂在它下面的子决策。根是"要做什么",往下分出方案选择、数据建模、边界行为等分支。

## 轮次与前沿

按轮次工作。每一轮的**前沿(frontier)**= 所有前置条件已落定、现在就能问的问题。

- 每轮把整个前沿一次性抛出,每题编号并附你的**推荐答案**(用户可以一个词接受)。
- 用户回答会解锁下游问题 → 重新计算前沿,进入下一轮。
- 同一轮内互相依赖的问题,靠后的属于下一轮,不硬塞。
- 访谈结束时,设计树没有任何分支是被默默假设的。

格式:

```
❓ Q1 <问题标题>:<题干,可含选项>

➡️ 推荐:<你的答案与一句理由>

---
❓ Q2 …
```

## 分工铁律

- **事实是你的活**:前沿问题需要代码库或环境事实时,自己去查或派子代理,绝不反问用户任何"查一下就知道"的东西。探索未完成只阻塞其下游问题,其余照常问。
- **决策是用户的活**:每个决策点都要交付给用户并等待回答。禁止自己替用户拍板设计决策。

## 结束与确认

前沿为空时:向用户完整总结共识(目标、方案、数据结构、接缝、非目标),声明"设计树已无含糊分支",**等用户确认达成共识**。确认之前不写任何设计文档、不碰任何代码。

用户中途改变想法或给出否定了前面某轮答案的新信息时:更新设计树上受影响的分支,重算前沿,把受波及的已"定"决策重新交付确认。
