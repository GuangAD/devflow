# dev-review — 代码库巡检

定期健康检查:找出"由浅加深"的重构候选。产出的是**调查报告**,不是动手改造;用户选中某个候选后,建议其以 `/dev <候选描述>` 进入重流程(heavy track)。

## 第一步:定范围(YAGNI)

- 用户给了方向(模块/痛点)→ 用它。
- 没给 → `git log --oneline -100` 找**热点**:反复被改动的文件与目录才是深挖对象,长期不动的角落不值得投资。热点分散就适当放宽。

## 第二步:扫描

**优先派 subagent**(环境支持时)做有机漫步,按以下摩擦信号记录;无 subagent 则自己在热点区域直接走查:

- 理解一个概念需要在多个小文件/模块间反复横跳(无**局部性**)
- 模块接口的复杂度接近其实现(浅模块):方法多、参数杂、实现薄
- 为测试而抽出的纯函数,但真正的 bug 藏在调用编排里
- 紧耦合模块跨边界泄漏内部细节
- 区域无测试,或现有测试必须伸进内部才能测(seam 缺失)

对每个疑似浅模块做**删除测试**:想象删掉它——复杂度凭空消失说明它是传达室;复杂度在多个调用点重新出现,说明它在挣饭吃。

对照 `CONTEXT.md` 的领域词汇命名候选,对照相关 ADR 检查冲突。

## 第三步:报告

写入 `docs/reviews/<YYYY-MM-DD>-architecture-review.md`(目录不存在则创建),每个候选一张卡:

```
### 候选 N:<候选名(用领域词汇,不用实现名)>

- **文件**:<涉及文件/目录>
- **问题**:<现状为什么造成摩擦>
- **方案**:<改动一句话描述>
- **收益**:<用 杠杆(leverage)/局部性(locality) 与可测试性表述>
- **改动前 → 改动后**:<两行示意,前:结构现状;后:深化后结构>
- **推荐强度**:强烈建议 | 值得探讨 | 存疑
- **ADR 冲突**:<若与某 ADR 冲突,标注编号并说明为什么值得重开;无则删去本行>
```

报告末尾给**首推**:最值得先做的一个及理由。

## 第四步:交付

向用户呈现报告路径与候选一览(名称+一行摘要+强度),问:"想深入探讨哪一个?"用户选中 → 提示:"可以直接 `/dev <该候选的一句话描述>` 进入完整设计流程。"用户不选,到此为止——**不擅自开工**。
