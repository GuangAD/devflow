# debugging — 根因先行调试

**铁律:没有找到根因之前,不做修复。** 症状式糊补(报错就 try-catch 吞掉、改边界值让测试碰巧通过)是禁止项。

## 第一步:建复现信号

在形成任何假设之前,先拥有"**一条命令,跑一次,能对准这个 bug 变红**"的信号:

1. 优先写失败测试(单测/集成/e2e,选能到达 bug 的最近 seam)。
2. 不适合测试框架的:脚本复现(curl、CLI 加输入比对输出、重放日志)。
3. 偶发 bug:目标不是完美复现,是**可调试的复现率**——循环触发、加并发、压时间窗,把 1% 拉到两位数;同时把信号拧紧(更快、断言具体症状而非"没报错"、固定时间与随机种子)。

真的建不出信号 → 停下,向用户说明试过什么、需要什么(环境访问、抓包文件、加临时插桩的许可)。**没有信号不进入假设。**

## 第二步:定位根因

- 通读错误信息与堆栈全文(答案常就在里面);记录确切症状,供修后验证。
- 查最近变更:`git log`/`git diff`,这个 bug 最可能是哪次改动引入的。
- 多层系统:在层与层的边界插桩取证,先定位断在哪一层,再深入。
- 找同代码库里**能正常工作**的相似代码,对比差异。

## 第三步:假设与验证

- 形成假设时写下可证伪的预测:"若是 X,改 Y 会让 bug 消失"。
- 一次只改一个变量;失败就换假设,不在失败修复上叠加新修复。
- 假设排序后(3 个以上时)给用户过目——领域知识常能瞬间重排;用户不在,按自己的排序继续,不阻塞。

## 第四步:修复与回归

- 回归测试写在修复**之前**:把复现信号转成该 seam 上的失败测试 → 看红 → 修复 → 看绿 → 用**原始场景**(未最小化的)再验证一遍。
- 修复保持单一:只修根因,不顺手改进、不捆绑重构。
- **三次修复失败 = 架构问题**:停下,向用户说明每次失败暴露了什么,讨论是否该改设计,而不是尝试第四次。

## 收尾清单

- [ ] 原始复现场景不再复现
- [ ] 回归测试通过(或已记录"无正确 seam",这本身是架构发现,值得提给 /dev-review)
- [ ] 临时调试日志/脚本全部清除(调试日志统一带 `DBG-` 前缀,清理时一次搜索)
- [ ] 根因写进 commit message:是什么、证据、为什么这样修

## 完成声称

宣报告一段落前,读取 verification 技能:本回合跑过验证、读全输出,才有资格说"修好了"。
