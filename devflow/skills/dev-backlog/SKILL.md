# dev-backlog — 待办盘点

回答一个问题:**这个项目现在欠着什么、谁在欠、不还会怎样。**

**只读。** 不改任何文件、不清账、不动判断。清账转 `/dev`(新做)或 `/dev-resume`(接着做)。

## 什么时候用

- 一个特性收尾之后(门 3 刚过,账最容易对不上)
- 换会话、放长假之前
- 拍板下一步做什么之前
- 怀疑「账对不上」时——任务看着做完了,`plan.md` 却没勾

## 只扫七类来源,不凭印象

| # | 来源 | 取什么 |
|---|---|---|
| 1 | `docs/plans/*/plan.md`「任务」节 | 未勾选任务 + 进度(n/m) |
| 2 | 同上「遗留项」节 | `brief` 第 6 节欠账的排期 |
| 3 | 各计划 `brief.md` 第 6 节 | 未定项,连「不定会怎样」一起取 |
| 4 | 各计划 `plan.md` 开发记录 | 挂起 Minor、waiver、结论里留给下游的坑 |
| 5 | 各计划 `brief.md` 第 7.1 与最终报告 | 验收项「未验证 / 本机不可达」 |
| 6 | `DECISIONS.md` | `已废弃` 但未清理的、`有效` 但被新需求顶掉的 |
| 7 | `ROADMAP.md`「下一步」、`docs/issues/`、代码 `TODO` / `FIXME` | 项目级未做的事、已知未修缺陷 |

来源不存在就写「不存在」,**不许静默跳过**:没有 `docs/plans/` 本身就是一条结论(说明这个项目没跑过 dev 流程);没有 `DECISIONS.md` 说明判断从来没有跨特性留痕。

## 准入:三条全过才进清单

1. **有承接位置**:指得出具体计划、任务号或 `ROADMAP` 条目,不是「以后再说」
2. **能写出后果**:不做会怎样,一句具体的话;「可能有影响」不算
3. **核实过现状**:用 `git log` 与文件实况确认它确实还没做

第三条最容易被跳过,也最容易出错:任务已经提交但没勾选,那不是「未做」,是**记账缺口**——单列一类,别混进未完成任务里。

## 分类与排序

| 类 | 内容 | 优先级 |
|---|---|---|
| **A 未验证** | 门 3 没过、验收项「未验证 / 本机不可达」 | 最高:东西交了但没证明 |
| **B 阻塞** | 未勾选任务里挡着别的任务的 | 高 |
| **C 未完成** | 其余未勾选任务、遗留项排期 | 中 |
| **D 欠账** | 未定项、挂起 Minor、waiver | 低 |
| **E 记账缺口** | 已提交未勾选、开发记录缺块、台账该有而没有 | 随手可修 |
| **F 项目级** | `ROADMAP` 下一步、`issues`、`TODO` | 按用户取向 |

排序不是审美:上面这个顺序的依据是「不做的话,哪一项会让已交付的东西站不住」。

## 呈报

```markdown
# 待办盘点 · <YYYY-MM-DD>

## 一句话
共 N 项:A 类 x / B 类 y / C 类 z / D 类 k / E 类 m / F 类 j。
其中 p 项有明确承接,其余只是记账缺口或纯欠账。

## A 未验证
| 项 | 来源 | 不验证的后果 |
|---|---|---|
| 验收「左栏可收起」本机不可达 | `docs/plans/x/brief.md` 第 7.1 节 | 交付声明留洞 |

## B 阻塞
| 计划 | 任务 | 挡谁 |

## C 未完成
| 计划 | 任务 / 遗留项 | 排期 |

## D 欠账
| 计划 | 欠的是什么 | 不定会怎样 |

## E 记账缺口
| 计划 | 任务 | 证据 |
|---|---|---|
| x | T3 | `git log` 有 `a1b2c3d` 引用 T3,但 `plan.md` 未勾选 |

## F 项目级
| 来源 | 事项 |

## 覆盖声明
- 扫过:<七类来源里存在的那些>
- 不存在:<缺哪些,缺它意味着什么>
- 没扫:<哪些没扫、为什么>

## 三问
1. 优先级对不对
2. 有没有我漏掉的来源
3. 哪些现在就要清
```

排版按 `self-check.md` 第 9 条:一行一项,不把三项焊进一句。

## 验收判据

| 判据 | 怎么验 |
|---|---|
| 数字自洽 | 「共 N 项」等于各表行数之和;计划数与任务数与文件实况一致,不许估 |
| 每项可回查 | 抽 3 项按来源路径打开,原文对得上 |
| 无静默跳过 | 覆盖声明列全七类来源的存在性 |
| 缺账能识别 | 至少核过一遍 `git log` 与勾选状态的一致性 |

## 只读边界

- 不改 `plan.md`、不清 `docs/issues/`、不动 `DECISIONS.md`、不删 `TODO` 注释
- 发现该修的地方写进清单交用户,不顺手动手
- 清账由 `/dev`(新做)或 `/dev-resume`(接着做)执行,本命令不碰

## 预算

L0 底图(`AGENTS.md`、`README` 的构建与测试命令、`ROADMAP` 当前阶段)+ 七类来源扫描,整轮不超过上下文 **25%**。计划很多时按「最近改动 + 有未勾选任务」筛,并在覆盖声明里写明筛掉了哪些。

## 与其它的分流

| 你其实想 | 用 |
|---|---|
| 接着做某个未完成计划 | `/dev-resume <名称>` |
| 从清单里挑一件新做 | `/dev <描述>` |
| 了解项目是什么 | `/dev-onboard` |
| 找架构摩擦(不是待办) | `/dev-review` |
| 沉淀术语或决策 | `/dev-doc` |

## 反例

- 把已完成但未勾选的任务报成「未做完」
- 把几百条 `TODO` 注释原样罗列,不判后果——那是噪音不是清单
- 静默跳过不存在的来源,让人以为全扫过了
- 清单里出现「优化代码」「补充文档」这类没有承接位置的项
- 顺手把清单改成勾选状态——本命令只读

## 硬规矩

- 每条带来源路径(文件 + 节号或行号)
- 不把建议当待办:没人在欠的事不进清单
- 数字必须自洽,不许「大概十几项」
- 覆盖声明必写,缺来源要说明缺它意味着什么
