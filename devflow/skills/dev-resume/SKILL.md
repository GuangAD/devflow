# dev-resume — 恢复协议

前提认知:**一切执行状态都在 plan.md 和 git 里,不在你的记忆里。** 上下文被压缩过或换了会话,都按本协议从头恢复,不依赖任何残留印象。

## 第一步:定位计划

- 用户给了路径或特性名 → 直接定位 `docs/plans/<...>/plan.md`。
- 没给 → 扫描 `docs/plans/*/plan.md`,列出所有含未勾选任务的计划(名称 + 进度:已完成 n/共 m),让用户选。
- **特殊状态:只有 brief.md、没有 plan.md**(上次在门 1 后停止)→ 列出这些目录,用户选中后跳到第四步 b。

## 第二步:重建上下文

1. 读 plan.md:任务清单(勾选状态)、依赖、开发记录(此前的评审发现、waiver、变更登记,**以及每条的「结论」——那是上游任务留给你的跨会话软依赖通道**)。同时看「开工前接口预检」块:有结果且不是「待 T1 开工前填写」之类占位,记为**预检已完成**;否则记为**预检未完成**。
2. 读同目录 brief.md:要什么、不要什么、关键决策、留着的欠账、验收标准(冻结快照)。
3. 读同目录 spec.md:数据结构、模块划分、覆盖标准、接口面清单——整体骨架。
4. 读当前要续做的那个任务的 `tasks/T<n>.md`:接口伪代码、开发步骤、测试规格。不读别的任务。**例外**:第二步判定预检未完成时,允许读全部任务契约与 `spec.md`,仅用于第四步 a 的一次性预检;预检做完后仍只读当前任务。
5. `git log --oneline` **双向核对**:
   - 正向:勾选声称完成的任务,其 commit 哈希确实存在于历史;
   - 反向:开发记录已回填 commit 哈希(或历史中存在引用该任务号的提交)但任务未勾选——上次中断发生在「提交后、落盘前」的窗口。确认该 commit 内容与任务相符后,补勾选、补记开发记录,**不重做该任务**。

发现不一致(勾了但 commit 不在)→ 向用户报告,以 git 实际状态为准修正勾选。

## 第三步:检查工作区残局

`git status` + `git diff` 查看未提交改动:

- **干净** → 直接续做。
- **有残局**(上个会话中断在任务中间):
  - 能判断残局"接近完成且方向正确" → 续完该任务,正常走评审与提交。
  - 判断不了或方向存疑 → 把现状(改了哪些文件、大概进度)给用户,问:续完还是丢弃(`git checkout/restore`)?**丢弃需用户确认,不自作主张。**

## 第四步:续做

**a. 有 plan.md**:若第二步判定预检未完成,先按 dev 技能**阶段 4 开头**执行一次性 T1 前接口预检——跨任务接口名称、签名、数据形状、文件落点与 `spec.md` 是否一致,以及 `self-check 2.1` 的测试命令可解析(T1 测试基座、跨任务测试模块命名与 `-k` 模式、每条 `Expected:` 的跑测条数);结果写入 `plan.md`「开发记录」的「开工前接口预检」块,再记录 T1 的 BASE。随后从第一个未勾选任务开始,严格按阶段 4 的任务循环执行(tdd → verification → code-review → commit → 勾选回填)。预检已完成则跳过,不重做。

**b. 只有 brief.md**(已批准):读取 dev 技能,从**阶段 2(切片)**继续:切片写 plan.md → 写 spec.md 与任务契约 → 跑自查 → 进入开发。

## 纪律

- **主动切换与被动中断走同一条协议**:dev 阶段 4 在上下文吃紧时会在任务边界提示开新会话。这与意外中断是同一条恢复路径,不额外产生交接文档——因为一切状态都在 plan.md 与 git 里。
- 恢复后进入阶段 4 时,先按 dev 技能「依赖与派发顺序」重算 ready set:**不要**机械地从任务清单的下一个编号继续,先确认它的硬依赖都已完成。
- 一次性动作不随恢复重做:T1 前接口预检只看 `plan.md`「开工前接口预检」块是否已有结果,有则跳过;恢复不是重新开工,已批准的门 1 / 门 2 同理。
- 恢复不是重开:已批准的 brief 不需要重新过门 1;除非开发记录显示某任务被标记为"暂停等用户"。
- 恢复过程中用户补充了新需求 → 那是变更,不是恢复的一部分:小变更直接追加一个任务;设计级变更走回退协议。
