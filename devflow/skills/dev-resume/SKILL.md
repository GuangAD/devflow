# dev-resume — 恢复协议

前提认知:**一切执行状态都在 plan.md 和 git 里,不在你的记忆里。** 上下文被压缩过或换了会话,都按本协议从头恢复,不依赖任何残留印象。

## 第一步:定位计划

- 用户给了路径或特性名 → 直接定位 `docs/plans/<...>/plan.md`。
- 没给 → 扫描 `docs/plans/*/plan.md`,列出所有含未勾选任务的计划(名称 + 进度:已完成 n/共 m),让用户选。
- **特殊状态:只有 design.md+spec.md、没有 plan.md**(上次在门 1 后停止)→ 列出这些目录,用户选中后跳到第四步 b。

## 第二步:重建上下文

1. 读 plan.md:全局约束、任务清单(勾选状态)、开发记录(此前的评审发现、waiver,**以及每条的「结论」——那是上游任务留给你的跨会话软依赖通道**)。
2. 读同目录 design.md:整体设计决策(冻结快照)。
3. 读同目录 spec.md:接口规格与用例表,**含变更记录节**——它是开发期接口真值的唯一变更 ledger。
4. `git log --oneline` 核对:勾选声称完成的任务,其 commit 哈希确实存在于历史。

发现不一致(勾了但 commit 不在)→ 向用户报告,以 git 实际状态为准修正勾选。

## 第三步:检查工作区残局

`git status` + `git diff` 查看未提交改动:

- **干净** → 直接续做。
- **有残局**(上个会话中断在任务中间):
  - 能判断残局"接近完成且方向正确" → 续完该任务,正常走评审与提交。
  - 判断不了或方向存疑 → 把现状(改了哪些文件、大概进度)给用户,问:续完还是丢弃(`git checkout/restore`)?**丢弃需用户确认,不自作主张。**

## 第四步:续做

**a. 有 plan.md**:从第一个未勾选任务开始,严格按 dev 技能**阶段 3** 的任务循环执行(tdd → verification → code-review → commit → 勾选回填)。

**b. 只有 design.md+spec.md**(已批准):读取 dev 技能,从**阶段 2(计划)**继续:补全 spec.md 用例详版 → 写 plan.md → 过门 2 → 进入开发。

## 纪律

- **主动切换与被动中断走同一条协议**:dev 阶段 3 在上下文吃紧时会在任务边界提示开新会话。这与意外中断是同一条恢复路径,不额外产生交接文档——因为一切状态都在 plan.md 与 git 里。
- 恢复后进入阶段 3 时,先按 dev 技能「依赖与派发顺序」重算 ready set:**不要**机械地从任务清单的下一个编号继续,先确认它的硬依赖都已完成。
- 恢复不是重开:已批准的计划不需要重新过门 2;除非开发记录显示某任务被标记为"暂停等用户"。
- 恢复过程中用户补充了新需求 → 那是变更,不是恢复的一部分:小变更走轻流程(light track)追加任务;设计级变更走回退协议。
